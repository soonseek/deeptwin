# DeepTwin 성장·재평가·운영 승격 계약

작성일: 2026-09-07 · 계약 버전: `growth-v1` · 상태: 위임받은 추천안에 따른 상세 설계. 제품 구현·실제 효과·사용자에 의한 개별 기술안 검토 완료를 뜻하지 않는다.

## 1. 권위·적용 범위

사용자는 전체 설계 후 구축·테스트까지 진행하고, 변경 필요 시 전체 맥락을 고려한 추천안을 자동 결정하는 개발 방식을 선택했다. 또한 이전 업무 큐 재평가가 일정 품질에 도달한 후 3회 이상 큰 개선이 없으면 종료하는 동작을 요구했다. **이 조기 종료는 구현되는 프레임워크 안의 개선 실험에만 적용한다. 개발 작업·전체 프로젝트·개발 세션을 조기 종료하는 규칙이 아니다.**

본 문서의 `patience=3`, 비교 방법, 품질 프로필, 상태·중단 정책은 위 요구를 구체화한 위임 설계 결정이다. 논문이 해당 수치를 입증했거나 사용자가 아래의 각 수치를 따로 검토했다고 기록하지 않는다. 실제 사용자 환경의 운영 승격에는 여전히 권한 있는 사람의 정확한 버전 승인이 필요하다. 개발 의사결정 위임으로 그 제품 기능을 자동 승인으로 바꾸지 않는다.

상위 근거:

- [통합 제품 설계 §4–6](../../../docs/superpowers/specs/2026-09-06-deeptwin-integrated-product-design.md): 원 수행, 실제 대안, 세 범위, SPLI, 재실행, 사람 승인과 기록 경계.
- [그래프 생성 계약](../../../docs/superpowers/specs/2026-09-07-deeptwin-graph-generation-design.md): 환경 버전은 역할·원형 산출물·인계·모델·도구·권한을 포함한다.
- [검증·선별 §3–8](../../../docs/superpowers/specs/2026-09-07-deeptwin-verification-selection-design.md): 의미 판정·시험 유효성·공동 실패·렌즈 효과·성장 증거의 구별.
- [렌즈 정의](../../../docs/lenses/definition-candidates.md), [조합 계약](../../../docs/lenses/composition-contract.md), [출처 지도](../../../docs/lenses/source-map.md), [검토 사례](../../../docs/lenses/review-cases.md), [검토 상태](../../../docs/lenses/review-report.md): 원자 주장·용도·기권·출처 제한과 해석/효과 상태.
- [현 평가 계획](../../../docs/superpowers/plans/2026-09-07-deeptwin-critic-evaluation.md), [Q01 Task](../../../evals/deeptwin/tasks/v01-q01/Task.md): 기존 계약·오프라인 검사는 실제 성장 평가가 아니다. 본 문서는 Q01을 수정하거나 실제 harness 점수를 생성하지 않는다.

## 2. 하나의 성장 에피소드가 다루는 것

실제로 보존된 노드·태스크 실행 경계와 그 경계의 산출물에서 시작한다. 모델 호출 내부의 숨은 생각을 추정해 되감거나, 대안을 사후 원 실행에 삽입하지 않는다.

1. 원 수행의 입력·모델/추론 설정·환경·도구 결과·전체 산출물·전달·공개 판단 근거를 고정한다.
2. 사용자가 작성하거나 업로드한 **자기 버전의 전체 또는 일부 산출물**을 원본과 연결한다. 최초 업무 설명, 요구 수정, 개발 검토 승인, 단순 수정 지시는 이 대안으로 둔갑시키지 않는다. 설명은 선택적 보조 증거다.
3. 문구·행·페이지·이미지 영역 등 실제 형식의 대응을 확인하고 관찰 차이를 만든다. 위치 대응이 미확정이면 추정과 확정을 구별하며, 파일 전체가 같다고 가장하지 않는다.
4. 시스템 결손과 사용자 판단 가설을 경쟁시킨다. 정보 추출·검색·활용·전달 실패, 새로운 조건부 판단, 기존 지식 미적용, 일회성 예외, 대안 오류, 원인 미확정, 일반화할 지식 없음이 모두 가능한 결론이다.
5. 실제 판단 차이와 확인된 `H_exp`가 있고 설명들이 갈릴 때 SPLI의 질문·반대 예측·렌즈 버전을 먼저 고정한다. 이후 얻은 새 행동·응답 `E_phi`로 `H_exp`를 검증·갱신한다.
6. 증거에 연결된 복원·학습·보호 변경을 별도 후보로 만든다. 후보 환경을 포크하고 관련 이전 업무 큐를 기준 환경과 짝지어 재실행한다.
7. 허용된 자동 반복 또는 필요한 사람 개입을 거쳐 개선을 탐색한다. 조기 종료는 이 튜닝 반복을 끝내고 최고 유효 후보와 결과를 남긴다.
8. 후보를 고정하고 별도 미관측/전향·경계·회귀·출처·안전 검사를 수행한다. 권한 있는 사람이 개선과 손실·범위를 보고 **정확한 환경 번들 버전**을 승인해야 운영 버전이 바뀐다.

대안의 양이 적어도 시작할 수 있다. `evidence_scope`, `change_scope`, `impact_scope`를 구분한다. 부분 증거가 변경의 후속 영향을 그 부분으로 제한하지 않으며, 반대로 미검토 부분까지 사용자 의도를 확인했다고 주장하지 않는다. 사용자의 침묵·생각을 실행 권한으로 읽지 않으며 “이 정도만 보고 다시”라는 특별 버튼이나 전체 피드백 완료 선언을 강제하지 않는다.

## 3. 최소 타입 계약

아래는 구현 언어와 무관한 필드 계약이다. `Ref`는 `{id: string, version: string, sha256: hex64}`의 내용 고정 참조다. `ArtifactRef`는 여기에 `media_type`, `byte_length`, `access_policy_ref`, `storage_ref`를 갖는다. 해시만 남아 원문이 없는 경우 `availability=missing`이며 재현 가능한 원본으로 세지 않는다. 시각·음성·표·문서 산출물을 일반 텍스트로 변환한 내용만으로 원형을 대체하지 않는다.

## 4. 렌즈·인과·변경의 접근 경계

- 초기 설계, 크리틱 반례 탐색, 대안 이후 SPLI는 같은 원자 정의를 참조할 수 있지만 입력 자격·도구·결과 효력은 분리한다. 현재의 17개 정의 후보는 검토된 문서 자료이지 학술·효과·운영 자격이 자동 부여된 목록이 아니다.
- 탐구자는 정의의 질문·조건·반대 예측·기권·금지 추론을 사용한다. 철학자 역할극, 렌즈명 부착, 새 감독 노드 수는 작동 증거가 아니다. 선택·비선택·조합·충돌·기권과 내용 버전을 기록한다.
- `H_phi/S_phi`는 제한된 에피소드 해석 감사 저장소에만 둔다. 변경 생성기와 운영 검색기의 입력 allowlist에 넣지 않는다. 변경 생성기는 실제 증거로 갱신된 `H_exp`와 검증 가능한 조건·행동·예외를 받는다.
- 원 대안의 문구·파일을 실행 입력이나 프롬프트에 복사해 같은 결과를 만든 것을 흡수 성공으로 세지 않는다. 복사·검색 노출 검사를 포함하고, 효과 평가에서는 대안 자체에 접근하지 않는 새로운 수행을 확인한다.
- 시스템 결손이 충분한 원인이면 복원 실험부터 수행할 수 있다. 모든 결손에 SPLI를 강제하지 않는다. 새 행동 증거가 필요한 가설만 보류하며 관련 없는 업무 전체를 멈추지 않는다.
- 사용자 철학·성격·정치/종교·도덕 등급 프로필은 만들지 않는다. 출처의 학술 충실도, 질문의 판별력, 변경의 실제 효과는 서로 다른 증명이다.
- 평가 기준·승인 정책 변경도 제안할 수 있으나 현재 후보가 스스로 통과 기준·승인 권한을 완화할 수 없다. 변경 전 기준의 결과를 유지하고 별도 정책 변경 계보를 만든다.

## 5. 이전 업무 큐의 짝지은 재평가

큐는 `work_id`, 원 입력/원형 파일 버전, 분류, 기준 실행 경계, 권한·도구 상태, 필수 산출물, 평가 항목과 개별 가중치가 고정된 manifest다. 선택 이유와 제외 이유를 기록하며 실패한 항목을 실행 후 조용히 빼지 않는다. 직접 영향을 받는 역할뿐 아니라 예상 후속 산출물·다른 역할·관련 과거 업무를 포함한다.

각 라운드에서 같은 큐·허용 자료·평가기준·초기 상태로 **불변 기준 환경과 후보 환경을 실제로 수행**한다. 원래의 과거 결과는 참고로 남기되 현재의 기준 재실행을 대신하지 않는다. 모델 변동·시간·외부 자료 변경의 교란을 줄이기 위해 짝 실행 순서와 반복 수를 사전에 고정하고 실제 순서를 기록한다. 통제할 수 없는 제공자 버전은 식별 한계와 실행 시각을 남긴다.

프레임워크 도구 실행기는 각 환경에 별도 상태를 제공한다. 발송·구매·게시·원본 변경을 재평가라는 이유로 재실행하지 않는다. 기록된 읽기 결과 재생, 승인된 격리 복제본, 별도 샌드박스 중 지원되는 경로를 지정한다. 재생 자료가 없는 동작은 `not_reproducible`이며 그 영향 범위의 효과를 확인했다고 하지 않는다. 코드/파일 생성은 각 전용 경로의 실제 산출물과 형식 검사·렌더링/시각 검토가 필요하다.

판정은 필수 정확성·권한·완전 인계·출처·안전 검사 → 의미/시각/업무 품질 → 실패·부작용·비용 순으로 근거를 제공한다. 필수 실패는 평균으로 상쇄할 수 없다. 생성자 자기평가와 별도 독립 원자료 평가를 구별한다. 사람 개입이 필요한 경우 어떤 판단이 남았는지 보존하며, 개입 대기 중 시간 제한과 새 호출 금지를 집행한다.

튜닝 큐를 반복 사용한 결과는 개발/적응 성적이다. 이를 미관측 평가나 일반화 성적으로 다시 이름 붙이지 않는다. 자료를 본 뒤 판정 기준·큐·가중치·평가기/모델·reset 조건을 바꾸면 기존 점수와 카운터를 이어 쓰지 않고 새 비교 계보를 만든다.

## 6. 조기 종료 정책 — 제품 내부에서만 적용

### 6.1 위임 기본값과 품질 프로필

`patience=3`은 **품질 하한에 도달한 후 연속된 세 번의 유효한 완료 비교에서 의미 있는 개선이 없으면 튜닝을 종료**한다는 기본값이다. 총 세 번, 호출 세 번, 에이전트 세 개, 무효 시험 세 번, 개발 시도 세 번이 아니다.

범용 단일 점수를 모든 업무에 강제하지 않는다. 자동 반복 시작 전에 해당 업무에 맞는 `QualityProfile`을 내용 버전으로 고정한다.

| 필드 | 계약·위임 기본안 |
| --- | --- |
| `profile_id/version/hash` | 평가 항목·판정 루브릭·증거 규칙까지 고정한 식별자 |
| `primary_metric` | 방향·척도·집계·항목별 분모·동률 규칙 명시. 누락이 없는 유효 측정만 사용 |
| `mandatory_gates` | 정확성·권한·출처·완전 인계 등 해당 업무의 필수 항목은 모두 통과 필요 |
| `quality_floor` | 해당 프로필에서 충분한 품질로 취급하는 최소값과 차원별 하한 |
| `min_delta` | 관측 전 고정하는 의미 있는 개선량. 숫자 차이는 고정소수점으로 비교 |
| `regression_limits` | 보호할 차원·업무별 허용 악화. 명시되지 않은 필수 차원 악화 허용값은 0 |
| `patience` | 기본 3. 동일 계보 실행 중 변경 금지 |
| `measurement_confidence` | 유효 점수로 인정할 증거·반복·불일치 해결 조건. 자기점수는 충족 근거가 아님 |

첫 제한된 비고위험 문서/자료 업무를 위한 **보정 전 제품 기본안** `bounded_artifact_quality_v1`은 0–1 정규화된 고정 루브릭의 주 품질 `quality_floor=0.80`, `min_delta=0.02`, `patience=3`을 사용한다. 개별 필수 항목은 모두 통과하고, 보호 차원의 허용 악화는 사전 프로필에 없으면 0이다. 이 수치는 사용자의 “일정 수준/큰 개선”을 구현하기 위한 위임 기본값이지, 80점의 보편적 적정성·2점 차이의 통계적 유의성·실제 성장 효과를 검증한 결과가 아니다. 해당 업무의 의미 있는 척도·루브릭·증거 조건을 구성/보정하지 못하면 자동 정량 plateau 판정은 활성화하지 않고 그 이유를 표시한다. 수치가 없는 의미 평가를 임의 점수로 바꾸지 않는다.

비교 가능한 단일 지표가 없는 다목적 업무는 숨은 가중합을 만들지 않는다. 프로필에 명시한 우선순위·Pareto 지배/허용 악화 규칙에 따른 의미 있는 개선 판정이 있어야 하며, 상충 관계가 미결이면 `needs_judgment`다. 사용자에게 매번 철학적 선택을 묻는 것이 아니라 실제 업무 이점·손실을 보여 준다.

### 6.2 최고 후보와 진전 기준을 분리한다

- `best_observed`는 같은 계보에서 필수 검사와 회귀 제한을 통과하고 비교가 유효한 후보 중 고정 비교 규칙상 가장 좋은 후보다. 작은 개선이라도 실제 최고 후보는 보존한다. 동률이면 더 이른 후보를 유지하고 후속 비용 기준이 있다면 그 고정 규칙만 적용한다.
- `progress_reference`는 마지막으로 **의미 있는 개선**을 달성한 후보/점수다. 최초로 품질 하한에 도달한 유효 후보가 이를 설정하고 `non_improving_valid_count=0`으로 시작한다. 하한에 처음 도달한 라운드를 무개선 1회로 세지 않는다.
- 이후 현재 유효 후보가 하한·필수 검사·회귀 제한을 충족하고 `current.utility - progress_reference.utility >= min_delta`이면 의미 있는 개선이다. `progress_reference`를 현재 후보로 갱신하고 카운터를 0으로 만든다.
- 의미 있는 개선이 아니면 카운터를 1 증가시킨다. `best_observed`는 별도로 갱신할 수 있다. 이 방식은 작은 개선이 누적돼 `min_delta`에 도달하는 경우 진전으로 인정하면서, 마지막 작은 개선 후보를 잃지 않는다.
- 정상 환경에서 완결된 평가가 확정한 업무 실패·회귀 후보는 유효한 비개선 비교다. 하한 도달 이후에는 카운터에 포함할 수 있지만 최고 후보를 대체하지 못한다. 안전·권한 침해는 별도 즉시 중단을 우선한다.
- 자료 누락·격리 실패·도구/평가기 장애·판정 미결·진행 중/취소 또는 관측이 끊긴 시간 초과는 완료된 유효 비교가 아니다. 점수 `null`, 카운터 불변이다. 반면 사전 기준에 정한 정상 실행 한도 내에 요구 산출물을 못 만들었다는 사실이 완전히 관측되고 독립 평가가 정상 완료되면 유효 능력 실패·비개선으로 셀 수 있다. 실행 terminal 이유와 비교 유효성은 별도 필드이며 단순 timeout 코드만으로 결정하지 않는다. 예산은 실제 소비대로 누적하며 무효 반복을 무제한 허용하지 않는다.

`non_improving_valid_count >= 3`이면 `plateau_reached`로 튜닝 종료한다. 이는 “가장 좋은 후보를 찾았다”거나 “운영 적용 가능”이라는 판정이 아니다. 종료 사유·최고 후보·미결 사항을 보여 주고 후보 고정 및 별도 검증 경로로 이동한다.

### 6.3 다른 종료 사유

모든 자동 세션에는 유한한 호출·벽시계·반복·동시성 한도와, API라면 명시 승인된 금액 상한을 고정한다. 제품 기본 세션 한도는 상위 실행 예산 계약을 참조하며 비어 있으면 dispatch 불가다. 구독 사용량이 실제 제공되지 않으면 금액/토큰 상한을 정확히 집행했다고 표시하지 않는다. 자동 API 전환·무단 한도 증액은 금지한다.

| 사유 | 조건·후속 상태 |
| --- | --- |
| `plateau_reached` | 하한 도달 후 세 연속 유효 비교에서 큰 개선 없음. 최고 후보 보존 → 별도 검증 준비 |
| `budget_exhausted` | 하한 도달 후 시간/호출/반복 등 한도 소진. 탐색 예산 종료라고 표시하며 수렴/plateau로 주장하지 않음 |
| `below_floor_exhausted` | 하한에 한 번도 도달하지 못한 채 유한 예산 소진. 품질 미달 종료이며 성공/승격 아님 |
| `evidence_blocked` | 필수 증거·원본·평가기 신뢰 조건 부족으로 다음 유효 비교 불가. 필요한 증거 표시, 허위 0점/plateau 없음 |
| `safety_stop` | 권한·격리·부수 효과 등 안전 경계 위반. 신규 호출 차단, 격리·원인 검토. 최고 점수도 승격 근거로 사용 불가 |
| `human_stop` | 사용자가 중단 요청. 최고 후보·진행 상태 보존. 운영 적용 동의로 해석하지 않음 |
| `lineage_changed` | 큐·원자료·평가 기준·프로필·판정기·비교 환경 조건 변경. 기존 루프 종료 후 새 기준 재실행·새 계보 |

### 6.4 정확한 예시 — 모두 합성 수치이며 실제 성적 아님

프로필은 하한 0.80, `min_delta=0.02`, `patience=3`으로 고정하고 아래에서 생략한 필수 검사/회귀 제한은 통과했다고 가정한다.

| 라운드별 유효 품질 | 기대 동작 |
| --- | --- |
| 0.79 → 0.80 → 0.805 → 0.81 → 0.81 | 0.79에서는 미시작. 0.80에서 기준/카운터 0. 이후 1·2·3회 → plateau. 최고 0.81 보존, 자동 승격 없음 |
| 0.80 → 0.81 → 0.825 → 0.83 → 0.84 → 0.84 | 0.81은 카운터 1이나 최고 갱신. 0.825는 기준 0.80 대비 0.025 개선이므로 기준 갱신/0. 이후 1·2·3 → plateau, 최고 0.84 보존 |
| 0.80 → 무효(도구 장애) → 0.81 → 미결 → 0.805 → 0.81 | 무효·미결은 불산입. 세 유효 비개선만 1·2·3으로 집계. 장애 소비 예산은 계속 차감 |
| 0.71 → 0.72 → 0.72 → 유한 한도 소진 | 하한 미도달. 세 번의 실행이 있어도 plateau 아님. `below_floor_exhausted` |
| 0.80 → 0.79 → 필수 품질 결함 확정 → 0.795 | 세 번 모두 유효 완료 비교이고 안전 중단 사유가 아니라면 비개선 3회. 최고 0.80 유지; 악화 내용을 숨기지 않음 |
| 0.80 → 0.81 → 평가기/큐 변경 → 0.82 | 이전 카운터 1을 이월하지 않음. 새 계보·새 기준 수행 후 별도 판정 |
| 0.80 → 0.81 → 사용자 중단 | `human_stop`. 1회를 3회로 채우거나 완료/승격으로 처리하지 않음 |

## 7. 상태 전이·중단·재개

주 경로는 다음과 같다. 각각의 화살표는 근거가 저장된 전이이며 화면을 반드시 하나씩 넘기라는 뜻이 아니다.

`original_sealed → alternative_linked → differences_ready → diagnosis → candidate_ready → tuning → tuning_stopped → candidate_frozen → validating → awaiting_human_promotion → promoted`

- `diagnosis → inquiry → diagnosis`는 SPLI 전제가 충족된 경우만 사용한다. `unresolved`, `no_generalizable_change`, `restore_only`, `declined`도 유효한 결과다.
- `tuning ↔ awaiting_evidence_or_human`은 개별 증거·권한 대기다. 자동 반복 모드에서도 새로운 사용자 행동을 합성하지 않는다. 대기 때문에 무관한 정상 업무까지 일괄 중단하지 않는다.
- `tuning_stopped → candidate_frozen`은 보존 후보의 품질·검증 가능성이 있을 때만 가능하다. 하한 미달·증거 부족·안전 문제는 해당 사유의 종료/보류이며 자동 다음 단계 성공이 아니다.
- `validating → validation_failed`면 실패 원인을 남긴다. 고정 후보를 수정하려면 새 후보/튜닝 계보로 이동한다. 본 미관측 자료는 개발 자료로 분류하고 새 봉인 자료를 준비한다.
- `awaiting_human_promotion → rejected|deferred`를 허용한다. UI 새로고침·침묵·개발자의 자동 의사결정·조기 종료는 `approve` 사건을 만들지 못한다.

큐 항목·라운드·요청에 별도 idempotency ID를 부여한다. dispatch 전 요청·예산 예약을 원자적으로 저장한다. 결과 수용과 `LoopState.revision` 비교/갱신은 한 트랜잭션으로 수행한다. 중복·늦은 결과는 원 요청에 붙이는 제한된 감사 기록일 뿐 종료 상태·최고 후보·카운터를 뒤집지 못한다.

재시작은 마지막 저장 상태를 복원한다. 살아 있는 실행에는 재접속만 하고 재전송하지 않는다. 소유 worker/제공자 상태가 불명확하면 `recovery_pending`으로 두고, 종료·외부 부수 효과가 확인된 후 권한 있는 재개 경로에서 새 요청 ID를 만든다. 재개는 새 세션 예산을 자동 지급하지 않는다. 큐·프로필·평가기·렌즈/변경 생성 규칙의 호환성을 재확인하고 비교 조건이 달라졌으면 새 계보로 분기한다.

취소는 저장된 중단 게이트 → 신규 dispatch 금지 → 소유 실행 중단 요청 → 종료 확인 순서다. 로컬 적용 차단, 프로세스 종료 관측, 원격 제공자 사용량 종료 확인을 별도 필드로 기록한다. 하나로 나머지까지 보장했다고 표시하지 않는다.

## 8. 봉인 검증·승격·롤백

튜닝 종료 이후 `candidate_frozen`에는 환경 그래프, 역할별 모델/추론, 프롬프트, 지식/기억 선택 규칙, 원형 입출력·인계, 도구/권한, 렌즈 버전, 적용 범위, 평가/승인 정책 참조를 한 번들 해시로 고정한다. 변경한 요소뿐 아니라 실제 실행에 필요한 의존 버전과 롤백 묶음을 포함한다.

별도 미관측/전향 검증은 단순한 문구 유사도가 아니라 조건부 판단과 실제 원형 산출물·전달·업무 효과를 확인한다. 최소한 원 사례 재구성, 범위 내 새 사례 전이, 적용 제외/반례, 다른 역할·기존 지식 회귀, 출처/대안 누출, 부수 효과/권한을 구분해서 보고한다. 후보 생성자·튜닝 에이전트는 봉인 정답/판정기 내부자료에 접근할 수 없다. 판정기 장애는 무효이며 실패를 소거하지 않는다.

관찰 전용은 실제 운영 결과에 영향을 주지 않는 별도 실행이다. 제한 적용이 필요하면 사용자가 정확한 후보·대상·시간·부수 효과 범위를 승인한 한시적 적용으로 구별한다. 최종 운영 승격은 어느 경우에도 자동이 아니다. 후보 자동 반복 권한이나 그래프 최초 선택으로 대체하지 않는다.

승격 전 화면에는 원/후보 환경, 최고 후보 선정 이유, 이전 큐 결과, 미관측·경계·회귀 결과, 실패/미결·영향 범위, 모델/도구·예산 변화, 롤백 대상을 보여 준다. 사람의 승인 후 현재 운영 버전을 조건부 갱신하여 승인 대상과 실제 적용이 같은지 확인한다. 승인 이후 파일·프롬프트·모델·지식이 바뀌면 그 승인을 재사용하지 않는다.

롤백은 지식만이 아니라 환경·프롬프트 파생물·권한·워크플로 구성의 호환 번들을 되돌린다. 이미 수행한 외부 발송·게시 등의 현실 효과를 자동 취소했다고 주장하지 않는다. 롤백 이후 원/새 수행은 버전을 유지한다. 정책·제공자 모델·자료 조건·새 충돌이 바뀌면 영향받는 범위의 재검증을 요구하며 과거 자격을 영구 보증으로 취급하지 않는다.

| G-06 | 관련 이전 큐의 기준/후보 수행 | 같은 manifest·평가 조건·실제 파일/수신 접근·다른 역할/비용을 짝 비교 |
| G-07 | §6.4의 plateau·누적 개선·하한 미달 예시 | 정의한 카운터/최고 후보/종료 사유와 정확히 일치 |
| G-08 | 장애·누락·미결·중복·취소·늦은 응답 | 점수/카운터 오염 없음. 실제 소비와 감사 결손을 별도 보존 |

| G-11 | 조기 종료 직후 운영 적용 요청 | 별도 검증 및 사람의 정확한 버전 승인이 없으면 거부 |
| G-12 | 미관측 결과를 보고 후보 수정 | 해당 자료를 튜닝/개발로 재분류, 새로운 봉인 자료 없이는 미관측 합격 주장 없음 |

| G-14 | 과거 발송/게시 포함 업무 큐 | 승인된 격리/재생 경계만 사용. 실제 서비스에 부수 효과 중복 실행 없음 |

| G-17 | 개발 작업 세 번에서 개선이 작음 | 이 계약의 plateau를 개발 완료/중단 근거로 적용하지 않음 |

완료 증거는 계약/상태 단위 검사, 실제 도구·형식/접근 통합 시험, 실제 사용자 대안이 있는 성장 실행, 별도 검증 성적을 구분한다. 합성 예시·개발자의 비평·729개 기존 회귀 통과를 사용자 대안이나 실제 성장/철학 렌즈 효과의 증거로 재사용하지 않는다. 본 문서는 설계 산출물이며 위 수용 사례의 실행·효과 확인은 아직 수행하지 않았다.
