# T070 — consistent age-encrypted backup and staged restore (2026-09-23, Linux x86_64)

Status: **code and tests landed; the checkbox stays open** (see "Not yet met").

## What landed

- `app/workers/backup_crypto.py` is the only code that calls age. `AgeRuntime.open` checks the exact
  locked member digests from `deploy/manifests/age-1.3.2.json` for `age` and `age-keygen` on both
  x86_64 and aarch64, and requires both to report `v1.3.2`.
  - Only native X25519 recipients and identities are accepted. Everything else is refused before
    any spawn: SSH keys, plugin/PQ/tag values, uppercase or short keys, flag-shaped values and
    comment lines.
  - The argv is fixed. The environment is empty, so there is no PATH and no plugin lookup.
  - The identity reaches age only through an owned pipe at `/proc/self/fd/N`: never in argv, a file
    or the environment. stderr is discarded, and errors never include secret material.
- `app/operations/backup.py` makes a backup in these steps:
  1. States run `backup_pending → snapshotting → encrypting → verify_restore → ready`, or end in
     `failed` with a reason.
  2. The snapshot uses SQLite's online backup API.
  3. Table classification is closed: every table is either included history or excluded under a
     named category. A table the module does not know refuses the whole backup.
  4. The excluded tables are dropped from the snapshot, then `integrity_check` and
     `foreign_key_check` must pass.
  5. The internal `BackupManifest` carries exactly the §5.2 fields and is written into a
     deterministic tar together with the database.
  6. The tar is encrypted with age, then decrypted in full again as a restore proof. Every record
     is read back through `DomainStore`. Only after that is the backup `ready`.
  7. The external `BackupReceipt` holds the ciphertext sha/size and `restore_verification_ref`.
     The manifest never contains its own hash.
- Key modes:
  - `instance_backup_key` uses the recipient from the `backup-key-init` volume. Its receipt says
    `recoverable_after_host_or_volume_loss=false`.
  - `portable_recovery` uses the user's recipient plus a `OneShotIdentity`, which is masked, used
    once and wiped. Its receipt says the backup survives host or volume loss.
- Restore works like this:
  - The target must be an empty staging directory. A restore into the active vault is refused.
  - The ciphertext must match the external receipt before anything is decrypted.
  - It checks full age authentication, the exact archive members and bounds, the manifest hashes,
    the schema version, that no excluded category is present, the vault identity, and the lineage
    of every record.
  - On success it writes a `restored_review.json` marker: dispatch is blocked until a new owner
    bootstraps, connections and service clients are re-created, and an exact environment is
    activated. On failure the staging directory is left empty.
- `age_keygen(runtime)` connects the real `age-keygen` to `backup-key-init`.

## Not yet met (why the checkbox stays open)

- The code does not yet run as its own **networkless backup-crypto service**. The contract splits
  the work: the control plane streams a typed archive, and only the worker mounts `backup-key`
  read-only. Today `create_backup` runs both halves in one process. The container, mount and
  network-none service definition belongs to the T081 scaffold and has no image here.
- No GUI yet, so there is no included-content preview or consent screen (T073), and no
  backup-before-migration gate (T072).
- Tests need the binary from outside the repo (`DEEPTWIN_AGE_RUNTIME_ROOT`). CI has no binary
  provisioning, so they skip there.

## Originals carried in the backup (same day)

**Defect found and fixed.** The backup archive carried only the SQLite database. The original
bytes the records name live beside it in the content-addressed store (`domain-cas/<purpose>/<sha256>`),
and they were never archived. The restore check reads every record through
`DomainStore.get`, which verifies referenced blobs, so a vault holding any original could not
produce a `ready` backup at all. The earlier tests passed only because their vaults had no
blobs.

- Every blob registered in the snapshot's `domain_blobs` is read from the source vault. The
  read uses no-follow, regular-file only, and an exact size and SHA-256 check. A missing or
  altered original refuses the whole backup and states why. Each original becomes its own
  archive member, `vault/domain-cas/<purpose>/<sha256>`, and gets its own `item_refs` entry.
- On unarchive, members are admitted only when they are the manifest, the database, or a
  content-addressed original (a strict name pattern). A running total bounds the whole
  archive. Each original's bytes must hash to its address. The restored `domain_blobs` rows
  must equal the set of originals exactly: nothing missing and nothing extra.
- Restore and the create-time restore proof write the originals as 0600 files in 0700
  directories, fsynced, before the lineage check. The verification scope gained
  `original_bytes`.
- Observed: `test_backup.py` **14 passed** with `DEEPTWIN_AGE_RUNTIME_ROOT` set. The new cases:
  - an original round-trips byte for byte, is never in the clear in the ciphertext, and the
    record naming it reads back after restore
  - an altered original refuses the backup, and so does a missing one; nothing is written

The operator guide (§4.3/§4.4) now says so.

## 2026-09-25 — the networkless backup-crypto worker as its own process; backup/restore GUI

**What changed.** `create_backup`/`restore_backup` no longer need the key in the calling process.
They take a crypto port. In production the port is the control plane's `BackupCryptoClient`
(`app/workers/backup_crypto_client.py`), which never receives a key handle or key path. The age
half runs in a separate entrypoint, `python -m app.workers.backup_crypto_main`, on the `cp-backup`
pair that deploy/security/service-ids.json already declared: requester `control` 20102, responder
`backup` 20111, pair group 21109, fixed profile `app/workers/backup_channel.py`. The pattern is
the credential gateway's: a verified UDS, SO_PEERCRED, the HMAC readiness record and the
handshake under the attachment's requester boot label.

- **Typed stream** (`app/workers/backup_stream.py`). One operation per connection:
  `backup_request {op: describe|encrypt|decrypt, key_mode, size, sha256, …}`, then chunks of at
  most 32 KiB, then an end frame that binds the size and SHA-256. The answer has the same shape.
  A body is accepted only whole. If a stream is cut, reordered, has an extra frame, or has one
  altered byte, `stream_invalid` is returned and nothing partial comes back. An instance-mode
  request never names a key. A portable decrypt carries the one-shot identity once.
- **Networkless worker.** Before opening anything, the entrypoint installs an audit hook
  (`forbid_network`). The hook refuses:
  - any socket that is not AF_UNIX: creation, bind, connect and sendto
  - every name lookup
  - every spawn except the two locked age binaries

  The real-socket tests also start the worker under `unshare --net`: an empty namespace with
  only an unconfigured `lo`.
- **Key root.** Only the worker reads it. The root must contain exactly `identity.age` and
  `manifest.json`, and it must be read-only: either a read-only mount or a directory whose mode
  grants no write. Anything else refuses the start with exit 2, including a credential-root-like
  directory or a writable one. An absent volume means the worker starts and answers
  `key_unavailable`. The worker imports no credential, vault, route, storage or domain code, and
  an AST test checks that. The client imports no key or age code.
- **Consent binding.** `create_backup(expected_preview_sha=…)` recomputes the preview from its
  own snapshot. If the vault changed, it refuses before anything is encrypted, so the
  `states` are `backup_pending, snapshotting, failed`. `backup_preview` stores nothing. It gives
  the included categories with row counts, the originals by count and bytes, and every
  excluded category with a closed reason.
- **Routes.** The `backups-v1` contribution (`app/api/backups.py`, `app/services/backups.py`)
  has 8 routes: state, preview, create, ciphertext and receipt download, restore begin
  (receipt), bundle upload (octet-stream, at most 64 MiB), and restore read. Backups and their
  consent sidecar (`{id}.consent.json`) live in the control state directory under `backups/`.
  Restores are staged under `restores/{id}/staged`, never over the active vault. The server
  gains `--backup-worker-config`. When it is absent, the state says `not_configured` and
  create/restore answer 503 `backup_worker_unavailable`. Pinned route counts went from 83 to 91.
- **GUI.** `app/static/records-backup.mjs` on the records page does the following:
  - shows the worker state (ready, key lost, unreachable or not configured)
  - shows the actual preview, then an explicit consent bound to its digest
  - reports a stale preview as stale
  - downloads the encrypted bundle and the external receipt
  - restores by uploading the receipt and the bundle, then shows the staged `restored_review`
    with each of the new-owner bootstrap, the re-created connections and service clients, and
    the explicit environment reactivation marked as required, dispatch blocked, and the active
    instance unchanged

### Still open (why T070 stays unticked)

- The Compose `backup` service still has no image or command. It does not yet mount the
  `backup-key` volume read-only or the two configuration files, and `control` does not yet get
  `--backup-worker-config` (T081 scaffold). The deployment hashes pin `deploy/compose.yaml`, so
  this change was not made here. The process, channel and tests exist; the deployed service does
  not.
- The browser path handles `instance_backup_key` only. Portable-recovery create/restore, with
  one-shot masked identity input, exists at the service/worker level but has no UI yet.
- Opening a staged `restored_review` vault as the new active instance is shown as required steps
  only. No route switches the active vault. The backup-before-migration gate (T072) is not
  implemented.
- The real-worker tests need Linux, root and `DEEPTWIN_AGE_RUNTIME_ROOT`. Elsewhere they skip and
  state why. CI has no age provisioning.
