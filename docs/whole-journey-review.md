# DeepTwin 전체 사용자 여정 검토 초안

작성일: 2026-09-06

상태: Superpowers brainstorming의 의도·성공 기준 확인용 경험 시나리오. 승인된 상세 설계, 구현 계획, 작동하는 제품이 아니다.

사용자가 철학 렌즈 누락을 지적한 뒤 전체 순환을 하나의 실제 경험으로 먼저 제시하는 데 동의했다. 이어 이전 업무 큐를 반복 재실행·평가한 뒤 사람이 최종 승인하면 해당 업무의 환경을 버전업하고, 제작자 피드백 전달은 선택적 행위로 분리하도록 직접 수정했다. 앞선 개별 긍정 응답을 전체 엔진이나 아래 UX 세부 사항의 승인으로 확대하지 않는다.

## 기본 해상도와 부분 반복 — 단계 번호를 전체 검토의 일괄 관문으로 쓰지 않는다

**핵심 입력 교정(INT-033):** 이 여정의 피드백은 사용자가 ‘무엇이 왜 잘못됐으니 어떻게 고쳐 달라’고 코멘트하는 것이 아니라, 해당 업무 상태에서 자신이 수행한 대안 산출물 전체/부분을 비교 대상으로 남기는 것이다. 차이의 발견·원인/판단 가설·렌즈 탐구는 그 뒤 DeepTwin의 책임이다. 자기설명은 선택적 보조 증거이며, 이유나 수정 지시가 없어도 이 흐름이 시작돼야 한다. 직전 C의 검토문에 문제 원인을 설명하며 개선을 요구하는 예시는 철회한다. C가 검토 의견 자체를 업무 산출물로 만드는 것과 사용자가 C를 고치라고 지시하는 것은 구별한다.

**최신 교정(INT-032):** 협업은 각 역할이 완성한 산출물을 다른 에이전트가 입력으로 사용해 다음 산출물을 만드는 관계다. 에이전트에게는 최종 산출물이지만 전체 업무 흐름에서는 중간 산출물일 수 있다. 산출물 전체·단락·문구·산출물 간 관계에 피드백할 수 있으며, 아래 ‘작은 차이’는 피드백의 초점을 뜻할 뿐 전달되는 산출물이나 필요한 맥락을 문구 수준으로 축소하라는 뜻이 아니다. 기록·화면·진단의 중심에 산출물 내용·역할·버전·입력과의 관계를 둔다. 모든 산출물을 항상 프롬프트 하나에 통째로 넣거나 모든 업무를 문서 파일로 강제한다는 뜻은 아니다.

**사용자 직접 교정(INT-030–031):** 에이전트 간 전달 한 건, 전달 내용의 한 필드, 중간 산출물의 문구, 특정 실행 지점에 피드백하고 필요한 미세렌즈 탐구·정제·흡수로 이어갈 수 있어야 한다. 일부만 피드백하고 다시 실행해 관찰한 뒤 추가 피드백하는 사용을 기본 경로로 삼는다. 최종 산출물이나 큰 정책 변경도 대상이지만 기본 피드백을 그 크기에 맞추지 않는다.

아래 3–7단계는 모든 산출물·전달·판단의 검토를 끝낸 뒤 통과하는 직렬 관문이 아니다. 선택한 작은 차이에서 진입하고, 현재까지 시험 가능한 변경으로 돌아보고, 결과의 새 위치에 피드백하며 반복하는 기능 흐름이다. 8단계의 업무 환경 버전은 검증된 변경을 담는 단위이지 매 피드백의 검토 크기가 아니다.

**기록과 사용 절차의 구별:** 사용자의 실제 대안과 원 실행·입력 산출물·원본/대안 버전·검토 범위를 연결한다. 상세 편집·업로드·저장·탐구 시작 방식은 미정이며 이유 입력을 필수로 두지 않는다. ‘일단 이 정도로 다시 보기’는 부분적인 대안과 변화 관찰을 오가며 다음 판단을 발견하는 사용 방식의 설명이지 별도 명령·버튼·제출 관문을 요청한 말이 아니다. 원본/대안 및 실험 후보의 식별은 필요하지만 사용자에게 각 내부 상태 전환을 별도 선언·승인하도록 요구하는 것과는 구별한다. 대안만으로 차이 탐구를 시작할 수 있고 미검토·보류·미확정 항목을 보존한다. 시험에 불필요한 추가 질문이나 전체 대안 완성을 요구하지 않는다. 실제 실행 계기·예산·권한 정책은 후속 설계하며 침묵이나 추정한 마음속 의도를 실행 권한으로 간주하지 않는다.

부분 대안의 범위는 비교 증거가 존재하는 범위이지 변경·영향·검증 범위의 상한이 아니다. 그 차이에서 탐구한 작동 방식이 바뀌면 같은 에이전트의 다른 문단과 산출물, 이를 활용하는 다른 역할, 관련 업무의 결과까지 달라질 수 있다. 미검토 부분은 승인된 영역도 변경 금지 영역도 아니다. 부분 증거만으로 전역 일반화를 확정하지 않되, 변경 가설과 실제 의존 관계를 따라 대안이 없는 영역까지 영향을 확인한다. 국소 시험은 관련 이전 업무 큐 반복 평가와 필요한 최종 검증을 대체하지 않는다. 원 운영 기준과 회차별 후보를 보존하고, 대안 범위 밖 변화의 개선·악화·불확실성도 구별한다.

현재 산출물의 수정, 이번 후보의 시험, 이후 지속 반영의 사람 최종 승인을 구별한다. 렌즈 탐구도 보류·재개할 수 있다. 아직 확인되지 않은 해석은 잠정 상태로 남기며 모든 철학 질문의 완결을 후보 시험의 전제 조건으로 강제하지 않는다. 선택 변경의 검증·영향 범위 안에서 필요한 조건을 충족해야 운영 승격할 수 있고, 무관한 나머지 개선 과제를 모두 끝내야 한다는 뜻은 아니다. 상세 UI·변경 묶음·시험 한도·의존성 처리는 후속 설계한다.

논문 연결: 4.4–4.7절(18–22쪽)의 부분 수정·검토 범위·전달 사건·차이 기준 추적, 4.8절(23–28쪽)의 조건부 탐구·중단, 4.9절(29쪽)의 국소 상태와 후속 효과, 5.4–5.5절(36–37쪽)의 범위별 검증·운영 반영. 부분 피드백 후 다시 보는 UX의 명시는 INT-031이다.

## 전체 여정의 화면 모드 — 세 모드 제공·공통 환경 관계 확인

**사용자 직접 결정(INT-024):** 업무 작업공간·대화·그래프 캔버스의 세 모드를 모두 제공한다. 이는 업무별 환경 설계안 기본 3개와 별개의 선택이다.

확인된 설계 관계: 같은 업무 환경과 선택 업무 건의 설계·실행·산출물·사용자 대안·탐구·실험·평가·승인 상태를 세 모드가 공유한다. 사용자는 ‘같은 환경·산출물·성장 이력을 서로 다른 방식으로 다루는 관계’라는 설명에 “응”이라고 답했다. 아래 전체 여정을 하나의 모드에만 고정하거나 각 모드를 별도 제품·별도 업무 복제본으로 나누지 않는다.

논문 4.3절(17쪽)의 역할별 입력·출력 계약과 4.4절(18–19쪽)의 실행·산출물 계보, 진단·실험 연결은 공통 참조의 근거다. 4.5절(19–20쪽)의 원 수행과 대안 수행·검토 범위 구별도 어느 화면에서든 유지해야 한다. 다만 세 모드 자체와 공통 상태를 공유하는 화면 구성은 논문의 직접 명시가 아니라 INT-024를 구현하기 위한 제품 설계 제안이다.

- 작업공간은 원 자료, 역할별 실제 산출물, 사용자 자신의 전체/부분 대안과 실행·비교 결과를 중심으로 다룬다.
- 대화는 같은 업무와 산출물을 참조하며 업무 설명·질문·탐구를 이어 간다. 대화에서 남긴 자기 버전도 원 수행과 연결된 대안 산출물로 보존한다. 핵심 입력을 수정 지시·자기설명으로 바꾸거나 대안을 채팅 로그 안에만 가두지 않는다.
- 그래프는 실제 역할과 산출물의 입력·출력·전달·파생 관계, 실행 진행과 실패를 중심으로 탐색한다. 설계상 연결과 실제 전달·관찰된 계보·개입으로 확인된 영향을 구별하며 선 하나를 인과 증명으로 표시하지 않는다. 원본과 사용자 대안, 실험의 관계를 볼 수 있다는 뜻이지 사용자 대안을 운영 에이전트의 입력으로 자동 전달한다는 뜻이 아니다.

예를 들어 한 초안의 특정 단락에 자기 버전을 남긴 뒤 다른 모드로 이동해도 같은 원본·대안·범위·버전을 참조하고, 앞서 입력으로 쓰인 보고서와 후속 크리틱 산출물을 연결해 살펴볼 수 있게 한다. 부분 대안의 영향은 작성 범위 밖으로 퍼질 수 있고, 그 영향은 시험과 증거로 확인한다. 모드별로 다른 대안이나 서로 다른 학습 이력이 생기는 구조가 아니다.

모드 전환 자체는 보기/작업 맥락의 변경이며 새 실행·승인·운영 환경 버전 생성이 아니다. 실제 변경에는 동일한 권한·검증·승인 규칙을 적용하고, 출발 모드와 관련 업무·버전·행위를 기록해 후속 진단에서 연결할 수 있게 하는 방향으로 설계한다. 전환만으로 편집 중인 내용을 잃거나 외부 행동을 재실행하지 않는다. 공통 참조는 하나의 물리 저장소나 모든 에이전트의 모든 자료 접근을 뜻하지 않는다. 원 실행 기록 봉인과 대안·렌즈 정보의 진단 전용 경계는 유지한다.

확인된 범위는 세 모드가 한 환경의 같은 업무·산출물·성장 이력을 다루는 관계다. 기본 진입 모드, 전환 조작·자동 전환, 동시 다중뷰, 모든 기능의 모드별 동등 제공, 직접 그래프 편집 범위, 편집 중인 내용의 저장·동시 수정 처리 방식은 미결이다. 비개발자에게 코드·노드 편집을 필수로 요구하지 않으며 기존 목업의 상세 배치를 그대로 승인한 것으로 보지 않는다.

## 전체 여정의 모델 실행 연결 — 두 구독 경로 필수, API는 선택

**사용자 직접 결정(INT-025–026):** Claude·Codex 각각의 본인 구독으로 실제 실행하는 경로를 필수 제공하고, API 실행은 사용자가 원할 때 명시적으로 선택·전환한다. 두 구독을 동시에 보유해야 시작할 수 있는 제품으로 만들지 않는다.

**대상 명확화:** 아래는 오픈소스 배포물을 설치해 쓰는 최종 사용자의 경험이다. 제작자가 프레임워크를 코딩할 때 사용할 도구·계정·과금 방식과는 별개의 계약이다. 새 설치 사용자도 UI와 자신의 구독으로 핵심 여정을 수행해야 하며 제작자 컴퓨터의 로그인 성공만으로 충족했다고 하지 않는다.

경험 설계 방향: 사용자는 UI에서 보유한 제공자의 공식 인증 흐름으로 연결하고 사용 가능한 모델을 선택한다. 구독으로 초기 업무 이해·후보 생성·크리틱·환경 실행·피드백 정제·반복 평가까지 주요 LLM 경로를 이용할 수 있어야 한다. API 키 입력이나 사용자 CLI 조작을 필수로 요구하지 않는다. 연결·모델 선택을 업무 시작 전 또는 첫 실행 시 어느 화면에 배치할지는 후속 설계한다.

구독 한도·연결 오류 시 보류/중단 상태를 알리고 기록·승인 맥락을 유지한다. API 키가 이미 있어도 자동으로 유료 전환하지 않는다. API 전환은 사용자가 대상·모델·과금 경로·적용 범위를 확인한 뒤 이루어지며, 실행 중 전환 처리와 재개 정책은 후속 설계한다. 연결 방식을 바꾼다는 이유로 기존 환경/업무 승인이나 평가 근거가 자동으로 다른 후보에도 유효해지는 것은 아니다.

제공자·실행기 버전·실제 모델·구독/API 경로·전환 선택을 실행/평가/환경 버전과 연결한다. 비밀 토큰·API 키는 기록/내보내기에서 제외한다. 선택 모드와 실제 호출 경로가 일치해야 하며 한쪽 구독만 작동하거나 크리틱·평가가 숨은 API 전용이면 전체 지원 완료가 아니다. 공식 연결·인증 조건을 준수하고 상세 기술 적합성은 양쪽 각각 검증한다.

## 1. 업무를 맡기고 시스템의 이해를 확인한다

사용자는 제안서 검토 업무를 설명하거나 기존 제안서·승인 정책·과거 사례를 올린다. 둘 중 하나만으로도 시작한다. 프레임워크는 자료를 실제로 반영한 목적·완료 조건·권한·위험·불확실성의 짧은 업무 모델을 보여 준다.

제품 경험 제안: 사용자는 출처를 열어 보고 자연어로 오해를 고친다. 같은 오해를 공유한 설계안 세 개를 먼저 제시하지 않는다. 추가 자료나 답이 없으면 이를 숨은 가정으로 채우지 않는다.

논문 근거: 4.2절, 16쪽.

## 2. 실제 운영 설계를 선택하고 환경을 구성한다

다중 에이전트가 타당한 업무라면 역할·권한·병렬성·기억·평가·사람 개입 위치 등이 다른 설계안을 비교한다. 사용자는 하나를 고르거나 책임 구조와 승인 게이트를 병합한다. 각 결정의 이유와 수용하지 않은 위험을 남긴다.

**사용자 확인된 확장(INT-021–023):** 이 설계안을 만드는 내부 절차에서도 출처 기반 미세렌즈 단독·하이브리드 생성 규칙을 활용한다.

1. 확인된 업무 모델·필수 제약을 공유하고, 업무에 적합한 관점과 조합으로 복수의 실행 구조 후보를 만든다. 렌즈 목록·후보 수·발동/라우팅·예산은 후속 설계한다.
2. 별도 크리틱이 공통 업무 기준으로 후보를 개별·병렬 평가한다. 렌즈 이름·조합·생성자의 자기평가와 다른 크리틱 결과를 가려 평가하며, 병렬 호출만으로 판단 독립성이 보장됐다고 주장하지 않는다.
3. 필수 제약을 통과한 후보 중 품질과 최소 두 축의 구조적 다양성을 고려해 기본 3개를 제시한다. 후보 부족을 숨기거나 같은 안의 변형으로 개수를 채우지 않는다.
4. 일반 설계 비교 UI에는 ‘철학’, ‘렌즈’, 철학자 이름을 노출하지 않는다. 누가 무엇을 하며 어떤 자료·도구를 쓰고 어디서 검토·승인하는지, 장단점·비용·위험을 업무 언어로 설명한다. 사용자는 선택·수정·병합할 수 있다.
5. 탈락·실패를 포함한 모든 후보, 렌즈 정의/출처/버전·조합·생성 설정, 평가기/기준/점수/근거, 선정·제시 순서와 사용자 수정 이력을 기록한다. 이후 실제 실행·평가·환경 버전과 연결해 생성 과정과 결과를 함께 감사할 수 있게 한다. 권한·민감정보·내보내기 정책은 별도 설계한다.

렌즈가 없는 생성 방식과 같은 비용 조건의 비교도 검증 계획에 포함한다. 초기 크리틱 점수는 예상 품질이며 실제 개선도나 운영 승격 근거를 대신하지 않는다. 합격 후보가 부족할 때의 재탐색 정책과 숫자 기준은 아직 미정이다.

**최신 사용자 요구(INT-027):** 동일 모델의 한계를 고지하는 것만으로 끝내지 않고 판단 오류의 독립성을 보장할 수 있는 크리틱 설계를 요구했다. 위 병렬·블라인드 절차만으로 충족됐다고 보지 않는다. 논문 6.4절(40쪽)의 결정적 검사·형식 비교·근거 기반 의미 평가·블라인드 전문가 판단과 통제 실험을 기준으로 검증 구조를 보완한다. 보장 범위·수용 시험은 현재 검토 중이며 다른 모델 연결이나 사람 승인만으로 오류 독립성이 증명됐다고 하지 않는다. 상세 논점은 [제품 의도 기준표](product-intent.md)의 INT-027에 기록한다.

**후속 확인(INT-028):** 검증 근거가 부족한 항목은 크리틱 점수가 높아도 자동 통과시키지 않는다. 평균 점수·다수결로 필수 검사 실패나 미확정 근거를 상쇄하지 않는다. 보완·재검증·권한자 확인을 사용자 경험에 연결하는 구체 방식은 후속 설계하며, 비교 준비 상태를 운영 검증·실행 승인·업무 환경 버전 승격과 혼동하지 않는다.

**렌즈의 검토·보완 연결(INT-029 확인):** 초기 생성 이후에도 출처 기반 미세렌즈가 숨은 전제·책임·예외에 대한 반례·검증 질문·시험 상황을 만든다. 별도 평가기는 렌즈의 이름이나 권위가 아니라 업무 기준·근거·시험 결과로 판정한다. 사실·구조 결함의 보완과 판단 근거의 충돌을 구분하고, 후자에 확인된 판단 차이와 전문가 판단 가설이 있으면 아래 5단계의 SPLI로 연결한다. 새 업무 증거로 갱신된 판단 가설을 통해 후보를 보완하고 재검증한다. 렌즈의 생성 결과 자체를 정답으로 쓰거나 렌즈 다양성만으로 독립성을 증명하지 않는다. 발동·미발동과 질문·응답·후보 리비전·평가의 연결도 기록한다. 보완 예산과 사용자 질문·기준 변경 승인 등의 구체 정책은 후속 검토한다.

이 경로는 5단계의 사용자 판단 탐구(SPLI)와 목적·증거 경계가 다르다. 출처 기반 렌즈 정의를 초기 설계 탐색에 사용하는 것은 허용하되, 에피소드 철학 해석(H_phi/S_phi)을 운영 규칙·개입에 직접 주입하지 않는다. 철학자 역할극이나 해결되지 않은 규범 충돌의 점수 평균으로 설계를 정하지 않는다.

제품 경험 제안: 사용자는 ‘가격과 납기는 사람이 확인한 뒤 진행’처럼 운영 조건을 조정한다. 프레임워크가 승인한 내용을 실행 가능한 환경으로 변환한다. 필요한 외부 도구 연결·인증은 UI로 안내하고, 미연결 기능을 실행 가능하다고 표시하지 않는다. 설계 승인을 외부 발송·결제 등에 대한 무제한 권한으로 해석하지 않는다.

논문 근거: 4.3–4.4절(17–18쪽)의 구조 대안·실행 구성, 4.8.5절(27–28쪽)의 설계 검토 출처 활용과 승격 경계. 구성 책임과 비개발자 UI는 INT-002·010·015. 렌즈별 생성·크리틱 선별·전체 탐색 로그는 INT-021–023의 사용자 확인된 확장이며 논문에 이미 있는 알고리즘으로 표기하지 않는다.

## 3. 산출물 흐름을 보고 같은 업무 상태에서 자신의 대안 산출물을 남긴다

사용자는 같은 업무 맥락에서 분석·견적·검토의 진행, 전달 자료, 산출물, 승인 대기와 실패를 확인한다. 노드 상태는 실제 실행 사건과 연결한다. 실패하면 해당 사건·근거로 이동하고 재개 가능한 범위를 안내한다.

가상 업무의 산출물 관계:

- A 조사 담당은 자료·출처·쟁점·제약을 정리한 조사보고서를 만든다.
- B 작성 담당은 그 보고서와 업무 요구를 사용해 문제·해결 방안·기대 효과·일정이 있는 제안서 초안 전체를 만든다.
- C 크리틱은 초안과 필요한 조사 근거를 검토하고, 대상 절·판단 근거·문제·수정 방향을 정리한 크리틱 검토문을 만든다.
- B는 기존 초안과 크리틱 검토문을 입력으로 수정 초안 전체를 만든다. 각 산출물과 사용한 입력 버전의 관계를 남긴다.

이 관계는 설명용이며 병렬 검토·여러 산출물의 결합·반복 수정 등 다른 실행 구조도 가능하다. ‘전달’은 산출물 파일의 전송 성공뿐 아니라, 다음 역할이 그 내용을 업무 목적에 맞게 활용해 자기 산출물에 반영하는 관계다.

가상 대안 수행: 사용자는 C가 맡은 검토를 자신이 수행해 ‘내 검토문’을 남긴다. C가 만든 검토문을 어떻게 고치라는 요청서가 아니라, 같은 초안과 관련 조사보고서를 놓고 사용자가 실제로 작성한 또 하나의 검토 산출물이다. 2장에 대한 검토 부분만 작성했다면 그 범위의 사용자 대안과 C의 원 검토문을 비교한다. B의 작성 수행을 비교하려면 B의 초안과 사용자의 초안을 대응시키며, 사용자 검토문을 B의 초안과 같은 유형의 정답으로 비교하지 않는다.

사용자는 자기 버전만 제출할 수 있다. 문제 이름·차이의 원인·수정 방법·철학적 이유를 설명할 필요가 없다. 대안 산출물 원문, 대상 역할·업무·입력/출처 버전, 원 결과를 본 편집인지 독립 수행인지, 실제 대안/검토 범위를 연결한다. 추가 자료 등 조건 차이가 있으면 가능한 범위에서 기록한다. 원 에이전트 산출물을 덮어쓰거나 완전한 동일 조건·독립 비교라고 가정하지 않는다. 나머지 부분은 미검토로 보존하며 이 부분 대안만으로 다음 탐구를 시작할 수 있다. 상세 UI는 제안이다.

논문 근거: 4.4–4.6절, 18–21쪽. 연속 관제·재개 UX는 기존 실패 사례를 반영한 제품 제안이다.

### 3.1 부분 대안과 전체 영향 — 직전 제출 절차 제안 철회

사용자는 직전 ‘작성 → 명시적 비교 제출 → 탐구 시작’ 제안에 동의하지 않았다. ‘이 정도로 다시 보자’는 자연스러운 생각을 인터페이스의 요구 조건으로 문자 그대로 변환하지 말라고 지적했다. 따라서 특정 버튼뿐 아니라 명시 제출을 핵심 관문으로 삼은 제안과 제출 여부를 사용자 판단의 완결로 본 설명을 철회한다. 원본 복사 편집·새 작성·외부 파일 가져오기 등 상세 입력 방식도 이번 발언으로 승인됐다고 보지 않는다.

유지할 것은 대안 산출물과 원 수행·입력 상태·범위·버전의 연결, 이유 설명 없는 탐구, 부분 대안 상태에서의 반복 사용이다. 원 결과를 본 수정과 결과를 보기 전의 독립 수행은 계속 구별한다. 원본을 보존하고 비교에 사용한 버전을 식별하는 내부 필요를 사용자의 별도 제출 의식으로 옮기지 않는다. 수집·저장·탐구/실행의 실제 계기와 조작은 아직 미정이며 자동 실행·무검증 운영 반영으로 반대로 단정하지 않는다.

부분 대안 → 차이와 복수 가설 → 렌즈를 통한 구별 조건·새 수행 증거 → 작동 방식 변경 후보라는 관계를 유지한다. 그 변경은 대안을 작성한 부분 밖의 산출물과 다른 에이전트의 수행에도 영향을 줄 수 있다. 사용자는 그러한 변화된 전체 수행을 보면서 다음 대안·판단을 발견할 수 있으며 전체 피드백을 미리 완성할 필요가 없다. 영향과 검증 범위는 대안의 크기가 아니라 변경 가설·의존 관계·관련 이전 업무 큐를 기준으로 정한다. 모든 부분을 무조건 바꿔도 된다는 뜻은 아니다.

논문 연결: 4.5절(20쪽)의 부분 검토는 비교 증거의 범위를 설명한다. 4.7절(22쪽)과 4.9절(29쪽)은 개입 후 국소 상태와 하류 결과를 함께 확인한다. 이 근거를 특정 UI 버튼·제출 단계의 근거로 확대하지 않는다. 새로운 상세 UI 제안은 현재 내지 않는다.

## 4. 시스템 문제와 아직 표현되지 않은 판단 기준을 함께 찾는다

프레임워크는 먼저 C의 검토문과 사용자의 검토문에서 실제로 다른 대목을 정렬한다. 다룬 쟁점·채택한 근거·우선순위·판단·구성·표현 등이 관찰 대상이며 문장 유사도만으로 끝내지 않는다. 예를 들어 한쪽만 출처 한계를 다룬다는 것은 관찰일 수 있지만 ‘사용자가 더 보수적이기 때문’이라는 설명은 아직 가설이다. 사용자가 제출하지 않은 자기설명·지시를 시스템이 만들어 원문처럼 저장하지 않는다.

그다음 관련 산출물과 실제 입력 기록을 대조한다. 두 수행의 정보 접근 차이, A의 조사 내용과 B의 초안 변환, C의 입력·역할 범위, 아직 명시되지 않은 조건부 판단, 표현 선호 또는 사례 한정 차이 등 복수 가설을 조사한다. 어느 쟁점이 실제 해당되는지는 원본과 대안 증거로 판단하며 예시 가설을 발견 사실처럼 쓰지 않는다. 대안이 C의 수행에 대응한다는 이유만으로 원인도 C라고 단정하지 않는다. 산출물이 입력에 존재했다는 사실만으로 실제 활용이나 인과적 영향을 입증했다고 하지 않는다. 사용자 대안의 오류·일반화할 지식 없음·원인 미확정도 남긴다.

제품 경험 제안: 사용자는 같은 검토 흐름에서 근거가 있는 관찰, 잠정 해석, 아직 모르는 부분을 구별해 본다. 여러 원인이 병존할 수 있으며 자료가 없으면 관찰 부족을 표시한다. 이 단계가 피드백 루프의 끝은 아니다.

논문 근거: 4.6–4.7절, 20–22쪽.

## 5. 두 수행의 차이를 설명하는 가설을 철학 렌즈로 탐구하고 새 증거를 얻는다

앎·표현의 사용 맥락·역할·의무·피해·정당성·예외 등의 차이가 판단 범위에 영향을 주는 상황이면 SPLI를 발동한다. 한 단어라도 발화 주체·근거의 지위·수신자의 행동 해석을 가르는 차이일 수 있다. 피드백 크기만으로 탐구를 배제하지 않는다. 반대로 기존 필드의 단순 복원임이 확인되면 철학적 새 의미를 억지로 부여하지 않는다.

INT-029에 따라 이 탐구는 사용자 피드백 뒤의 고립된 단일 화면이 아니다. 설계 크리틱·보완 또는 반복 평가에서도 확인된 판단 차이·전문가 판단 가설과 적용 조건이 갖춰지면 연결하고, 얻은 증거를 해당 후보의 보완·재검증으로 돌려보낸다. 초기 설계 때 관련 판단 증거가 아직 없으면 에피소드 성향을 만들어내지 않고 출처 기반 반례 탐색·업무 확인과 구분한다.

1. 대안 수행 이후 확인된 차이와 전문가 판단 가설을 출발점으로 삼는다. 사용자에게 자신의 판단 원인을 먼저 해설하게 하거나 한 설명을 확정한 뒤 그에 맞는 철학 이름을 붙이지 않는다. 논문 4.8.2절의 실제 사례 세 개 비교는 사용자 구성개념을 얻는 추가 증거 수집 절차로 다룬다. 대안 제출 이전의 자기설명 요건으로 옮기지 않으며 실제 사례 부족은 드러낸다.
2. 관찰된 수행과 양립하는 복수의 출처 기반 미세렌즈·대조 렌즈·unknown을 유지한다. 선택 뒤의 사용자 설명이 있더라도 보조 증거로 분리하고 그 설명에 맞는 해석만 남기지 않는다. 한 대안은 근거 기준·목적·역할 책임·예외 등에 관한 여러 해석과 양립할 수 있다.
3. 경쟁 해석이 다른 수행을 예측하는 최소변형 상황을 만든다. 예를 들어 자료는 같고 문서의 사용 목적만 달라졌을 때 사용자가 작성하는 검토가 달라지는지, 또는 목적은 같고 증거의 강도만 달라졌을 때 달라지는지를 각각 대조할 수 있다. 듀이의 경험적 탐구와 아리스토텔레스의 맥락적 실천지 계열 등은 이런 탐구의 출처가 될 수 있지만 어느 렌즈가 맞는지는 새 수행/선택을 보기 전에 확정하지 않는다(논문 4.8.1절 24쪽). 일반 UI에서는 철학 이름을 숨기고 새로운 작성·선택을 먼저 받으며 이유 설명은 필요할 때만 보조적으로 요청한다. 이 구체 사례와 추가 부분 작성 UX는 제품 제안이며, 사용자가 모든 질문이나 장문 대안을 완성해야 시험 가능한 구조로 강제하지 않는다.
4. 사용자는 해석을 확인·수정·거절하거나 답변을 보류할 수 있다. 질문 정보 가치·부담·민감성·예산을 고려하고 계속 묻는 것이 도움이 되지 않으면 중단한다.
5. 아직 보지 않은 선택의 예측을 고정한 뒤 새 응답·후속 실제 업무 선택으로 시험한다. 이 새 증거로 전문가 판단 가설을 갱신하거나 기권한다.

제품 경험 제안: 사용자는 이번 업무와 연결된 짧은 심화 검토를 수행한다. 질문의 출발점과 판단에 미치는 영향을 이해할 수 있어야 한다. 당장 답할지 나중에 재개할지, 상세 해석·출처를 어디서 열어 볼지는 아직 UX 선택 사항이다. 철학자 성향 검사나 모든 업무에 고정된 설문은 아니다.

논문 근거: 4.8절, 23–28쪽. 이 단계는 자기설명의 철학적 재서술이 아니라, 대안 수행에서 관찰한 차이의 여러 해석을 구별할 추가 업무 증거를 얻는 과정이다. 기존 초기 설계·크리틱의 출처 기반 렌즈 활용(INT-021·029)은 유지하되 이 사후 대안 비교 경로와 구별한다.

## 6. 검증할 변경 후보와 평가 기준을 준비한다

새 업무 증거를 바탕으로 갱신된 전문가 판단 가설과 시스템 가설에서 변경 후보를 만든다. 철학 해석 기록을 그대로 운영 지식이나 프롬프트에 주입하지 않는다.

가상 후보 예시(두 수행의 비교와 추가 증거가 해당 가설을 뒷받침할 때만 해당하며, 사용자 대안이 들어오기 전에 확정한 문제·정답이 아님):

- 복원: C가 검토에 사용하도록 정해져 있던 A의 조사보고서나 출처 참조를 받지 못했다면 해당 입력 연결을 복원한다.
- 학습: 새 증거로 필요한 판단 기준이 확인되면 C가 효과 주장과 근거의 연결·남은 불확실성·필요한 수정/추가 검증을 검토문에 반영하도록 하는 조건부 변경 후보를 만든다. 해당 업무·역할·검토 범위에 한정하며 사용자 수정 검토문을 향후 정답으로 복사하지 않는다.
- 보호: 수정 초안이 유효한 비판을 반영했는지 별도 검사하는 후보를 시험한다. 모든 크리틱 의견을 무조건 수용하거나 근거 없는 비판도 출력에 강제하지 않는다.

세 가지를 한꺼번에 적용하고 성공 이유를 단정하지 않는다. 변경 대상을 나눠 시험하고 조합의 효과도 별도로 확인한다. 사용자는 지금 확인한 한 변경부터 시험하고 나머지는 보류할 수 있다. 전체 피드백·전체 렌즈 탐구가 끝나야 후보를 시험할 수 있다는 구조로 만들지 않는다.

가령 C의 검토 방식 변경을 시험한다면 동일한 조사보고서·초안 버전에서 새 검토문을 만들고, 그 검토문을 받은 B의 수정 초안도 비교할 수 있다. 이는 산출물의 초점 부분만 바꿔 끼우는 것이 아니라 해당 에이전트의 실제 수행과 다음 산출물에서 효과를 확인하는 제안이다. 영향 범위·재실행 시작점은 가설과 실행 의존성에 따라 정하며 관련 이전 큐·별도 최종 검증을 대체하지 않는다.

제품 경험 제안: 사용자는 무엇을 왜 바꾸려는지, 지지·반대 증거, 적용 조건과 예외, 아직 확인되지 않은 부분을 비교한다. 현재 운영 환경의 기준 버전, 비교할 업무 큐·입력·외부 응답 스냅샷, 평가 기준·평가기 버전과 변경 대상을 식별해 비교 실험을 준비한다. 기준과 목표는 결과를 보고 유리하게 바꾸지 않는다. 구체 평가 지표·큐 선정·목표 수치는 후속 설계 대상이다.

논문 근거: 4.8.5–4.10절, 27–30쪽.

### 6.1 무엇을 사례로 보존하고 무엇을 작동 방식으로 흡수하는가 — 핵심 분리 원칙 확인

대안 원문·탐구 기록·실행 지식을 분리하고 검증된 지식/구성 변화를 환경의 성장으로 남긴다는 설명에 사용자가 ‘응’이라고 답했다. 아래 분리·반영 원칙의 확인이며 상세 스키마·시험 정책·UI·전체 설계의 승인은 아니다. 직전 제출 절차 제안을 되살리지 않는다.

논문 4.8.5–4.9절(27–29쪽), 5.3–5.5절(35–37쪽)에 근거해 다음을 구별한다.

| 구분 | 남기는 내용 | 실행과의 관계 |
| --- | --- | --- |
| 대안 수행 증거 | 원 업무 상태, 에이전트 산출물, 사용자 버전과 실제 대안 범위·생성 조건 | 비교의 원본으로 보존한다. 전문가 원문을 실행 검색이나 중간 정답으로 삽입해 재현 성공을 만들지 않는다. |
| 탐구 기록 | 관찰된 차이, 복수 시스템/판단 가설, 사용한 미세렌즈와 대조 상황, 새 수행/선택, 지지·반박·미결 | 철학 해석을 곧 운영 규칙으로 삼지 않는다. 새 업무 증거로 갱신한 가설이 변경 후보에 연결된다. 어떤 렌즈·대조가 어떤 증거와 결과를 만들었는지 감사 계보는 보존한다. |
| 재사용할 지식과 실행 구성 | 증거가 붙은 조건·행동·예외, 적용 업무/역할/상황, 검증 결과·버전과 되돌릴 대상 | 적용 조건에 맞는 활성 지식을 선택해 프롬프트·검색 정책·도구 제약·핸드오프·평가기·그래프 설정으로 변환한다. 프롬프트는 파생 실행물이며 지식 원본이 아니다. |

모든 대안에서 반드시 새 지식을 만들지는 않는다. 이미 존재한 정보·입력 연결의 결손이라면 복원이 적합할 수 있고, 새로 확인된 수행 기준이 있으면 구성적 학습 후보가 될 수 있으며, 아직 이유가 불명확하면 에피소드 증거와 가설로 남긴다. 특정 사례의 수치·사실 정정·표현 선호를 모두 범용 판단 규칙으로 바꾸지 않는다. 표현·구성 차이도 정당한 개선 대상이며 해당 유형의 지식으로 구별한다.

후보마다 바꿀 구성요소, 기대되는 수행 변화, 예상 파급 범위, 서로 다른 가설을 가를 시험과 결과를 연결하는 방식으로 상세화한다. 가능한 모든 가설·후보를 전수 실행하거나 항상 세 후보를 만드는 정책은 정하지 않는다. 단독 변경 효과와 필요한 조합 효과를 구분하며 실제 시험 예산·우선순위는 별도 설계한다. 비용 부족이나 같은 모델의 고득점은 검증 통과를 뜻하지 않는다.

부분 대안에서 출발했어도 재실행 결과는 해당 부분의 문자 유사도뿐 아니라 에이전트 산출물 전체와 후속 역할, 관련 이전 업무 큐에서 비교한다. 사용자 대안이 없는 영역도 사전에 정한 업무 성공·사실·형식·안전·회귀 기준 등 해당 업무의 근거로 검사하며 그 영역을 사용자가 검토했다고 표시하지 않는다. 기준은 후보에 유리하도록 결과를 보고 바꾸지 않는다. 학습 후보로 개선됐다는 사실과 원래 실패 원인을 입증했다는 주장은 구별한다. 새로운 사례의 최종 검증과 사람의 정확한 후보 환경 승격은 기존 요구를 유지한다.

확인된 것은 ‘대안 증거·탐구 기록·실행 지식을 분리하고, 검증된 지식/구성 변화를 업무 조건에 맞춰 사용한다’는 흡수 구조다. 저장 기술·구체 지식 스키마·후보 수·예산·수치 지표·UI 조작까지 정한 것이 아니다.

### 6.2 새 대안과 기존 학습의 차이 — 재학습 핵심 원칙 확인

사용자는 성장을 지식의 계속된 추가뿐 아니라 이전 학습의 적용 범위 수정·잘못된 학습 대체까지 포함한다는 설명에 “응”이라고 답했다. 아래 내용의 재학습 원칙을 확인한 것이며 구체 충돌 해결 자동화·권한·중단 UX까지 확정한 것은 아니다.

새 대안이 이전 대안과 다르다는 사실만으로 지식 충돌을 선언하지 않는다. 각 수행의 업무·입력 산출물·역할·목적·시점을 비교해, 상황이 다른지 같은 조건에서 수행 기준이 양립하지 않는지부터 조사한다. 사용자에게 자신의 변화나 모순을 먼저 설명하도록 요구하지 않는다.

논문 4.7절(22쪽)은 조건부 판단·유효한 트레이드오프·정책/환경 변화·일회성 사례·전문가 오류 등을 가설로 둔다. 5.4–5.5절(36–37쪽)은 충돌한 지식을 덮어쓰지 않고 조건·권한·시점을 구분하며, 철학 해석의 충돌은 점수 합산이 아니라 새 관찰 계획으로 연결한다. 이를 다음과 같이 제품에 해석하는 방향을 제안한다.

- 다른 업무 조건에서 둘 다 타당하다면 적용 조건을 구분하는 후보를 만든다. 최신 사용자 버전을 전체 업무의 새 정답으로 쓰거나, 기존 규칙과 다르다는 이유로 새 대안을 배척하지 않는다.
- 이전 학습이 지나치게 일반화됐거나 잘못됐을 가능성이 있으면 해당 지식의 범위를 수정하거나 대체·비활성화할 후보를 시험한다. 실제 업무 조건의 변화라면 과거 당시의 타당성과 현재 적용 가능성을 구별한다. 무조건 새 예외를 덧붙여 기존 규칙을 보존하지 않는다.
- 철학 렌즈는 기존 학습을 방어하는 설명이 아니라 서로 다른 수행을 설명할 경쟁 가설과 구별 조건을 탐구하는 데 사용한다. 기존 기록을 먼저 활용하고 필요한 새 수행/선택 증거를 얻되, 추가 대안·자기설명을 의무화하거나 효과 없는 질문을 반복하지 않는다.
- 지식 변경 후보는 관련 이전 업무 큐와 새 조건에서 재실행해 원래 대안 밖의 파급효과도 평가하고, 별도 최종 검증과 사람의 정확한 후보 환경 승격에 연결한다. 과거 결과와 무조건 같아져야 회귀 통과라는 뜻은 아니며 당시/현재의 유효한 기준을 구별한다.
- 해결되지 않은 충돌을 임의 평균·최신 우선·관점 다수결로 운영에 적용하지 않는다. 충돌이 실제 실행 판단에 걸리면 문제가 된 지식의 적용과 의존하는 실행 범위를 보류·재검증/사람 확인 대상으로 다룬다. 모든 새 대안 입력이나 무관한 전체 업무를 일괄 중단시키는 정책은 정하지 않는다.

원 대안과 과거 지식의 이력은 덮어쓰지 않는다. 운영 지식의 철회는 유효 종료·비활성화와 재검증 계보로 관리하는 논문 원칙을 따르되, 원문 보존·삭제 요청·민감정보 정책은 별도다. 이번에 확인된 것은 ‘새 대안과 기존 학습의 관계도 탐구해 조건 분화·수정·대체할 수 있다’는 재학습 원칙이며 구체 충돌 해결 자동화·권한·중단 UX까지 승인된 것으로 보지 않는다.

## 7. 이전 업무 큐를 재실행하고 개선 정도를 평가하며 반복한다

**사용자 직접 수정(INT-018):** 운영 반영을 승인하기 전에, 변경 후보가 적용된 환경으로 이전 업무 큐를 다시 진행하고 얼마나 개선됐는지 평가한다. 필요하면 자동 또는 사람 개입 방식으로 후보를 수정하고 재실행·재평가하는 루프를 돌린다.

제품 경험 제안:

1. 기준 환경과 후보 환경을 분리하고, 비교 가능한 같은 대상 업무 큐와 입력 조건에서 실제 평가용 재실행을 수행한다. 저장된 정답·기존 평가표를 보여 주는 것만으로 재실행을 대신하지 않는다. 처치 외 모델·도구·프롬프트 버전과 외부 응답은 가능한 한 고정하고 불일치·재현 불가 조건을 표시한다.
2. 같은 업무별 기존 결과와 후보 결과를 대응해 판단 품질·업무 성공·실패와 위험·비용·시간 등 합의한 기준의 변화를 비교한다. 전체 및 업무별 개선·악화·동률·실패·누락·측정 불가를 함께 표시하며 평가 자체가 달라지면 점수의 직접 비교 가능성을 구분한다.
3. 부족한 부분에 대해 진단·필요한 추가 피드백 및 철학 렌즈 탐구·변경 후보 수정으로 돌아가 다시 큐를 실행한다. 자동화할 수 있는 반복과 사람이 개입할 지점을 구분한다. 반복 한도·비용·중단 조건·허용 변경 범위는 후속 설계하며 무한 실행으로 해석하지 않는다.
4. 매 회차의 후보·변경 내역·실행·평가·사람 개입을 연결한다. 실패한 회차도 남긴다. 실험용 후보 버전은 아직 승인된 운영 환경의 새 버전이 아니다.
5. 최종 후보를 고정하고 별도로 보존한 미관측 사례 또는 독립된 전향적 자료, 경계·역사적 회귀 검사로 최종 확인한다. 반복 수정에 사용한 이전 업무 큐는 개발·재구성 근거이며, 다시 봉인된 미관측 전이 성능이라고 부르지 않는다.

재실행은 분리된 평가 환경에서 수행한다. 과거 메일 발송·결제·외부 데이터 변경 등의 부작용을 실제로 중복 실행하는 허가는 아니다. 원 실행과 증거를 덮어쓰거나 전문가 정답을 운영 검색에 넣어 점수를 올리지 않는다. 재현할 수 없는 항목은 검사 성공으로 취급하지 않는다.

이 단계는 다음 신규 업무에서 변화를 관찰하는 단계와 구별되는 **운영 반영 전 반복 평가 루프**다. 자동 반복도 최종 운영 승인을 대체하지 않는다. 자료가 부족하면 기본 검사를 거친 출력 영향 없는 관찰 전용 상태에서 추가 증거를 모으되 개선 검증·버전업 완료로 표시하지 않는다.

논문 연결: 4.9–4.10절(29–30쪽)의 반복 비교, K1 동일 사례 재구성·K2 전이·K3 경계·K4 역사적 회귀와 개발/봉인/전향 자료 구분. ‘이전 업무 큐를 반복 평가하는 제품 루프’는 이번 사용자 요구로 명시했다.

### 7.1 자동 반복과 사람 개입의 경계 — 핵심 원칙 확인

사용자는 ‘허용된 실험은 자율적으로 이어 가고, 새로운 사람 판단·권한이 필요한 지점에서 개입하며, 운영 승격은 사람이 결정한다’는 설명에 “응”이라고 답했다. INT-018–019의 반복 개선에 관한 권한·중단 경계의 핵심 원칙 확인이다. 화면 모드 세 가지와 별개이고, 별도 자율성 모드나 단계마다 승인하는 UI를 추가하는 제안이 아니다. 구체 한도·시작/재개 조건·화면 조작은 미정이다.

논문 4.8.3절(26쪽)은 질문의 정보 가치·부담·민감성·예산, 거절과 기권을 다룬다. 4.9–4.10절(29–30쪽)은 격리된 구성 변경과 반복 비교, 렌즈 기권 뒤에도 본체 검증을 이어 갈 가능성, 사전 검증 기준과 사람의 승격을 명시한다. 6.2절(39쪽)은 외부 부작용 도구의 재실행 제한을 정한다. 이를 근거로 다음 경계를 제안한다.

- **허용된 실험 안의 자율 진행:** 대상 업무 환경·변경 가능한 구성 종류·자료와 도구 권한·실행 시간/사용량/반복 한도·검증 조건이 정해진 범위 안에서 차이 탐구, 필요한 렌즈 후보·반례 탐색, 변경 후보 생성, 관련 이전 큐 재실행과 재평가를 이어 갈 수 있다. 각 가설·렌즈·후보 생성마다 사람 승인을 받는 절차로 만들지 않는다. 고정 기준을 점수 통과를 위해 임의로 낮추거나 권한·자료·모델/과금 경로를 몰래 바꾸지 않는다. 변경 허용 범위는 사람의 부분 대안 작성 범위와 같지 않으며 그 밖의 영향을 계속 검사한다.
- **새 사람 수행·권한이 필요할 때의 연결:** 기존 증거로 구별할 수 없는 판단 차이에 새 수행·선택이 필요하면 관련 원본과 조건을 놓고 자신의 버전이나 선택을 받을 수 있게 한다. 시스템이 대신 사람의 응답을 만들어내거나 수정 이유·원인 설명을 의무화하지 않는다. 새 외부 접근·부작용·비용 한도 확대·업무 목적 또는 검증 기준 변경 등이 필요하면 기존 권한으로 처리하지 않고 해당 선택을 요청한다. 필요한 지점에 의존하는 후보/분기만 보류하며, 영향을 받지 않는 허용 작업과 사용자 본래의 업무까지 일괄 중단하지 않는다. 렌즈 질문 거절은 해당 탐구 경로의 기권일 수 있고 전체 개선 루프의 실패 판정은 아니다.
- **끝없이 반복하지 않는 종료·보류:** 사용자가 멈추거나, 합의한 한도에 도달하거나, 비교 근거를 더 얻지 못하거나, 실험 자체의 안전·격리·권한 경계를 유지할 수 없으면 해당 범위의 자동 반복을 종료 또는 보류한다. 후보의 일반적인 평가 실패는 허용 범위 안에서 수정·재검증할 수 있으며 실패를 기록하고 승격을 차단한다. 더 넓은 영향의 발견 자체를 전역 중단 사유로 삼지 않되 실제 안전 위험이 미치는 범위는 별도로 판단한다. 현재 후보·변경·실험 결과·남은 불확실성과 중단 사유를 보존하고, 부족한 상태를 성공으로 바꾸거나 구독 한도에서 API 유료 경로로 자동 전환하지 않는다. 일시적 실패의 재시도, 진전 없음의 판정, 구체 수치와 자동 재개 조건은 후속 설계한다.
- **시험 결과를 확인하는 일과 운영 승격의 분리:** 사용자는 반복 중에도 실제 후보 산출물과 원본/자기 대안, 관련 다른 산출물의 변화를 확인하며 새 대안을 남길 수 있다. 모든 탐구가 끝난 뒤에만 결과를 볼 수 있는 일괄 처리로 만들지 않는다. 결과가 좋아 보여도 후보 고정·별도 최종 검증·사람의 승격을 거쳐야 지속 운영 버전이 된다. 원 대안·비교 대상·후보 버전을 식별하며 새 대안이 들어왔을 때의 회차/분기 처리는 후속 설계한다.

이 경계는 사용자의 침묵이나 ‘이 정도 보면 됐다’는 자연스러운 생각을 자동 실행 허가로 해석하지 않는다. 실제 저장·탐구 시작·시험 재개 계기, 기본 한도와 승인 UX는 미정이다. 이번 대화의 확인은 향후 제품 동작의 설계 검토이지 현재 프로젝트에서 모델·외부 도구 호출을 수행하도록 허가하는 것이 아니다.

## 8. 사람이 개선 결과를 최종 승인하면 해당 업무 환경을 버전업한다

**사용자 직접 수정(INT-019):** 사람이 반복 개선 결과를 최종 승인하면 그 후보를 해당 업무의 멀티에이전트 운영 환경의 새 버전으로 삼는다. 이는 지식 항목의 저장이나 프레임워크 프로그램 자체의 버전업과 다르다.

제품 경험 제안: 승인 대상은 특정 후보 환경과 연결된 비교 평가·최종 검증 결과, 적용 범위, 변경 내역이다. 예시에서는 해당 전달의 무엇이 바뀌고 수신·후속 산출물과 관련 과거 업무에서 어떤 개선/악화가 확인됐는지 보여 준다. 전체 역할·그래프를 처음부터 재검토하도록 요구하지 않는다. 권한 있는 사람이 이를 보고 최종 승인한다. 점수 달성이나 자동 루프 종료만으로 운영 버전을 전환하지 않는다. 승인 후 후보 내용이 바뀌면 이전 승인을 그대로 재사용하지 않는다.

환경 버전은 해당 업무의 역할·그래프·기억/판단 정책·도구 제약·사람 승인·평가 설정 등 실제 구성과 연결된 지식·실행물 버전을 식별한다. 매번 모든 요소를 바꾼다는 뜻은 아니다. 운영 기준 버전과 실험 후보의 계보를 유지하고, 평가한 후보와 승인한 후보와 운영에 반영된 버전이 일치해야 한다.

제품 경험 제안: 관찰 전용·제한된 검증 운영에 대한 승인과 새 운영 환경 버전에 대한 최종 승인을 구별한다. 사용자는 검증 근거·대상 업무·권한자·중단 조건·되돌릴 버전을 보고 최종 적용을 판단한다. 최종 승인이 보류·기각되면 기존 운영 기준 버전을 유지한다.

최종 승인된 환경 구성이 해당 업무의 실행에 연결된다. 다음 업무에서 실제로 어떤 환경 버전과 그 안의 지식·설정 버전이 사용됐고 어떤 행동이 달라졌는지 확인한다. 반례·정책 변화·새 오류가 발생하면 재검증·중단·롤백으로 이어진다. 지식 문서에 ‘학습 완료’만 표시하고 실행은 그대로인 상태를 완료로 보지 않는다.

질문도 매번 처음부터 반복하는 고정 설문이 아니다. 기존 증거와 현재 역할·상황을 고려해 더 확인할 가치가 있는 부분을 묻는다. 판별력이 검증되지 않은 렌즈에 효과가 있다고 주장하지 않는다.

논문 근거: 4.8.3–4.8.5절, 25–28쪽; 4.10절, 30쪽; 5.4–5.5절, 36–37쪽.

## 선택적 행위 — 원할 때 제작자에게 로그와 피드백을 전달한다

**사용자 직접 수정(INT-020):** 이는 앞 단계 다음에 항상 수행하는 8번 단계가 아니다. 사용자가 원할 때 수행하는 별도 행위다. 업무 완료·개선 루프·승인·환경 버전업의 선행 조건이나 완료 조건으로 강제하지 않는다.

업무 환경의 지식 개선과 별도로, 설치·사용·요청·설계 후보 생성/탈락/크리틱/선정·설계 수정·실행·피드백·렌즈 질문·변경·승인 과정의 기록을 연결한다. 기록은 내보내기 기능을 만들 때부터가 아니라 설치 직후부터 마련한다. 초기 탐색 로그에는 렌즈·하이브리드 구성과 후속 실행 성과를 연결하되 모델의 숨은 사고과정·비밀번호·API 키를 수집하지 않는다.

제품 경험 제안: 사용자는 UI에서 필요한 기록을 선택하고 공개 범위·민감정보를 확인한 뒤 파일로 추출해 의견과 함께 제작자에게 전달한다. 자동 외부 전송은 전제하지 않는다. 정확한 원문 포함 범위·가림·보관·전달 방식은 별도 설계 대상이다.

이 행위의 직접 근거는 논문에서 추론한 부가 기능이 아니라 사용자 요구 INT-005–007·020이다. 기록 기반은 전 과정에 걸쳐 유지하되, 추출·전달은 선택적이다.

### 기록과 제작자 전달의 경계 — 공유용 증거 묶음 원칙 확인

사용자는 내보낼 파일을 ‘공개 범위를 확인한, 관련 맥락과 재현 한계까지 담긴 증거 묶음’으로 설계한다는 설명에 “응”이라고 답했다. 기록을 단순 오류 로그로 축소하지 않고 프레임워크가 관련 근거를 모으며, 사용자 환경의 성장과 제작자 피드백 전달을 구별한다는 원칙의 확인이다. 파일 형식·보존기간·세부 수집/가림 정책·전달 채널의 승인은 아니다.

논문 4.4절(18–19쪽)은 원 실행·사후 진단·개입/실험을 구별해 계보로 연결한다. 6.2절(38–39쪽)은 해시만으로 내용을 복구할 수 없으므로 실제 입력·스냅샷·버전·접근/재배포 상태를 가진 재현 봉투가 필요하다고 명시한다. 6.5절(40–41쪽)은 원문·상세 추적의 로컬 또는 조직 지정 저장, 외부 전송 최소화와 사전 표시, 역할별 접근·목적별 보존을 정한다. 다음은 이 근거와 사용자 요구를 결합한 제품 제안이며 아직 직접 확인된 상세 정책은 아니다.

- **첫 사용부터 이어지는 내부 기록:** 설치 직후부터 프레임워크 안의 정상 사용·요청·설계·실행·오류·변경·승인 사건과 관련 산출물/버전을 연결한다. 수집 목적과 범위를 알리고, 원문·상세 기록은 로컬 또는 조직이 지정한 저장소에서 관리하는 방향을 제안한다. 오류 로그만 남기거나 내보내기 기능 개발 시점부터 기록하는 구현은 불충분하다. 전 과정의 사건을 다룬다는 요구를 다른 앱의 활동·모든 키 입력·비밀정보 수집 또는 원문 무기한 보존으로 확대하지 않는다. 원문 수집·보관·삭제 및 기록 실패 처리의 상세 정책은 별도 설계한다.
- **탐색의 전체 이력:** 채택된 안뿐 아니라 단독/하이브리드 렌즈 정의·출처·버전·조합, 후보 생성·실패·탈락, 크리틱 근거·불일치·선정·제시 순서, 사용자 선택과 후속 실제 성과를 연결한다. 원 대안·관찰 차이·가설·렌즈 질문/새 증거·시험 후보·운영 버전을 혼합하지 않는다. 미실행 후보의 예상 평가를 실제 실행 성과로 표시하거나 선택된 안만으로 렌즈의 우월성을 주장하지 않는다. 개인별 철학·성격 점수를 만들기 위한 집계가 아니라 해당 설계/업무 에피소드의 탐색 기록이다.
- **선택적 공유용 증거 묶음:** 사용자가 다루려는 업무·문제·기간을 기준으로 관련 기록과 버전을 프레임워크가 모으고, 포함 내용·원문·가림/제외 범위를 확인해 추출하도록 설계한다. 사용자가 기술 로그와 의존 파일을 직접 조합할 필요가 없어야 한다. 원문·자격증명·숨은 추론을 자동 업로드하지 않으며, 자격증명과 숨은 추론은 로그 수집 대상에서도 제외한다. 가림으로 원 기록을 덮어쓰지 않고 공유용 사본을 만들며, 제외·삭제·접근 불가로 증거가 빠진 위치와 그로 인한 진단/재현 한계를 표시한다. 비식별화 성공이나 완전 재현을 자동 보장하지 않는다. 공유 묶음에는 별도의 무결성·참조 검사를 적용하되 원문 해시 등 식별 가능 메타데이터의 외부 공개 여부도 검토한다.
- **두 성장 순환의 분리:** 사용자 자신의 대안 수행이 업무 환경의 검증된 지식·구성 변화로 이어지는 순환과, 사용자가 제작자에게 보낸 기록·의견으로 프레임워크 자체를 개선하는 순환은 별개다. 보내지 않아도 자신의 환경은 계속 성장한다. 전달 동의를 개인 판단 지식의 공통 기본값 반영·모델 학습·공개 데이터셋 배포 동의로 간주하지 않는다. 제작자가 받는 자료는 문제 이해와 개선 가설의 증거이며 보편적 정답이 아니다. 재현을 위한 모델 호출이나 외부 도구 실행도 추출·파일 열기만으로 허용하지 않는다.

이번에 확인된 것은 ‘내부 전 과정 추적’과 ‘사용자가 공개 범위와 결손을 확인한 선택적 공유용 증거 묶음’의 관계다. 파일 형식, 전달 채널, 보존기간, 세부 가림 정책, 자동화 범위, 구체 UI는 아직 정하지 않는다. 모델 실행에 필요한 제공자 전송과 제작자 진단 자료 전달 역시 다른 경로로 구분한다.

## 이 경험을 검증할 기준 초안

- 비개발자가 별도 코드·명령어·어댑터 파일 작업 없이 업무 설명부터 실제 환경 구성과 실행까지 진행한다.
- Claude·Codex 두 구독 경로 각각에서 API 키 없이 대표 핵심 LLM 여정이 실제로 실행되는지 확인한다. API 방식은 사용자 명시 선택 후에만 호출되고, 구독 한도·인증 실패 때 유료 API로 자동 전환되지 않아야 한다. 호출 경로·모델·버전 기록과 비밀정보 비노출도 검증한다(INT-025–026).
- 작업공간·대화·그래프 캔버스 세 모드를 제공하고, 같은 업무의 설계·실행·산출물·대안·탐구·실험·평가·승인 맥락이 모드 전환에도 유지되는지 확인한다. 전환만으로 중복 실행·승인·환경 버전이 생기거나 작성 중인 내용이 사라지는 결과는 허용하지 않는다. 공통 관계는 확인됐고 저장·충돌·전환의 구체 방식은 후속 설계한다.
- 초기 설계에서 단독·하이브리드 관점의 실제 구조 후보와 독립 크리틱 평가, 필수 제약·품질·다양성을 고려한 선별을 확인한다. 일반 UI의 중립적 설명과 내부 감사용 출처 기록을 구분하고, 탈락·실패 후보까지 후속 성과와 연결한다.
- 설계·실행·피드백·철학 탐구·실험·적용을 이동해도 업무·출처·버전의 연결이 유지된다. 중단·재개 시 기록이나 승인 상태를 잃지 않는다.
- 렌즈는 관점 이름을 붙이는 데서 끝나지 않는다. 판별 질문, 새 증거, 해석의 갱신 또는 기권, 검증할 변경으로의 연결을 확인할 수 있다.
- 운영 반영 전에 이전 업무 큐를 재실행해 기준 환경과 비교하고, 자동 또는 사람 개입으로 변경·재평가를 반복한다. 개선뿐 아니라 악화·실패·측정 불가와 모든 회차의 이력을 확인한다.
- 반복 평가에 쓰인 큐와 최종 검증 자료를 구별하고, 평가한 정확한 후보에 대한 사람의 최종 승인 전에는 해당 업무의 새 운영 환경 버전을 활성화하지 않는다.
- 다음 업무에 적용된 변경과 미적용 후보를 구분할 수 있고, 승인되지 않은 후보가 실운영에 섞이지 않는다.
- 제작자는 사용자가 추출·전달한 기록에서 문제의 전후 맥락과 버전을 검토할 수 있다. 실제 수집·공유 범위는 별도 합의에 따른다.
- 사용자가 제작자에게 아무것도 전달하지 않아도 업무 수행·반복 개선·환경 버전업을 완료할 수 있다.

이 문서의 목적은 위 전체 경험이 의도와 맞는지 확인하는 것이다. 상세 화면·아키텍처·지원 도구·자동화 수준을 확정하거나 구현을 시작하지 않는다.

## 통합 검토 절차 재설계 — 선행 산출물 없는 피드백 검토 시도 철회

사용자는 유튜브 콘텐츠 기획 업무를 설명한 뒤, 그 설명을 피드백으로 가공하려는지 질문했다. 이어 실제 상황과 선행 산출물을 먼저 제시한 뒤 대안을 받아야 하며 이번 턴은 피드백 실험으로 무효라고 지적하고 검토 절차를 다시 설계하도록 요청했다. 직전 ‘업무 설명을 받아 통합 검증으로 진행’ 제안은 유효한 피드백 검토 절차로 채택하지 않는다.

### 이전 턴의 데이터 지위

- 당시 비교할 선행 산출물은 제시되지 않았고 실제 사용자 대안도 얻지 못했다. 피드백·학습·개선 효과·검증 증거는 성립하지 않았다.
- 받은 업무 설명을 사용자 대안, 선호 학습, 정답, 평가 기준 또는 새 산출물에 대한 사후 피드백으로 재분류하지 않는다. 그 세부 설명에 맞춰 선행 산출물을 나중에 만들고 앞선 설명을 소급해 대안으로 연결하는 일도 금지한다. 다음 예시를 개인화하는 지시나 개인 평가표로 우회 활용하지 않는다.
- 원 대화는 절차 오류를 확인한 이력으로 남기되 학습/평가 증거로 삼지 않는다. 기록 보존과 증거 채택은 다르다. 사용자의 검토 절차 정정은 제품 설계에 반영하지만, 배제된 업무 설명을 DeepTwin 학습 데이터로 넣지 않는다.

### 논문 근거와 이번 검토의 한계

4.4절(18–19쪽)은 대안이 생성되기 전에 원 실행을 봉인하고 사후 진단이 원 실행을 바꾸지 못하게 한다. 4.5절(19–20쪽)은 실제 대안·원본/입력 맥락·검토 범위와 생성 조건을 기록한다. 4.6–4.8절은 관찰된 차이 이후 경쟁 해석과 필요한 렌즈·새 수행 증거를 탐구한다. 4.9–4.10절(28–30쪽)은 대안 복사에 의한 누출을 금지하고 동일 사례 재구성과 전이·회귀·사람 승격을 구별한다.

이번 대화에서 수행할 수 있는 것은 명시된 예시 산출물과 실제 사용자 대안으로 절차·제품 경험을 검토하는 수동 리허설이다. 자동화된 DeepTwin 엔진, 실제 전체 관찰 계약, 이전 큐 반복·전이·회귀 성능을 이미 검증한 실험이라고 부르지 않는다. 절차 리허설에서 얻은 실제 대안도 나중에 미관측 최종 평가 자료로 재사용할 수 없다. 원 산출물을 보고 만든 대안은 그대로 ‘원 결과를 본 대안’이며 독립 수행으로 표시하지 않는다.

### 당시 제안한 새 순서 — MANUAL-001 비교 전 종료, 재시도하지 않음

1. **개발자가 먼저 검토 패킷을 준비한다.** 새로 명시한 업무 상황, 과업 목적·허용 조건, 실제 제공할 입력 자료, 해당 역할과 산출물을 받을 다음 역할을 정한다. 예시·가정과 확인된 사실을 구분하고 사용자에게 기존 업무 설명이나 평가표를 다시 쓰게 하지 않는다. 한 역할이 완성한 선행 산출물 전체와 필요한 앞뒤 맥락을 패킷에 포함한다. 소재·분량·구체 역할은 이 절차 확인 뒤 패킷에서 제시한다.
2. **사용자 대안 이전의 산출물과 생성 조건을 고정해 제시한다.** 기준 산출물 작성에는 허용된 패킷만 전달하는 별도 문맥을 사용하고 실제 전달 입력을 남기는 방향으로 준비한다. 현재 대화는 이전 설명을 이미 봤으므로 완전한 블라인드·오류 독립성을 주장하지 않는다. 나중 대안을 보고 원본을 수정하지 않으며, 의도적으로 저품질 결과나 특정 결함을 만들어 예상한 피드백을 유도하지 않는다. 상황·자료·산출물을 한 번에 보여 주되 예상 문제·해석·철학 이름·정답 힌트는 먼저 제시하지 않는다. 상세 선행 산출물이 없으면 대안 비교 단계로 진행하지 않는다.
3. **사용자는 그 상태에서 자기 버전을 남긴다.** 전체 또는 선택한 부분에 대한 실제 대안을 받는다. 이유·원인 설명·수정 지시, 나머지 부분 검토나 완성 선언을 요구하지 않는다. 비교에 사용한 범위·시점·버전을 구별하는 내부 기록을 새 제출 버튼이나 단계별 승인 의무로 바꾸지 않는다. 대안이 없거나 차이가 없으면 비교 근거가 없는 상태 또는 차이 없음으로 남기며 학습할 차이를 꾸며내지 않는다.
4. **실제 차이에서 탐구한다.** 관찰된 차이와 그 설명 가설을 분리하고 복수 해석·불확실성을 남긴다. 필요한 철학 미세렌즈는 해석을 구별할 조건·반례·질문을 만들며, 사용자에게 철학적 자기설명을 요구하지 않는다. 실제 새 수행·선택 증거로 가설을 갱신하거나 기권한다. 렌즈 이름, 설명의 그럴듯함, 사용자의 단순 동의를 효과 증거로 삼지 않는다.
5. **변경 가설과 재수행 결과를 나란히 검토한다.** 무엇을 바꾸고 어떤 국소·후속 변화가 예상되는지 먼저 기록한다. 가능하면 명시한 입력과 변경 조건으로 실제 재수행하고, 하지 않은 실행은 예상으로 표시한다. 사용자의 대안을 복사하거나 현재 대화 전체를 실행 입력에 넣은 재작성을 독립적 흡수로 주장하지 않는다. 작성 부분 밖의 산출물 변화도 보며 사용자가 새 대안을 남기는 반복을 허용한다. 수동 리허설 결과는 원인 입증·엔진 학습 효과·운영 승격 증거와 구별한다.
6. **경험 검토와 구현 후의 효과 검증을 분리해 마무리한다.** 이번에는 사용자가 자신의 대안을 남기고 차이 탐구·변화를 확인하는 경험이 의도와 맞는지 검토한다. 어긋난 지점을 설계·수용 기준에 반영하되 자동으로 ‘UX 일치’ 판정을 내리지 않는다. 실제 엔진의 이전 업무 큐 반복 평가·별도 미관측/전향 검증·사람 최종 환경 승격은 구현 후 실제 실행 근거로 검증한다. 리허설에서 모든 렌즈 질문을 끝내거나 모든 차이를 해결해야 다음 산출물을 볼 수 있다는 절차로 만들지 않는다.

이것은 기존 제품 정의 전체의 철회가 아니라 검토 절차의 수정이었다. 사용자는 실효성에 대한 의문을 유지하며 가능하다면 한 번 해보라고 했다. 이에 [MANUAL-001](rehearsals/manual-001/README.md)에서 새 가상 입력과 별도 문맥 작성자의 기준 산출물 1건, 논문 기반 수동 렌즈 질문 규칙 초안을 준비했다. 이후 사용자는 기획안이 대안을 남길 수 없을 정도로 부적합하여 현 단계에서 이런 방식의 검증은 수행할 수 없다고 판단했다. 이 시도는 비교 전에 종료했다. 위 순서는 시도 이력으로만 보존하며 현재 사용자에게 대안을 요구하는 절차가 아니다.

실제 사용자 대안·차이 탐구·렌즈 적용·재수행·효과 검증은 없다. 이번 거절을 대안 수행이나 학습 증거로 가공하지 않으며 새 기획안으로 재시도하지 않는다. 사용자가 인정한 것은 대화를 통한 의도 이해의 의미다. 제품 경험 일치·DeepTwin 효과·크리틱 독립성 또는 전체 설계 승인으로 확대하지 않는다. 실제 환경·렌즈 엔진·평가기의 효과 검증은 미실시로 남으며, 실패한 수동 검토를 제품의 효과 없음으로 일반화하지 않는다. 기존 제품 요구는 유지하고 설계 검토와 구현 후 검증을 구별한다. 구체 화면·버튼·구현은 시작하지 않는다.
