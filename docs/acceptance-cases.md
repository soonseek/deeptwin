# 의도 보존을 위한 수용·거부 사례 초안

날짜: 2026-09-06

상태: 사용자 제공 실패 사례·목업·영상에서 도출한 **검토용 기준**. 실제 기능 테스트 결과나 사용자 개별 승인 완료를 뜻하지 않는다. 대표 업무 입력은 아직 정하지 않았다.

근거: [참고 자료 검토](reference-review-2026-09-06.md), [제품 의도](product-intent.md).

| ID | 거부할 결과 | 대응하는 수용 방향 |
| --- | --- | --- |
| AC-001 | 비개발자가 먼저 에이전트 코드·JSONL·실행 경로를 준비하거나 별도 코딩 에이전트에 개발을 맡겨야 업무 환경을 시작할 수 있다. | 업무 설명·자료를 출발점으로 설계·검토를 돕고 승인한 실행 가능한 환경 구성을 프레임워크가 맡는다(INT-010 확인). 지원 도구·연결 방식·내부 구현 방식은 후속 설계한다. |
| AC-002 | 자료 업로드는 성공했지만 설계에 자료 내용이 반영되지 않는다. | 자료에서 이해한 업무 조건과 설계의 연결을 확인할 수 있다. 읽지 못한 자료·불확실성도 표시한다. |
| AC-003 | 노드 이름과 선을 장식적으로 보여주지만 실제 업무의 진행·전달·실패와 연결되지 않는다. | 실제 실행 사건과 선택 업무에 근거해 흐름·상태·상세 근거를 확인한다. 재생/모의/실시간 상태를 구별한다. |
| AC-004 | 업무 한 건을 파악하기 위해 독립 페이지에서 매번 같은 건을 다시 찾고 결과·추적·승인 맥락을 조합해야 한다. | 같은 업무·실행·설계 버전을 유지하면서 결과·근거·흐름·평가·승인으로 이동할 수 있다. 모든 정보를 한 화면에 과밀하게 넣으라는 뜻은 아니다. |
| AC-005 | 피드백과 변경 JSON을 저장하고 점검 보고서를 출력하는 것으로 성장 기능이 끝나거나, 이전 업무 큐의 재실행·반복 평가 없이 운영에 반영한다. | 철학 렌즈의 필요한 탐구·진단·변경 후보가 이전 업무 큐의 재실행·기준 환경과의 비교 평가로 연결된다. 자동 또는 사람 개입으로 수정·재평가를 반복하며, 사람이 개선 결과를 최종 승인한 정확한 후보가 해당 업무 환경의 새 운영 버전이 된다(INT-018–019). 무검증 정답 누적·자동 운영 승격과 구분한다. |
| AC-006 | 화면과 테스트가 통과해도 새로고침 후 기존 업무 검토를 UI에서 이어갈 수 없다. | 저장된 업무·버전·진행 맥락을 다시 열어 안전하게 이어간다. 외부 동작 중복 실행은 방지한다. |
| AC-007 | 후기 피드백 기능을 만들 때부터 오류 로그만 모아 앞선 요청·설계 변경 맥락을 잃거나, 제작자 피드백 전송을 업무 개선·환경 버전업의 필수 마지막 단계로 강제한다. | 설치 직후부터 정한 범위의 사건을 연결해 남긴다. 추출·전달은 사용자가 원할 때 하는 독립 행위이며 이를 하지 않아도 업무 수행·반복 개선·환경 버전업을 완료한다(INT-020). 민감정보 처리·내보내기 범위는 별도 설계한다. |
| AC-008 | 기능 이름·메뉴·검증 문서는 존재하지만 비개발자가 환경 구성·운영·개선의 전체 흐름을 완수하지 못한다. | 대표 업무에서 사용자 가치가 끝까지 연결되는지 확인한다. 제한 범위의 단계적 구현과 전체 목표 완료를 구별한다. |
| AC-009 | 환경 구성은 사용자에게 남겨 두고 DeepTwin은 별도 검수 프로그램으로만 제공한다. | 프레임워크가 구성을 맡고 DeepTwin이 사용자 피드백의 정제·흡수를 담당하는 핵심 엔진으로 연결된다(INT-010–011 확인). 변경 대상과 적용 권한은 별도 확인한다. |
| AC-010 | 반복 평가에서 잘된 회차만 제시하거나, 반복 수정에 사용한 업무 큐 점수를 미관측 전이 성능으로 보고한다. | 회차·후보·입력·평가기·결과의 계보와 개선·악화·실패·측정 불가를 보존한다. 반복용 큐와 최종 확인 자료를 구별하고 승인 증거에 둘의 의미를 표시한다. 세부 지표·임계값은 후속 설계한다. |
| AC-011 | 과거 업무 큐의 평가용 재실행이 실제 발송·결제·외부 데이터 변경을 중복 수행하거나, 사람 승인 뒤 평가하지 않은 후보로 운영을 전환한다. | 평가 환경과 운영 환경을 분리하고 외부 부작용을 통제한다. 평가한 후보·승인한 후보·해당 업무의 새 운영 버전이 일치하며 재현 불가와 외부 권한 부족을 성공으로 표시하지 않는다. |
| AC-012 | 초기 설계의 철학 활용이 페르소나 문구나 이름만 다른 같은 구조 3개에 그치거나, 사용자 목적·필수 제약이 관점마다 달라진다. | 동일한 확인 업무 모델 아래 단독·하이브리드 미세렌즈 생성 규칙이 실제 역할·권한·그래프·기억·평가 등의 차이로 이어진다. 필수 제약과 품질을 통과한 후보 중 최소 두 구조 축의 차이를 갖춘 기본 3안을 선별한다. 적합한 후보 부족은 표시한다(INT-021–022). |
| AC-013 | 크리틱이 생성자의 렌즈 이름·조합·자기점수나 다른 크리틱의 결론을 보고 평가하거나, 병렬 실행만으로 독립성이 입증됐다고 주장한다. | 별도 크리틱이 해당 정보를 가린 채 공통 업무 모델과 후보를 개별 평가하고 명시적 근거·의견 불일치를 남긴다. 철학적 우열이 아닌 요구 충족·실행 설계 품질을 평가한다. 모델·평가 기준·점수식은 후속 명세한다(INT-022). |
| AC-014 | 설계 비교에 철학·렌즈·철학자 이름을 전면 노출하거나, 용어를 숨긴다는 이유로 실제 승인·위험·비용 차이도 설명하지 않는다. | 일반 설계 비교 UI는 업무 언어로 실제 선택 기준과 구조적 장단점을 제시한다. 내부 출처·조합은 감사 기록으로 보존하되 상세 감사 UI와 접근 권한은 별도 설계한다(INT-021·023). |
| AC-015 | 선택된 설계만 기록하여 다른 조합·탈락 후보·실패·평가·제시 순서를 확인할 수 없거나, 초기 생성 기록과 실제 업무 성과의 연결이 끊긴다. | 전체 후보와 업무 모델/입력·렌즈/조합/생성 설정·평가기/근거·선정/사용자 수정·실행/평가/환경 버전 계보를 연결한다. 비렌즈 생성과 같은 비용의 비교로 추가 효용을 검토한다. 선택된 안의 성과만으로 렌즈의 우월성을 단정하지 않는다(INT-023). |
| AC-016 | 초기 크리틱 고득점을 실측 개선으로 표시하거나, 사용자의 에피소드 철학 해석을 직접 운영 정책으로 바꾼다. | 초기 설계 탐색용 렌즈 정의와 피드백 SPLI의 H_phi/S_phi 경로를 구별한다. 초기 품질 점수는 예상치이며, 후속 업무 큐 반복 평가와 사람 최종 승인·환경 버전업을 대체하지 않는다(INT-018–019·021–023). |
| AC-017 | 작업공간·대화·그래프 중 하나만 제공하고 다른 두 가지는 제외하거나, 모드 제공을 이름만 붙인 장식 요소로 대체한다. | 세 가지를 실제 사용 가능한 화면 모드로 제공한다(INT-024). 같은 전체 제품 역량에 연결하되 모드별 기능 배치·조작 범위·동등성은 별도 설계한다. 작업공간 중심만 채택됐다고 해석하지 않는다. |
| AC-018 | 모드 전환으로 업무·버전·검토 맥락이나 작성 중인 내용을 잃고, 별도 실행·승인·환경 버전이 중복 생성되거나 권한 검사가 우회된다. | 같은 환경·업무·산출물·사용자 대안·탐구·실험·성장 이력과 권한을 공유한다는 관계는 사용자 후속 확인됨(INT-024). 전환 자체와 실제 변경/승인/실행을 구별하며, 모드별 행위와 관련 대상을 로그로 연결한다. 저장·충돌·전환 정책·기능 동등성의 구체 구현 승인은 아니다. |
| AC-019 | 제작 과정에서 개발자가 구독 도구를 사용한 것을 제품 지원으로 대체하거나, Claude·Codex 중 하나의 구독 실행을 제외하거나, 로그인만 지원하고 핵심 LLM 경로에 API 키를 필수로 요구한다. | 배포물을 새로 설치한 최종 사용자가 UI와 자신의 구독으로 설계·크리틱·실행·피드백·반복 평가를 수행하는 여정을 양쪽 각각 검증한다(INT-025, MUST). 제작자 전용 설정·인증에 의존하지 않으며 사용자 CLI 조작·API 키·두 구독 동시 보유를 필수로 두지 않는다. 공식 인증·실행 경로를 사용하고 한쪽 미지원·모의 응답·설치 성공만으로 완료라고 하지 않는다. |
| AC-020 | 구독 한도·인증 만료·실패 때 API로 자동 전환하거나, API 키가 설정되어 있다는 이유로 구독 선택과 다르게 과금 호출한다. | API 전환은 사용자가 대상·모델·과금 경로·적용 범위를 명시적으로 선택한 뒤 수행한다(INT-026). 전환 전에는 안전하게 보류/중단하고 상태를 알린다. 연결 오류·한도 도달과 이미 저장된 API 키가 있는 경우도 검사한다. |
| AC-021 | 화면에는 구독 실행으로 표시되지만 실제 경로가 API이거나, 모델/실행기/전환 이력을 잃고 인증 토큰·키를 로그에 저장한다. | 실제 제공자·실행기 버전·모델·구독/API 경로·전환 선택과 실행/평가/환경 버전이 연결되고 UI와 일치하는지 확인한다. 자격증명은 로그·내보내기에서 제외하며, 모델/경로 변경 시 기존 평가의 직접 비교 가능성과 승인 적용 범위를 확인한다. |
| AC-022 | 동일 모델 크리틱은 한계가 있다고 고지하는 것으로 종료하거나, 다른 모델·두 번째 구독을 필수로 요구하거나, 역할/문맥 분리·다수결·사람 승인을 판단 오류 독립성의 증명으로 표시한다. | INT-027의 독립성 요구를 별도 설계·검증 대상으로 유지한다. 생성자의 결론에 기대지 않는 기준·근거·검사 경로와 미관측/결함 사례 시험을 설계하며, 정보 격리·검사 범위 내 판정·측정된 공동 오류·보장되지 않은 영역을 구분한다. 모든 업무의 통계적 독립성 또는 그 대체 수용 기준이 승인·달성됐다고 미리 선언하지 않는다. 보장 계약은 사용자 검토 중이다. |
| AC-023 | 높은 크리틱 점수·평균·다수결로 근거 부족 또는 필수 검사 실패 항목을 자동 통과시키거나, 미검증 항목을 사람이 확인했다는 이유만으로 검사 성공으로 바꾼다. | 필수 조건과 근거 충분성은 점수 합산보다 먼저 적용한다(INT-028 확인). 부족·실패 상태와 근거를 보존하고 새 증거·수정·재검증 또는 권한자 판단의 종류를 구별한다. 구체 보완 루프·표시 문구·자동화 예산·위험 수용 권한은 후속 설계한다. |
