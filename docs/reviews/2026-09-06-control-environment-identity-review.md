# 관제 환경 정체성 재검토

날짜: 2026-09-06

상태: 사용자 제공 화면과 기존 근거의 재검토 결과. 새 UI 설계의 승인, 구현 계획, 제품 검증 통과를 뜻하지 않는다. 기존 시제품은 제품 정체성 검토 실패 상태로 보존한다.

## 1. 결론

제품의 중심 대상은 문서나 피드백 양식이 아니라 **사용자의 업무를 수행하는 멀티에이전트 환경**이다. 프레임워크는 이 환경의 설계·구성·실행·관제·LLMOps를 소유하고, DeepTwin은 실제 수행과 사용자 대안의 차이를 탐구·검증하여 그 환경을 성장시키는 핵심 엔진이다.

이번 지적은 그래프 탭과 PDF 뷰어의 추가 요청이 아니다. 초기 자료에도 있던 관계가 구체적인 화면·데이터·수용 기준으로 옮겨지는 과정에서 소실됐다는 교정이다. 참고 화면을 제공했으므로 영상 재생이나 Mac 잠금 해제를 재검토의 선행 조건으로 두지 않는다.

### 논문 기준선과 사용자 확장을 섞지 않는다

논문의 부트스트랩·실행 관찰·타입별 대안 비교·SPLI·개입 검증은 원문 근거다. 초기 설계 후보 생성에 단독/하이브리드 미세렌즈를 적용하고 별도 크리틱으로 선별하는 경로, 크리틱의 반례 탐색에 렌즈를 연결하는 경로는 사용자와 후속 확인한 제품 확장이다. 세 UI 모드, 양쪽 구독 지원, 프레임워크 자체 도구 소유도 사용자 요구다.

논문 §6.3의 첫 공개 참조 범위는 텍스트·제한 DOCX, 로컬 웹/CLI, 제한 그래프·단일 제공자다. 개발 도구 제안서 1·3쪽은 이 범위를 따르며 SPLI를 후반 선택 확장으로 배치한다. 이 연구용 최소 구현을 현재 제품의 전체 범위로 적용하면 후속 직접 요구와 충돌한다. 원문을 숨기거나 논문이 모든 형식의 편집기를 이미 명세했다고 주장해서도 안 된다.

현재 제품은 다형식 산출물을 다룰 계약과 경험을 가져야 한다. 어떤 형식부터 얼마나 풍부하게 미리보기·편집·부분 비교를 지원할지는 상세 설계 사항이며, 이 미결을 텍스트 전용 데이터 모델의 근거로 사용하지 않는다.

## 5. 구현 계획에서 어디가 축소됐는가

1. 통합 제품 기준선 §1–3은 환경·업무 한 건·산출물 전달·개선 실험·환경 버전을 연결했다. 클릭 시제품 계획은 목표를 읽을 수 있는 가상 본문, 범위 선택, 초안 편집, 세 모드 상태 연속성으로 좁혔고, Task 1에서 상태 연속성을 수용 경계로 선언했다.
2. 실제 `prototype/views.mjs`의 `roleGraph`는 V02에서만 선택 설계의 구조를 반영한다. 다른 장면에서는 고정 직렬 역할 그래프로 돌아간다. 그래프 선택은 역할 본문 열기에 연결되지만, 선택 환경의 단계 실행과 산출물 이력에는 연결되지 않는다.
3. 실제 상태 키는 업무/실행/역할/입력/산출물/텍스트 범위를 참조한다. 단계 실행·재시도·형식별 산출물을 별도 대상으로 두지 않아 같은 역할의 반복 실행과 여러 출력이 드러나는 사례를 검증할 수 없다.
4. 원본 전문·텍스트 보존·이스케이프·안전한 로컬 서버 검사는 유효하다. 하지만 그 통과는 위 제품 관계의 성립을 증명하지 않는다. “실제 엔진 미연결”이라는 정직한 고지도 실행 관계가 없는 예시 구조를 적절하게 만들지는 않는다.

이는 특정 스킬이 부족해서라는 결론이 아니다. **상위 의도와 다른 방향으로 좁힌 계획을 작성하고, 그 계획 안에서만 구현·검토를 완료한 실패**다. 문서끼리의 일관성 검사와 코드 검사가 동일한 누락을 공유할 수 있었다.

## 6. 다음 설계에서 유지할 연결 구조

아래는 근거에서 도출한 검토 기준이며, 새 레이아웃·스키마의 확정안이 아니다.

```text
업무 설명·자료 → 환경 후보 그래프 비교·선택 → 환경 버전
                                                 │
                                  업무 큐 → 개별 실행
                                                 │
                            단계/시도 → 입력·출력·도구·전달
                                                 │
                                     특정 산출물 전체/부분
                                                 │
                                          사용자 자기 대안
                                                 │
                         차이·경쟁 가설·렌즈 탐구·새 업무 증거
                                                 │
                                  검증할 환경 변경 후보
                                                 │
                 이전 업무 큐의 기준/후보 재실행 ↔ 수정·재평가
                                                 │
                      별도 최종 검증·사람 승인 → 새 환경 버전
```

이 도식은 대상·증거의 연결을 요약한 것이며, 필수 클릭 순서나 에이전트들의 직렬 실행 구조가 아니다. LLMOps는 전 과정에 연결된다. 부분 대안 이후에도 허용된 후보 시험·관찰·추가 대안의 반복이 가능하다.

- **설계 그래프 / 실행 그래프 / 기록 재생 / 변경 비교를 구별한다.** 서로 연결되지만 동일한 상태나 증거가 아니다. 기록 재생은 새 모델·도구 실행이 아니며, 과거 큐 재실행은 별도 실행이다. 외부 발송·게시·수정의 중복 부작용을 통제한다.
- **산출물은 별도 핵심 객체다.** 환경 버전·업무·실행·단계·시도·입출력 버전·소비자를 추적한다. 문서·표·이미지·PDF·코드·미디어 등은 형식에 맞게 열람하며, 지원 한계는 보이되 원본을 일반 텍스트로 대체하지 않는다. 모든 단계가 반드시 파일을 만들거나 출력이 하나뿐이라고 가정하지 않는다.
- **부분 대안은 변경 범위의 상한이 아니다.** 같은 업무·입력 상태의 대안을 일부 남긴 단계에서도 전체 검토나 모든 렌즈 질문의 완결을 기다리지 않고, 해당 시험에 필요한 근거·권한·안전 조건 안에서 후보 시험 → 결과 관찰 → 추가 대안을 반복할 수 있다. 원본 전체 문맥과 정확한 버전을 유지하고, 수정하지 않은 부분을 승인으로 취급하지 않는다. 작은 비교 증거에서 파생된 환경 변화가 다른 산출물·역할·업무에 미친 영향도 검사한다. 사람의 자연스러운 판단을 새 필수 버튼으로 문자화하지 않으며, 후보 시험과 최종 운영 승격의 검증은 구별한다.
- **LLMOps가 같은 실행을 다룬다.** 상태·실패·재시도·도구/모델 사용·비용·시간·평가 근거·사람 개입·재현 범위를 관련 실행과 연결한다. 보이지 않는 내부 사고를 로그로 제공한다고 약속하지 않는다.
- **철학 렌즈는 세 경로에 연결된다.** 초기 구조 후보 생성, 크리틱의 반례/판별 질문 탐색, 사용자 대안 이후의 심화 탐구다. 일반 UI는 업무 언어를 쓰되 모든 후보·탈락·렌즈/조합·평가·선정 이력은 감사 경로에서 찾을 수 있어야 한다. 이름을 숨기는 것과 엔진의 작동·근거를 숨기는 것은 다르다.
- **렌즈 해석은 운영 규칙 자체가 아니다.** 논문 §4.8.5에 따라 H_phi/S_phi를 개입·지식 후보의 직접 입력으로 삼지 않는다. 새 업무 증거로 갱신한 판단 가설에서 조건·행동·예외와 변경을 검증한다. 병렬·블라인드·렌즈 다양성만으로 크리틱 오류 독립성이 달성됐다고 판정하지 않는다.
- **세 UI 모드는 같은 환경을 다룬다.** 작업공간·대화·그래프를 유지하며, 모든 사람에게 노드를 수동으로 그리게 하거나 전체 기능을 거대한 한 화면에 펼치지 않는다. 구체 배치와 모드별 역할은 다음 설계에서 제시한다.
- **독립 제품과 기록 원칙은 유지한다.** 프레임워크가 화면·도구·상태·산출물·권한·평가를 소유한다. 최종 사용자의 Claude 또는 Codex 구독 실행을 모두 지원해야 한다는 요구와 명시적 API 선택을 유지하되 실제 지원 완료로 보고하지 않는다. 설치 직후 전 과정 기록, 비밀정보 제외, 선택적 로그 추출·제작자 전달은 전체 순환에 걸치며 버전업의 마지막 필수 단계가 아니다.

## 7. 수정할 수용 기준의 제안

| 검토 기준 | 화면·조작에서 확인할 증거 | 거부할 결과 |
| --- | --- | --- |
| 구조 비교 | 같은 업무의 후보들을 그래프로 비교하고 권한·조정·기억·평가 등 두 축 이상의 차이를 이해 | 설명 문구·이름·노드 수만 다른 카드 |
| 설계에서 운영까지의 연결 | 선택한 환경 버전의 역할·분기·도구·게이트가 이후 실행에 일관되게 연결 | 설계에서는 병렬인데 운영은 별개의 고정 직렬 예시 |
| 단계·시도·산출물 계보 | 같은 역할의 반복·재시도·병렬 합류, 텍스트가 아닌 산출물에서도 입력/출력 버전과 다음 소비자를 확인 | 역할당 본문 하나, 최신 결과만 열람, 모든 내용을 textarea로 대체 |
| 관제에서 성장까지의 연결 | 특정 산출물의 자기 대안부터 차이·가설·새 증거·변경 대상·이전 큐 비교·정확한 승인 버전까지 추적 | 별개의 진단 카드·회차 점수·지식 저장 화면 |
| 증거 종류 분리 | UI 정체성, 코드 동작, 실제 실행/엔진 효과를 각각 보고 | 테스트 개수나 문서 검토 PASS로 사용자 정체성 실패를 상쇄 |

이 기준은 UI 검토에 사용할 예시 데이터의 관계를 더 엄격하게 요구하는 것이지, 가상의 기획안으로 DeepTwin 효과 실험을 재개하자는 제안이 아니다. 표시용 예시는 끝까지 표시용이다. 실제 사용자의 대안 없이 사용자 피드백을 만들어내지 않는다.

## 8. 이번 작업의 범위와 다음 산출물

Superpowers brainstorming의 맥락 재검토로 돌아와 위 관계를 정리했고 PDF 스킬로 원문을 확인했다. 다음 설계 산출물은 기존 8개 페이지의 문구 수정이 아니라, **같은 환경을 설계·실행·산출물 열람·평가·성장에서 어떻게 이어서 다루는지 보여 주는 정보 구조와 연결된 화면안**이어야 한다. 구체 레이아웃은 아직 승인되지 않았다.

Spec Kit는 그 검토된 관계를 요구·작업·수용 시험으로 연결하는 데, Superpowers는 계획·구현·회귀 검토에, LangChain Skills는 승인된 실행 계약을 구현하는 방법 확인에 사용한다. 도구 사용 자체를 의도 일치의 증거로 삼지 않는다. 새 스킬·패키지 설치가 이번 실패의 해결책이라는 근거는 없다.

기존 시제품·입력·기록은 삭제하지 않는다. 텍스트 선택·보존 등 검증된 부품은 재사용 후보로 남기되, 기존 페이지 수와 역할-본문 모델을 새 설계의 고정 조건으로 삼지 않는다. 이번에는 새 UI·엔진·모델 호출·계정 연결·파일 삭제·커밋·병합·푸시를 수행하지 않았다.
