# DeepTwin 렌즈 기반 그래프 생성 상세 설계

작성일: 2026-09-07 · 문서 수준: 생성 엔진 핵심 계약 기준선 0.1

상태: 생성 아키텍처, 렌즈 정의의 작성·확장·버전 관리 원칙, 크리틱 이중 검증 구조, 후보 부족 시 선공개·한도 내 자동 보완, 이전 그래프 보존·명시적 재생성 방식 승인. DG-L01 문서 묶음의 개발 검토 후 사용자가 17개 후보·3개 사례를 DG-V01 검증 설계의 기준 자료로 쓰는 데 동의했다. 전체 코드 구현 명세 또는 구현 시작 승인이 아니며 미결 기술 계약은 9절의 후속 작업으로 분리한다.

## 1. 승인 기록과 범위

사용자는 다음 세 생성 방식을 비교한 뒤 첫 번째 방식의 채택 질문에 “응”이라고 답했다.

1. 렌즈별 설계 판단을 만들고 실제 그래프로 구체화한다. **채택.**
2. 렌즈마다 완성된 그래프를 직접 생성한다.
3. 공통 기본 그래프를 만든 뒤 렌즈별로 변형한다.

승인된 핵심은 출처 기반 미세렌즈 단독 또는 하이브리드가 설계 판단을 만들고, 그 판단이 실제 역할·전달·기억·권한·평가 구조로 이어지는 것이다. 미리 만든 세 그래프에 이름이나 설명만 붙이는 방식은 아니다. 나머지 두 방식은 이번 기본 경로로 채택하지 않았으며 영구 금지한 것은 아니다.

이후 “업무별 선택·조합은 유연하게 하되 렌즈 정의 자체의 추가·변경은 별도 검토와 버전 배포를 거치도록 할까요?”라는 질문에 사용자가 “응”이라고 답했다. 개발 단계에서 출처 기반 렌즈를 작성하고 검토 상태를 구별하며, 업무별 선택·조합, 새 정의의 별도 검토·배포, 과거 버전 보존을 적용한다. 구체 최초 목록·정량 합격 기준·조합 알고리즘까지 승인된 것은 아니다.

이어 “후보를 검토하는 크리틱도 먼저 검증받아야 하는 이중 검증 구조”의 채택 질문에 사용자가 “응”이라고 답했다. 구조·권한 검사, 원자료 대조, 렌즈 반례 탐색과 별도 판정의 책임 분리, 프레임워크의 접근 제한, 크리틱 구성의 자격 검사, 필수 결함을 놓친 구성의 해당 항목 자동 통과 금지와 변경 후 재검사를 채택했다. 구체 시험셋·정량 임계값·후보 선별 및 보완 한도까지 확정하거나 판단 오류 독립성을 달성했다고 선언한 것은 아니다.

다음으로 “통과한 안은 먼저 보여 주고, 부족한 안은 정해진 한도 안에서 자동 보완하는 방식”의 채택 질문에 사용자가 “응”이라고 답했다. 후보 부족을 숨기지 않고 통과 후보의 그래프를 먼저 표시하며, 실패 이유에 따른 내부 보완·재검토, 목적·필수 조건·권한·합격 기준 유지, 한도·진전 없음·설계 확정 시 중단을 채택했다. 이 승인은 제품의 동작 방식이며, 구체 한도 수치나 현재 개발 환경에서 실제 모델 호출을 시작할 권한은 아니다.

이후 “이전 그래프는 비교용으로 유지하고 새 조건의 생성은 사용자의 명시적 요청으로 시작하는 방식”의 채택 질문에 사용자가 “응”이라고 답했다. 입력·생성 모델 설정 변경 뒤 이전 그래프 보존·조건 구분, 새 조건 생성의 명시 요청, 후보 안 개별 에이전트 모델 변경의 새 버전·재검토, 새로고침·재접속 중복 생성 방지와 중단 뒤 늦은 응답의 현재 결과 덮어쓰기 방지를 채택했다. 화면 배치나 새로운 버튼 목록을 확정한 것은 아니다.

통합 설계서를 자체 검토와 두 독립 검토로 확인한 뒤, “이 설계서를 확인한 뒤 첫 번째 ‘렌즈 정의·조합 규칙’ 작업 계획으로 넘어가도 될까요?”라는 질문에 사용자가 “응”이라고 답했다. 이는 작성된 핵심 계약 기준선의 검토 완료와 계획 작성으로의 이행이다. [DG-L01 작업 계획](../plans/2026-09-07-deeptwin-lens-definition-contract.md)의 작성·실행과 운영 코드 구현은 서로 구별한다.

이 문서는 [통합 제품 설계 기준선](2026-09-06-deeptwin-integrated-product-design.md)의 하위 설계다. 원문 PDF는 `<owner-provided reference PDF, not in the repository>`이며, 관련 근거는 4.2–4.4절, 4.8절, 6.4절이다. 논문의 서술·예시, 사용자 확정 요구, 이 문서의 신규 제안을 구분한다.

## 2. 이번 기능의 경계

현재 연결된 실제 업무 이해 결과와 원자료에서 출발해, 사용자가 비교할 환경 설계 후보를 만드는 기능이다. 전체 흐름은 다음과 같다.

확인된 공통 업무 기준 → 렌즈별 설계 판단 → 구조화된 그래프 후보 → 별도 검토 → 기본 3안 제시.

- 업무 설명·업로드·이해 수정은 초기 요구 입력이다. 사용자 대안 산출물, 판단 학습, 환경 개선 효과로 재분류하지 않는다.
- 설계 후보는 아직 실행되지 않은 계획이다. 노드·연결이 있다고 실제 전달·도구 사용·산출물 생성이 일어났다고 표시하지 않는다.
- 설계 선택, 외부 행동 권한, 개선 환경의 운영 승격은 다른 효력이다. 이번 선택으로 다른 권한을 부여하지 않는다.
- 이후 사용자 대안으로부터 차이를 탐구하고, 이전 업무 큐를 재실행·평가하고, 사람이 최종 승인해 환경을 버전업하는 루프는 유지한다. 이번 생성 기능으로 대체하지 않는다.
- 기존 MANUAL-001은 비교 전에 종료된 미검증 시도다. 당시 임시 렌즈와 예시를 승인된 레지스트리 또는 평가 통과 자료로 사용하지 않는다.

## 3. 승인된 생성 경로

### 3.1 공통 업무 기준을 먼저 고정한다

목적, 원자료, 산출물과 완료 조건, 권한, 필수 제약을 후보 생성 전에 정리한다. 모든 후보는 같은 업무를 수행한다. 주요 불확실성은 근거 있는 사실과 구별하고, 설계나 위험을 실질적으로 바꾸는 미확정 조건만 사용자에게 확인한다.

기존 업무 이해 결과도 원자료와 대조한다. 인용이 원문에 존재한다는 검사만으로 해당 해석이 옳거나 실행 요건이 완전하다고 선언하지 않는다. 공통 업무 기준의 오해를 여러 후보가 공유하는 위험을 별도로 다룬다.

### 3.2 렌즈가 설계 판단을 만든다

미세렌즈는 철학자 페르소나가 아니라 출처에 근거한 탐구 규칙이다. 어떤 검증이 필요한지, 누가 어떤 산출물을 받아야 하는지, 어디에 기억·권한·승인 경계를 둘지에 실질적인 차이를 만든다.

하이브리드는 여러 설명을 평균내는 것이 아니다. 각 구성 렌즈가 어떤 판단을 맡았는지, 충돌이 무엇이고 어떻게 처리됐는지 추적한다. 렌즈 하나가 에이전트 하나나 그래프 하나에 반드시 대응하는 구조로 고정하지 않는다.

논문 4.8절은 주로 확인된 전문가 판단 가설을 탐구하는 SPLI를 설명한다. 이를 최초 환경 설계의 후보 생성으로 연결하는 것은 사용자와 합의한 제품 확장이다. 최초 업무 설명에서 전문가 판단 가설이나 개인의 철학적 성향을 만들어 내지 않는다.

### 3.3 판단을 실제 그래프 구조로 구체화한다

각 후보는 역할의 책임·입력·출력, 에이전트 간 산출물 전달, 흐름과 검토 위치, 기억, 자료·도구 접근과 권한을 표현한다. 문서·이미지·PDF 등 업무에 필요한 산출물 형식을 일반 텍스트로 축소하지 않는다.

브라우저 등 외부 도구와 역할별 모델 설정도 설계 구조에 연결한다. 이는 프레임워크가 소유할 실행·도구 책임을 나타내며, 특정 구독 도구가 제품 전체를 대신 실행한다는 뜻이 아니다. 모델·도구의 실제 이용 가능성과 연결 요구를 구별한다.

어떤 렌즈 기반 판단이 어떤 그래프 요소에 반영됐는지 확인할 수 있어야 한다. 중간 표현이 역할·연결·산출물의 다양한 구조를 고정 템플릿으로 제한하지 않도록 설계한다.

### 3.4 별도 크리틱이 개별 평가한다

후보 생성 전에 공통 평가 기준을 마련한다. 크리틱은 생성자의 렌즈 이름·자기평가와 다른 크리틱의 결론을 보지 않고, 후보별로 원자료와 평가 기준을 사용해 별도·병렬 평가한다. 형식 검사와 반례 검사를 병행한다.

필수 조건 실패는 평균 점수로 상쇄하지 않는다. 같은 모델을 써도 공통 오류를 줄이고 발견하는 설계를 필수 과제로 다룬다. 판단 오류 독립성의 보장 범위와 수용 시험은 미결 핵심 요구로 유지하며, 오류 감소만으로 이를 대체하거나 완료 판정하지 않는다. 다만 독립 호출·역할·정보 격리만으로 모든 업무에서 판단 오류의 통계적 독립성을 입증했다고 주장하지 않는다. 이중 검증의 책임과 자격 검사 원칙은 6절에서 확정했고, 구체 시험셋·정량 통과 기준은 후속 상세 설계 대상이다.

### 3.5 품질과 구조적 다양성을 함께 보고 제시한다

필수 조건을 통과한 후보 중 품질과 구조적 다양성을 함께 검토해 기본 3안을 제시한다. 최소 두 구조 축에서 차이가 나야 하며, 철학자 이름·에이전트 이름·인원수·배치만 달라서는 충분하지 않다.

적합한 후보가 부족하면 부족함을 표시한다. 세 안을 채우려고 부적합하거나 동등한 후보를 포함하지 않는다. 내부 생성 후보 수, 재생성 한도, 구체 점수·정렬 규칙은 이 승인으로 정하지 않았다.

후보 부족 시 통과한 안을 먼저 표시하고 한도 안에서 자동 보완하는 동작은 7절을 따른다. 통과 후보의 선공개는 아직 검토되지 않은 그래프를 합격 후보처럼 표시하는 것이 아니다.

일반 사용자에게는 멀티에이전트 그래프와 실무적인 차이를 보여 준다. 철학·렌즈·철학자 이름을 기본 비교 화면에서 노출하지 않는다. 사용자가 원할 때 권한 있는 감사 경로로 출처와 조합을 확인할 수 있게 한다.

## 4. 기록과 검증의 정직성

선정 후보뿐 아니라 렌즈 정의·출처·버전·조합, 설계 판단, 전체 후보, 검토 근거, 탈락·선정 이유를 추적한다. 숨은 사고과정·인증 비밀을 수집한다는 뜻이 아니다. 세부 저장·보존·내보내기 형식과 권한은 별도 계약으로 확정한다.

생성 당시의 예상 성능·비용과 실제 실행 후의 측정 결과를 구별한다. 후보의 변경 전 검토 결과를 변경 후 후보의 합격으로 자동 승계하지 않는다. 그래프 생성 성공이나 화면 검사를 렌즈 효용·크리틱 독립성·DeepTwin 학습 효과의 증명으로 사용하지 않는다.

## 5. 승인된 렌즈 라이브러리 운영 원칙

### 5.1 정의를 개발 단계에서 준비한다

원전과 논문을 대조해 실제 탐구 규칙으로 작성한다. 철학자 이름을 넣은 한 줄 역할 프롬프트로 대체하지 않는다. 정의에는 출처·버전·핵심 주장·판별 질문·반대 예측·혼동 요인·금지 추론을 연결한다.

출처 검토, 작동 검사, 실제 업무 효과 검증은 서로 다른 상태와 이력을 갖는다. 수행하지 않은 전문가 검토를 완료라고 표시하지 않으며, 출처의 충실성을 행동 예측의 타당성으로 바꾸지 않는다. 논문은 최초 파일럿을 판별 가능한 소수로 시작할 것을 제시하지만, 제품의 초기 규모와 첫 목록은 아직 확정하지 않았다. 소수로 시작하더라도 전통 전체를 포괄한다고 주장하지 않는다.

### 5.2 업무별 선택·조합은 유연하게 한다

업무의 목적과 상황에 맞게 사용 가능한 정의를 선택하고 조합한다. 어떤 렌즈가 어느 설계 판단에 기여했는지 남기며, 한 철학자와 한 에이전트를 고정 대응시키지 않는다. 맞는 렌즈가 없으면 임의 분류하지 않고 미확정을 유지한다.

초기 목록을 영구적인 폐쇄 목록으로 만들지 않는다. 기존 정의를 이용한 업무 환경의 일상적인 탐구·개선이 매번 렌즈 라이브러리 업데이트를 기다려야 하는 것도 아니다. 라이브러리 개정과 업무 환경의 변경·검증·사람 승격은 다른 경로다.

### 5.3 새 정의는 별도 검토와 버전 배포를 거친다

업무 중 부족한 관점을 발견하면 새 렌즈를 제안할 수 있다. 다만 실행 중인 LLM이 새 정의를 즉석에서 공식 사용 가능한 렌즈로 승격하지 않는다. 제작자·기여자의 별도 검토와 버전 배포 경로를 거친다. 누구의 어떤 검토로 어떤 용도에 사용할 수 있게 됐는지 기록한다.

이는 구체적인 전문가 인력·배포 채널·검토 도구가 확보됐다는 선언이 아니다. 검토 역할과 세부 채택 기준은 후속 구현 명세에 명시하며, 없는 검토 결과를 생성하지 않는다.

### 5.4 당시 버전과 결과를 보존한다

과거 후보·검토 기록은 당시 사용한 렌즈 정의와 조합 버전을 참조한다. 새 정의로 재검토해도 과거 기록을 덮어쓰지 않으며, 어떤 다른 렌즈·하이브리드 구성이 어떤 결과를 냈는지 비교할 수 있게 한다. 정의 배포만으로 기존 업무 환경이 검증·승격됐다고 처리하지 않는다.

## 6. 승인된 크리틱 이중 검증 구조

### 6.1 검사 책임을 세 경로로 나눈다

| 경로 | 책임 |
| --- | --- |
| 구조·권한 검사 | 산출물 전달 누락, 입출력 형식 불일치, 승인 우회 등 명세로 판정 가능한 항목을 코드로 검사한다. |
| 원자료 대조 | 생성자의 요약을 그대로 정답으로 삼지 않고, 원자료의 요구·예외가 설계에 반영됐는지 확인한다. 인용의 존재와 주장을 뒷받침하는 의미를 구별한다. |
| 렌즈 기반 반례 탐색 | 숨은 전제·책임·예외를 드러낼 시험 상황을 제안한다. 별도 판정 경로가 반례의 타당성과 후보의 대응을 검토한다. 반례 생성자가 자신의 제안을 정답이나 실제 발생 사실로 확정하지 않는다. |

이는 서로 다른 모델 세 개를 의무화하거나 정확히 세 에이전트로 고정하는 계약이 아니다. 단일 구독·동일 모델 사용 조건에서도 책임과 입력을 분리한다. 각 검토는 계획의 구조·근거에 대한 검사이며, 실제 실행 전 업무 성능·산출물 품질·도구 동작까지 검증했다고 표시하지 않는다.

### 6.2 프레임워크가 정보 접근을 제한한다

프롬프트에 보지 말라고 쓰는 것에 그치지 않고, 프레임워크가 전달 자료와 접근 가능한 저장소를 제한한다. 3.4절의 생성자 렌즈 정체성·자기평가·타 크리틱 결론 차단을 실제 접근 경계로 구현한다.

업무 검토에 필요한 원자료와 후보의 기능 정보는 제공한다. 생성자에 대한 평가 유도 정보의 차단을 후보의 실제 모델·도구·권한 구성까지 숨기라는 뜻으로 해석하지 않는다.

### 6.3 크리틱 구성도 자격 검사를 통과해야 한다

실제 엔진을 구현한 뒤 별도로 준비한 검사 자료로 다음을 확인한다. 현재 사용자 자료에 결함을 삽입하거나 사용자에게 수동 리허설을 다시 요구하는 작업이 아니다.

- 필수 산출물 전달 또는 사람 승인 경로를 제거한 후보를 찾아내는가?
- 인용은 존재하지만 해당 주장을 뒷받침하지 않는 경우를 구별하는가?
- 생성자와 크리틱이 동일한 원문의 예외를 함께 놓치는가?
- 정상 설계나 복수의 타당한 설계를 무조건 탈락시키지 않는가?

필수 결함을 놓친 구성은 수정·재검증 전까지 해당 항목의 자동 통과 판정에 사용하지 않는다. 다른 크리틱의 고득점·다수결·사람의 위험 수용을 검사 성공으로 대체하지 않는다. 무관한 업무 전체를 영구 중단하는 것으로 확대하지도 않는다.

모델·검사기 구성이 바뀌면 관련 검사도 다시 수행한다. 변경 전 구성의 검사 결과를 변경 후 구성의 자격으로 자동 상속하지 않는다. 구체적인 구성 식별, 시험 자료, 허용 오거절·공동 실패와 비용 기준은 아직 확정하지 않았다.

### 6.4 강제할 조건과 측정할 성능을 구분한다

정보 격리와 필수 실패 차단은 구현으로 강제한다. 결정적 검사의 보장은 해당 입력 명세와 검사기의 정확성 범위 안에서 다룬다. 의미 판단의 오류·공동 실패는 별도로 측정한다. 자격 검사를 통과했다는 사실을 모든 업무에서 판단 오류의 통계적 독립성이 증명됐다는 주장으로 바꾸지 않는다.

이 검증은 프레임워크 내부 책임이다. 사용자에게 내부 단계마다 새로운 승인 버튼이나 크리틱 시험 수행 의무를 추가하지 않는다. 이번 승인은 구조의 채택이며 실제 자격 검사·효과 검증 완료가 아니다.

## 7. 승인된 후보 부족 처리와 자동 보완

### 7.1 통과한 후보를 먼저 보여 준다

적합하고 구조적으로 구별되는 후보가 기본 개수에 미달해도, 이미 통과한 후보와 현재 부족 상태를 보존·표시한다. 두 안만 통과했다면 실제 그래프 두 개와 추가 구조 검토 상태를 보여 준다. 아직 생성·검토하지 않은 후보로 빈자리를 채우지 않는다.

3절의 원자료·공통 업무 기준과 6절의 검사 자격·필수 조건을 충족한 범위에서만 통과로 표시한다. 초기 설계의 통과를 실제 업무 수행 성공이나 DeepTwin 학습 완료로 표시하지 않는다.

### 7.2 실패 이유에 맞춰 내부적으로 보완한다

전달 누락이면 관련 구조를 수정하고, 후보들이 너무 비슷하면 다른 렌즈·하이브리드 구성으로 탐색한다. 수정한 후보는 다시 검토하며 이전 버전의 합격을 자동 상속하지 않는다. 같은 내용을 이름만 바꿔 다시 제시하는 것을 새 구조 탐색으로 세지 않는다.

업무 목적·필수 조건·권한·합격 기준은 보완 중에도 유지한다. 이를 바꾸지 않고는 해결할 수 없다면 그 실질적인 선택을 사용자에게 묻는다. 내부 수정마다 승인을 요구하지 않는다. 크리틱 구성의 자격 미달을 다른 후보의 높은 점수나 요구 완화로 우회하지 않는다.

### 7.3 한도와 중단을 집행한다

정해진 탐색 한도 또는 진전 없음에 도달하면 자동 보완을 멈추고, 통과 후보와 부족 이유를 남긴다. 무제한 호출이나 세 안을 채울 때까지의 무한 반복을 허용하지 않는다. 사용할 시간·사용량·반복 한도의 구체 값과 진전 없음의 판정 조건은 아직 확정하지 않았다.

사용자가 설계를 확정하면 해당 버전을 고정하고 추가 탐색을 중단한다. 설계 확정이 실제 업무 실행이나 새로운 외부 행동 권한을 자동 허가하지는 않는다.

### 7.4 초기 설계 보완과 성장 루프를 구별한다

이번 보완의 입력은 업무 요구, 설계 후보와 검토 결과다. 이를 사용자의 대안 산출물이나 판단 학습 증거로 기록하지 않는다. 실제 수행 이후 대안에서 출발하는 차이 탐구·이전 업무 큐 재평가·사람의 환경 승격 루프를 대체하지 않는다.

## 8. 승인된 버전·재생성·화면 연결 원칙

### 8.1 이전 그래프를 비교용으로 보존한다

업무 설명·자료·생성 모델 설정을 바꾸더라도 이전 조건의 그래프와 검토 기록을 덮어쓰지 않는다. 이전 조건의 설계임을 분명히 표시하고 비교용으로 남긴다. 그 결과를 새 조건의 검토 완료 결과로 표시하거나 승인에 재사용하지 않는다.

### 8.2 새 조건의 생성은 명시적 요청으로 시작한다

입력 저장이나 생성 모델 설정 변경만으로 새 조건의 모델 호출을 시작하지 않는다. 사용자가 새 조건으로 만들어 달라고 요청하면 해당 조건을 고정한 새 버전의 생성을 시작한다. 대화로도 요청할 수 있으며 별도 복잡한 절차나 사용자 CLI 조작을 요구하지 않는다.

여기서 명시적 요청이 필요한 것은 최초 생성 또는 변경된 조건의 새 생성 묶음이다. 이미 시작한 같은 조건의 생성 묶음 안에서 7절에 따라 허용된 내부 보완까지 매번 다시 요청하라는 뜻은 아니다. 입력·모델 설정 변경을 기존 묶음의 숨은 조건 변경으로 끼워 넣지 않는다.

### 8.3 후보 안의 에이전트 모델 변경을 구별한다

설계를 생성·검토하는 모델 설정과, 후보 그래프 안의 각 업무 에이전트에 배정할 모델 설정을 구별한다. 후자를 바꾸는 것은 후보 수정으로 다루며, 기존 후보를 덮어쓰지 않고 새 버전으로 만들고 변경에 필요한 검토를 다시 수행한다. 진행 중인 호출은 시작 당시의 설정을 보존하며, 새 설정을 과거 기록이나 다른 에이전트에 조용히 적용하지 않는다.

그래프 버전에는 토폴로지뿐 아니라 역할별 모델 설정, 다중형식 입출력 계약, 프레임워크 소유 도구·자료 접근·권한이 연결돼야 한다. 이러한 기능을 특정 구독 실행기가 제품 전체를 대신하는 구조나 사용자 어댑터 제작 의무로 바꾸지 않는다.

### 8.4 재접속과 늦은 응답은 기록된 요청 상태를 따른다

새로고침·재접속은 저장된 상태와 결과를 복구하며, 그것만으로 중복 생성하지 않는다. 중단된 요청의 늦은 응답이나 이전 조건의 결과가 현재 조건의 결과를 덮어쓰지 못하게 한다. 서버 재시작 후 진행 중이던 호출의 상태가 불명확한 경우 자동 재전송하지 않는 기존 업무 이해 기능의 경계를 유지한다.

중단 상태의 저장과 원격 제공자의 중단 완료는 구별한다. 로컬 결과 적용을 막았다고 원격 실행이나 구독 사용량이 즉시 중단됐다고 보장하지 않는다. 명시적 재개가 필요한 상황과 계속 살아 있는 작업에 화면만 다시 연결하는 상황을 후속 연결 명세에서 구분한다.

현재 업무 이해 기능의 근거는 [업무 이해 계약](../../ui/2026-09-07-work-understanding.md)과 [모델·음성 요구 및 계약](../../ui/2026-09-07-model-control-and-voice.md)이다. 이 원칙을 그래프 생성에 상속할 것이며, 이미 그래프 엔진까지 구현됐다는 뜻은 아니다.

## 9. 후속 작업의 범위와 진입 조건

이 문서는 구현자가 빈칸을 임의 기본값으로 채울 수 있는 전체 플랫폼 구현 명세가 아니다. 작성된 핵심 계약 기준선을 검토한 뒤, `writing-plans`에서는 먼저 아래 DG-L01처럼 경계가 분명한 작업의 계획을 만든다. 이 표는 작업 묶음과 의존성이지, 별도의 파일별 구현 작업 목록이나 구현 착수 승인 기록은 아니다.

| DG-L01 · 렌즈 정의와 조합 계약 | 최초 정의 후보별 원전 위치·버전·원자적 주장·판별/반대 예측·금지 추론·허용 용도·검토 상태, 적용/기권 조건, 선택·조합·충돌 규칙과 커버리지 공백 | 정의와 검토 역할·채택 검사·사용 가능 상태를 검토한다. 예시 렌즈나 MANUAL-001을 임시 운영 기본값으로 넣지 않는다. |
| DG-V01 · 검증·선별·보완 계약 | 검사 항목별 판정 책임·근거, 크리틱 구성 식별과 자격 시험 자료, 실패·미확정 처리, 품질·구조적 다양성 비교, 시간·사용량·반복 한도와 진전 없음 판정 | 구체 보장 범위·정량 수용 기준·선별 규칙을 코드 상수나 시험 기대값보다 먼저 정한다. 한도·중단 계약 검토 전에는 실제 자동 반복 호출을 활성화하지 않는다. |
| DG-C01 · 생성과 화면 연결 계약 | 입력→설계 판단→후보→검토→확정의 버전 연결, 산출물·노드·전달 계약, 모델·도구 이용 가능성, 저장·중단·재접속·오류·늦은 응답의 처리, 실제 그래프 비교 화면의 수용 시험 | 사용 가능한 렌즈와 검토 계약을 참조한다. 저장 실패·중복·취소·재시작 경계를 검사하며, 검증되지 않은 경로를 운영 가능 또는 검토 통과로 표시하지 않는다. |

각 작업에서 기존 승인 원칙을 반복 질문하지 않는다. 원전 해석·효과 근거·비용·권한·사용자 경험을 실질적으로 바꾸는 선택은 추천안과 근거를 제시해 검토한다. 단순 파일 분리나 내부 자료구조 같은 구현 판단과 이런 제품 선택을 구별한다.

### DG-L01 문서 작업의 실제 결과 — 2026-09-07

[검토 보고서와 사용자 확인 범위](../../lenses/review-report.md)에 [출처 지도](../../lenses/source-map.md), [원자적 정의 후보](../../lenses/definition-candidates.md), [선택·조합 계약](../../lenses/composition-contract.md), [LC-01–12 문서 검토](../../lenses/review-cases.md)를 연결했다. 원전 13항목의 실제 실독 범위에서 정의 후보17개와 조합 사례3개를 준비했으며 개발 내용·명세·품질 검토의 지적과 수정 범위를 보고서에 남겼다.

P035의 미실독 검사 절, 지정 현대 번역·판본 대조 한계와 미사용 주장은 보류 상태다. 학술 검토·실제 효과·크리틱 자격 시험·운영 사용은 미완료다. 2026-09-07 구체 결과를 제시한 뒤 사용자가 “응”으로 동의한 범위는 이 묶음을 DG-V01 설계 기준 자료로 쓰는 것이다. 기존 계획 실행 승인을 정의 목록·운영 용도의 채택으로 재사용하지 않는다. 이 문서 작업을 제품 사용자의 대안 산출물·판단 학습으로 취급하지 않는다.

사용자 묶음 검토를 마쳐 DG-V01에는 정의/버전·질문·반대 예측·미해결 비교와 검사 요구를, DG-C01에는 입력·조합·원형 산출물·모델/도구/권한·기록 및 접근 경계를 넘긴다. 준비된 문서를 운영 기본값으로 넣거나 실제 호출·새 UI 단계를 활성화한 것은 아니다.

후속 [DG-V01 검증·선별·보완 초안](2026-09-07-deeptwin-verification-selection-design.md)을 작성했고, 사용자는 이를 기준으로 첫 시험의 엔진 연결·구현 계획을 작성하는 데 동의했다. 첫 구체 시험과 재사용 평가 지식은 초안에 연결했다. [첫 크리틱 연결 계획](../plans/2026-09-07-deeptwin-critic-transport.md)은 A 원시 전송·지시 분리, B 자료/판정기/기록 실행기, C 실모델 시험으로 나눈다. 계획 제시 후 별도 사용자 동의로 A 코드와 오프라인 회귀를 준비했다. 원시 전송 경로는 생겼지만 실제 후보 생성·의미 크리틱·선별·업무 실행 엔진은 연결하지 않았으며 `design_generation=false`, `execution=false`를 유지한다. B/C와 정량 자격·실행 예산·정렬 규칙도 여전히 확정/구현 전이다.

입력 revision, 렌즈 정의·조합, 설계 판단, 그래프 버전, 검토·탈락, 사용자 선택은 서로 연결돼야 한다. 전 과정 기록은 상세 원문·인증 비밀을 무조건 수집하거나 외부로 자동 전달하는 권한이 아니다. 배포 후 프레임워크가 관측 가능한 첫 제어 사건부터의 기록과 선택적 제작자 전달 요구는 상위 기준선을 유지하고, 저장·보존·가림·내보내기 세부 정책을 별도로 명시한다.

### 확인할 완료 근거를 분리한다

- **문서의 일관성:** 승인 범위·책임·버전·예외가 서로 충돌하지 않는가?
