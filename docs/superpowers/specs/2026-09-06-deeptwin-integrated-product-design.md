# DeepTwin 통합 제품 설계 기준선

작성일: 2026-09-06 · 버전: 기준선 0.1

상태: 사용자가 전체 제품 구조를 다음 상세 설계의 기준선으로 채택했다. Superpowers B6의 설계 문서이며 정리된 문서에 대한 B8 최종 검토는 대기 중이다. 승인 완료된 상세 구현 명세·구현 계획·작동 제품은 아니다. MANUAL-001은 비교 전에 종료했고 이 문서는 그 시도를 재개하지 않는다.

### 채택 기록과 승인 범위

2026-09-06에 “이 통합안을, 의도한 제품 구조를 보존하는 다음 상세 설계의 기준선으로 삼아도 될까요?”라는 질문에 사용자가 “응”이라고 답했다.

- **채택된 기준:** 제품 정의, 설계·운영·대안·성장 전체 흐름, 세 모드의 공통 맥락, 렌즈의 세 적용 경로, 부분 증거와 전체 영향, 기록·평가·사람 승격의 책임 경계, 후속 상세 설계의 방향.
- **유지되는 미결:** 9절의 지원 범위·구체 UI·렌즈/크리틱 계약·실험 정책·기록/배포 권리. 같은 모델 크리틱의 독립성과 두 구독 연결의 실제 기술 적합성은 달성됐다고 선언하지 않는다.
- **이번 응답에 포함되지 않은 권한:** 새 UI/제품 코드 구현, 개인 계정 조작·실험, 수동 리허설 재시도, 외부 게시·푸시. 문서 정리와 해당 설계 문서의 로컬 버전 기록만 수행한다.

이 문서는 여러 하위 기능의 방향을 유지하는 상위 기준선이다. 전체 플랫폼을 한 번에 구현하는 작업 명세로 사용하지 않는다. 후속 계획은 먼저 초기 화면의 정보 구조·이동 흐름 등 범위가 정해진 작업으로 나누고, 구체 제품 선택은 관련 상세 설계에서 검토한다.

## 1. 제품을 한 문장으로 정의한다

비개발자가 자신의 업무를 설명하거나 자료를 제공하면 프레임워크가 실제로 운영할 수 있는 에이전트 환경을 설계·구성하고, 사용자가 역할별 산출물에 자신의 전체 또는 부분 대안을 남기면 DeepTwin이 두 수행의 차이를 탐구하여 작동 변경을 시험하며, 이전 업무 큐의 반복 평가와 사람의 최종 승인을 거쳐 그 업무 환경을 성장시키는 오픈소스 프레임워크다.

프레임워크는 환경을 만들어 운영하는 제품 전체다. DeepTwin은 사용자 대안에서 출발한 차이 탐구·정제·검증·흡수를 담당하는 핵심 엔진이다. 철학 렌즈는 초기 환경 설계, 크리틱의 탐색, 실제 판단 차이의 심화 탐구에 연결한다. 설치 직후부터의 기록과 선택적 제작자 전달은 전체 과정에 걸친 별도의 성장 기반이다.

### 근거와 문서 우선순위

- **사용자 확인:** [제품 의도 기준표](../../product-intent.md)의 INT-001–033 및 직접 수정·후속 확인. 후속 직접 정정은 그보다 앞선 예시·개발 제안을 대체한다.
- **논문 근거:** `DeepTwin_OpenSource_Reference_Paper_KO.pdf`의 4.2–4.10절(16–30쪽), 5.4–5.5절(36–37쪽), 6.1–6.5절(37–41쪽). 논문은 설계 근거이며 효과가 입증됐다는 증거가 아니다.
- **통합 기준:** 아래 사용자 경험의 묶음과 논리적 책임 경계는 다음 상세 설계의 기준으로 채택됐다. 실제 화면 배치·물리 배포·파일별 구현 순서와 새 상세 정책까지 확정한 것은 아니다.
- **미결:** 9절에 모아 둔다. 미결을 관행·패키지 기본값·논문 예시로 조용히 확정하지 않는다.

논문 6.3절의 최초 참조 구현 예시에는 CLI·단일 제공자·제한된 그래프가 있다. 이것을 사용자 요구보다 우선해 최종 사용자 CLI, 한쪽 구독만 지원, 단순 직렬 에이전트만 제공하는 제품으로 축소하지 않는다. 초기 설계의 렌즈 단독/하이브리드 생성·크리틱 선별은 사용자 확인된 확장이며, 논문에 이미 완성된 알고리즘이 있는 것처럼 표현하지 않는다. 세 UI 모드와 두 구독 경로 역시 직접 사용자 요구다.

## 2. 사용자가 실제로 다루는 것

사용자에게 핵심이 되는 대상은 논문 용어가 아니라 다음 다섯 가지다.

1. **업무 환경:** 특정 반복 업무를 맡은 역할, 연결, 자료·도구 권한, 기억, 평가와 사람 개입 규칙.
2. **업무 한 건:** 그 환경에서 처리한 입력, 진행 상태, 역할별 산출물과 전달 관계.
3. **나의 대안:** 같은 역할·업무 상태에서 내가 만든 산출물 전체 또는 일부. 원본을 본 대안인지, 독립 수행인지도 구별한다.
4. **개선 실험:** 어떤 작동을 바꿨고, 원래 업무와 관련 과거 업무에서 무엇이 달라졌는지 보여 주는 비교.
5. **환경 버전:** 실제 평가와 사람 승인을 거쳐 운영에 반영한 정확한 구성. 프로그램 자체의 릴리스 버전과 다르다.

역할별 산출물은 초안 전체·조사보고서·크리틱 검토문처럼 다음 역할이 업무 입력으로 사용하는 완결된 결과다. 전체 업무에서는 중간 산출물일 수 있다. 피드백을 문구 수준까지 받을 수 있다는 요구는 이 산출물과 앞뒤 맥락도 짧은 의견 메시지로 줄이라는 뜻이 아니다. 모든 역할을 직렬로 고정하거나 문서 파일만 허용하는 뜻도 아니다.

## 3. 화면과 실제 작동이 이어지는 전체 흐름

아래 번호는 이해를 위한 순서이며 매번 통과해야 하는 메뉴·버튼·승인 관문 목록이 아니다. 특히 대안 작성과 실험 관찰은 여러 지점에서 반복할 수 있다.

| 사용자 경험 | 화면에서 확인할 내용 | 프레임워크가 책임지는 실제 작동 |
| --- | --- | --- |
| 업무를 맡긴다 | 업무 설명 또는 파일, 이해한 목적·완료 조건·권한·위험·미해결 사항과 출처 | 실제 자료 처리와 짧은 업무 모델 구성. 중요한 미확정 조건만 질문하며 읽지 못한 자료를 반영했다고 하지 않음 |
| 환경 설계를 비교한다 | 누가 무엇을 만들고 전달하는지, 도구·자료 접근, 검토 위치, 비용·위험이 다른 기본 3안 | 공통 업무 모델 아래 렌즈 단독/하이브리드 후보 탐색, 별도 크리틱, 필수 제약·품질·구조적 다양성 선별 |
| 설계를 조정하고 승인한다 | 선택·병합·수정한 설계, 필요한 연결, 승인 범위와 구성 상태 | 승인된 버전을 실행 구성으로 변환. 사용자에게 코드·YAML·어댑터 제작을 맡기지 않음 |
| 실제 업무를 운영한다 | 역할별 진행·실패·대기, 실제 입력과 산출물, 앞뒤 전달 관계 | 승인된 역할·권한·도구·게이트를 집행하며 실행·계보·상태 보존 |
| 자신의 버전을 남긴다 | 원본과 자신의 전체/부분 대안, 해당 역할·입력·산출물 맥락 | 실제 대안과 검토 범위를 보존하고 차이·복수 해석을 탐구. 이유·원인 해설을 필수로 요구하지 않음 |
| 변경된 수행을 살펴본다 | 원본/후보 산출물, 대안 밖의 영향, 이전 업무별 개선·악화·실패·미확인 | 격리된 후보 환경 재실행, 필요한 렌즈·새 증거 탐구, 허용 범위의 자동/사람 개입 반복 평가 |
| 새 환경 버전을 승인한다 | 정확한 변경 후보, 검증 근거와 남은 한계, 적용 범위·되돌릴 버전 | 최종 후보 고정·별도 검증 뒤 사람 승인을 해당 운영 버전에 연결. 이후 실제 적용·재검증·철회 추적 |

업무에 따라 결정적 워크플로나 단일 에이전트가 더 적합하면 그 근거도 검토한다. 플랫폼의 멀티에이전트 구성·관제 역량을 없애는 축소안은 아니다. 다중 구조 비교의 기본 3안은 최소 두 구조 축에서 달라야 하며, 적합한 후보가 부족하면 그 상태를 보여 준다. 철학 이름이나 에이전트 수만 바꿔 세 안을 채우지 않는다.

설계 승인, 이번 업무의 외부 행동 허가, 개선된 환경의 지속 운영 승인은 서로 다른 효력이다. 모든 행동에 버튼 세 개를 붙인다는 뜻이 아니라 한 승인을 다른 권한으로 확대하지 않는다는 뜻이다. 자세한 조작·승인 배치는 후속 UX 설계 대상이다.

### 세 모드는 같은 제품의 서로 다른 보기다

- **작업공간:** 원 자료, 역할별 산출물, 내 대안, 비교 결과를 읽고 작업한다.
- **대화:** 같은 업무·산출물을 참조하며 요청·설계 조정·필요한 탐구를 이어 간다. 대화에 남긴 실제 자기 버전도 산출물과 연결한다.
- **그래프:** 설계 구조와 실제 역할·입출력·전달·진행·실패를 탐색한다. 노드에서 해당 산출물·실행 기록으로 연결한다.

세 모드는 같은 환경·업무·버전·대안·실험·승인 이력을 참조한다. 전환만으로 새 실행·승인·학습 이력을 만들지 않는다. 전환 중 작성 내용과 맥락을 잃지 않아야 한다. 모든 기능을 세 번 복제하거나 직접 노드 편집을 사용자 의무로 만드는 설계는 아니다. 공통 상태는 모든 에이전트에게 진단 자료를 공유한다는 뜻도 아니다.

그래프의 설계상 연결, 실제 전달 기록, 관찰된 산출물 계보, 개입으로 지지된 영향은 구별한다. 선이 그려졌다는 사실만으로 정보가 적절히 활용됐거나 원인이 증명됐다고 하지 않는다.

## 4. DeepTwin 엔진의 상세 작동

### 4.1 대안의 범위와 변화의 범위는 다르다

사용자가 한 단락만 자기 버전으로 남겨도 비교는 시작할 수 있다. 차이가 가리키는 작동 방식이 바뀌면 같은 산출물의 다른 부분, 다른 역할, 관련 과거 업무까지 달라질 수 있다. 따라서 다음 세 범위를 따로 관리한다.

- **비교 증거 범위:** 사용자가 실제로 남긴 전체/부분 대안과 검토한 범위.
- **변경 대상:** 탐구에서 나온 후보 기억·판단 정책·프롬프트·핸드오프·역할·그래프·도구·평가·승인 설정.
- **영향·검증 범위:** 후보가 영향을 줄 수 있는 앞뒤 산출물·업무 조건과 실제 시험에서 확인한 범위.

평가·승인 설정을 변경 후보로 다룰 수 있다는 것은 환경이 자신의 합격 기준이나 승인 권한을 자율 변경하도록 허가한 것이 아니다. 해당 변경 권한, 고정할 평가 기준, 기준 변경 전후의 비교 방식은 9절의 상세 정책에서 검토한다. 사람의 최종 운영 승격과 필수 검사 우선 원칙은 이 후보 생성으로 우회할 수 없다.

미검토 영역은 승인된 곳도 변경 금지 구역도 아니다. 부분 증거를 전역 규칙으로 즉시 일반화하지 않지만, 실험도 그 단락에 가두지 않는다. 사용자는 변화된 수행을 보며 다른 부분에 대안을 남길 수 있다. 전체 대안 완성이나 모든 렌즈 질문의 종료를 일률적 선행 조건으로 두지 않는다.

“이 정도 보고 다시 해 보자”는 자연스러운 작업 태도다. 별도 제출 버튼·완료 선언을 요구하는 근거로 삼지 않고, 반대로 마음속 의도나 침묵을 자동 실행 권한으로 읽지도 않는다. 저장·탐구 시작·실험 재개 조작은 이 원칙 안에서 별도로 설계한다.

### 4.2 비교에서 흡수까지의 연결

1. **원 수행을 보존한다.** 입력·역할·모델/구성·도구 결과·산출물/전달 기록을 대안과 사후 해석이 섞이지 않게 유지한다.
2. **실제 대안과 관찰 차이를 연결한다.** 표현뿐 아니라 내용·조건·근거·우선순위·정보 활용의 차이를 맥락 안에서 구별한다. 사용자 설명은 선택적 보조 증거다.
3. **시스템 설명과 사용자 판단 가설을 따로 탐구한다.** 정보 추출/검색/활용/전달 실패인지, 새로운 조건부 판단인지, 일회성 예외·사용자 대안 오류·일반화할 내용 없음인지 경쟁 설명을 유지한다. 없는 실행 기록은 꾸며내지 않는다.
4. **필요한 렌즈가 판별 조건과 새 증거를 찾는다.** 아래 4.3절의 경로로 가설을 구별한다. 렌즈와 무관한 사실 오류까지 철학 문제로 바꾸지 않는다.
5. **시험할 작동 변경을 만든다.** 기존 기능 복원, 새 지식/절차 추가, 보호 장치 보강을 구분한다. 무엇을 바꾸고 어떤 국소·후속 결과가 예상되는지 먼저 남긴다.
6. **실제로 재실행하고 반복한다.** 기준 환경과 후보 환경에서 관련 이전 업무 큐를 비교한다. 자동 또는 필요한 사람 개입으로 수정·재시험한다. 튜닝에 사용한 자료는 최종 미관측 평가로 재명명하지 않는다.
7. **검증된 후보만 운영에 연결한다.** 고정된 후보를 별도 미관측/전향 자료·경계·회귀·출처·안전 검사로 확인한 뒤, 권한 있는 사람이 개선 결과와 범위를 최종 승인한다. 승인한 정확한 후보가 업무 환경의 새 운영 버전이 된다.

이 순서는 매 차이마다 새 지식을 만들어야 한다는 뜻이 아니다. 복구·보호만 필요하거나 원인 미확정·일반화할 지식 없음으로 끝날 수 있다. 이미 흡수한 방식도 새 증거에 따라 조건을 나누고 범위를 고치거나 대체·비활성화할 수 있다. 최신 대안으로 과거 지식을 무조건 덮어쓰지 않는다.

### 4.3 철학 렌즈가 작동하는 세 경로

**초기 설계:** 출처 기반 미세렌즈를 단독 또는 하이브리드로 사용해 실제 역할·조정·기억·권한·평가 구조 후보를 탐색한다. 사용자 목적과 필수 제약은 후보마다 바꾸지 않는다. 별도 크리틱이 각 후보를 개별·병렬·블라인드 평가하며 생성자의 렌즈 정체성·자기평가와 타 크리틱 결론을 가린다. 모든 후보와 조합·탈락 이유를 기록한다(INT-021–023).

**크리틱·보완:** 렌즈는 후보의 전제, 예외, 책임, 누락된 근거를 드러낼 반례·검증 질문을 만든다. 별도 평가 경로가 실제 업무 근거와 시험 결과로 이를 판단한다. 반례 생성과 합격 판정을 같은 것으로 취급하지 않는다(INT-029).

**대안 이후의 심화 탐구:** 관찰 차이와 확인된 사용자 판단 가설에서 서로 다른 설명이 남을 때 SPLI를 적용한다. 실제 업무 사례 비교에서 사용자 언어의 구별을 얻고, 복수 미세렌즈 및 미확정을 유지하며, 한 조건이 달라질 때 예측이 갈리는 질문·새 수행을 설계한다. 새 수행·응답을 보기 전에 렌즈 정의·질문·예측을 고정해 사후에 맞춘 해석과 구별한다. 모든 사용자가 고정된 철학 설문을 먼저 끝내야 하는 온보딩이 아니다. 적합한 실제 사례나 판별 근거가 부족하면 부족함을 남긴다.

논문은 인간·동기, 규범, 앎·해석, 권력·제도, 수양·변화의 다섯 기능 층을 제시한다. 예컨대 아리스토텔레스의 맥락·목적·수단, 듀이의 관찰·시험, 밀의 편익·피해, 공자의 관계·역할, 니체의 기준 형성·변형, 푸코의 관찰·정상화, 폴라니·쇤의 암묵적 단서·성찰적 실험 등은 서로 다른 탐구 질문의 출처다(4.8.1절, 23–25쪽). 이는 최초 구현 렌즈 목록을 확정하거나 철학자 전체를 하나의 성격/프롬프트로 축약한 것이 아니다.

렌즈 정의는 출처·버전·원자적 주장·판별 조건·반대 예측·혼동 요인·금지 추론을 가져야 한다. 일반 사용자 화면에는 철학·렌즈·철학자 이름 대신 구체적인 업무 선택과 그 차이를 보여 준다. 사용자가 원할 때 권한 있는 감사 경로에서는 출처·조합·버전·다른 후보가 낸 결과를 확인할 수 있어야 한다.

**운영 반영의 경계:** 에피소드 철학 해석(H_phi/S_phi)은 운영 규칙이나 변경 후보의 직접 입력이 아니다. 렌즈가 만든 판별 질문 이후의 실제 업무 행동·응답 증거가 사용자 판단 가설을 갱신하고, 그 근거로 조건·행동·예외를 가진 변경을 검증한다. 철학 출처는 감사 참조이며 효과 증거가 아니다. 원 대안 문구를 실행 입력에 복사해 흡수 성공으로 보고하지 않는다.

렌즈가 실질적인 추가 판별력을 주는지는 구현 후 동일 비용 조건에서 비렌즈·일반 다관점·사용자 구성개념 등의 기준선과 비교한다. 비용·정보 접근·평가 자료의 조건을 기록하며 더 많은 호출이나 추가 정답 노출의 효과를 렌즈 효과로 혼동하지 않는다. 이름을 숨겼거나 사용자가 설명에 동의했다는 사실은 효용 증명이 아니다. 미확정·기권·질문 거절을 허용하며 그 자체로 무관한 업무 전체를 멈추지 않는다. 사용자별 철학·성격·민감 특성 프로필은 만들지 않는다.

### 저장·접근의 불변 경계

- 원 실행 기록, 사후 대안·진단, 개입·실험을 각각 식별하고 부모·출처·버전으로 연결한다. 원 실행은 사후 진단 때문에 달라지지 않는다.
- 업로드 문서·외부 도구 결과는 업무 자료다. 그 안의 지시를 사용자의 실행 권한이나 시스템 지시로 승격하지 않으며, 문서·링크·매크로·기억을 통한 오염과 프롬프트 인젝션을 검사한다.
- 대안 원본과 미승격 파생물은 운영 에이전트의 일반 검색에 열지 않는다. 철학 해석 기록도 운영 지식과 분리한다. 화면에서 함께 볼 수 있음과 실행기가 함께 읽을 수 있음은 다르다.
- 재사용 지식이 정본이며 프롬프트는 파생 실행물이다. 업무·역할·권한·시점·호환 조건에 따라 지식을 선택하고 프롬프트·검색·핸드오프·도구·그래프 등에 반영한 버전을 남긴다.
- 기억이 저장됨, 검색됨, 명시적으로 참조됨, 산출물과 연결됨, 개입으로 영향이 지지됨을 구별한다. 체크포인트나 해시만으로 재현·인과·안전을 보장하지 않는다.
- 산출물의 문구 단위 차이를 진단할 수 있어도 하나의 모델 호출 내부 숨은 판단을 임의로 되감지는 못한다. 실제 상태가 보존된 노드·태스크 경계에서 재수행하고 후속 영향을 관찰한다.

## 6. 실행·평가·승인의 공통 경계

### 최종 사용자의 구독 실행

Claude 구독 경로와 Codex 구독 경로를 각각 필수 지원한다. 사용자는 둘 중 보유한 구독 하나로 핵심 LLM 여정을 수행할 수 있어야 하며, 크리틱·렌즈·평가에 숨은 필수 API 경로를 두지 않는다. API는 명시적으로 선택하는 추가 경로다. 사용자 CLI 조작·어댑터 작성·두 구독 동시 보유는 필수가 아니다.

공식 인증·실행 경로를 UI에 연결하는 기술 계약은 별도 검증한다. 제공자·실행기/모델 버전·구독/API 경로를 기록하고, 화면의 선택과 실제 경로가 같아야 한다. 한도·인증 실패 시 기록과 작업 상태를 유지하고 API로 자동 과금 전환하지 않는다. 제작자 계정의 로그인 확인은 배포물 지원 증거가 아니다. 이 기준선은 기술 지원이 이미 완료됐다고 주장하지 않는다.

### 같은 모델에서도 유효한 크리틱

판단 오류의 독립성을 보장할 수 있는 설계는 미해결 핵심 요구로 유지한다. 다른 모델을 권하거나 같은 모델의 한계를 고지하는 것으로 대체하지 않는다. 생성자의 자기평가·렌즈 정체성·타 크리틱 결론을 가리고, 원 자료에서 독립적으로 세운 기준·출처 검사·반례·결정적 검증과 봉인된 시험을 연결하는 구조를 제안한다.

이 격리 구조, 병렬 호출, 다수결, 렌즈 다양성이나 사람 승인을 통계적 오류 독립성의 증명으로 부르지 않는다. 구체 보장 범위·수용 시험을 상세 설계에서 먼저 해결해야 하며 충족 전 완료 판정을 하지 않는다. 필수 검사 실패·근거 부족은 높은 평균 점수로 상쇄하지 않는다. 사람의 위험 수용과 검사 성공도 구별한다.

### 자동 반복과 사람 개입

합의된 실험 권한·데이터·도구·변경 종류·시간/사용량/반복 한도 안에서는 탐구·후보 생성·재실행·비교를 자율 진행할 수 있다. 내부 단계마다 승인을 요구하지 않는다. 새 사용자 수행·판단 증거 또는 추가 권한이 필요하면 관련 부분에서 요청하고, 무관한 작업까지 일괄 중단하지 않는다. 한도·새 증거 없음·안전 문제에서는 해당 범위를 보류/종료하며 부족한 상태를 성공으로 바꾸지 않는다.

이전 업무 재실행에서 발송·구매·외부 파일 변경 등을 중복 수행하지 않는다. 격리 수단이나 재현 자료가 없으면 그 한계를 표시한다. 실제 출력에 영향 없는 관찰 전용과 제한된 적용, 최종 운영 승격은 구별한다. 사람의 최종 승인 전에는 개선 후보를 새로운 지속 운영 기준으로 전환하지 않는다.

### 로그와 두 성장 순환

설치 직후부터 프레임워크 내부의 정상 사용·요청·설계 변경·실행·대안·렌즈·후보 탈락/실패·실험·승인까지 연결 기록한다. 마지막에 로그 화면을 붙이는 것이 아니라 첫 기능부터 기록 계약을 구현한다. 다른 앱 감시·키로깅·자격증명·숨은 사고과정 수집 요구가 아니다.

사용자 업무 환경의 개선과 제작자의 프레임워크 개선은 별개다. 사용자는 원할 때 UI에서 관련 기록을 모으고 공개 범위·가림·빠진 증거를 확인한 파일을 추출해 의견과 함께 전달한다. 전달하지 않아도 자신의 업무와 성장 루프를 완료할 수 있다. 기록된 해시만으로 원문을 복구할 수 없으므로 내용·접근 가능성·재배포 조건·재현 한계까지 구별한다. 제공자 모델 호출에 필요한 자료 전송과 제작자에게 보내는 진단 자료는 다른 경로다.

## 7. 구축 순서와 도구 역할 — 제안

이 표는 개발자가 수행할 순서다. 최종 사용자에게 개발 스킬이나 CLI 사용을 요구하는 절차가 아니다. 세부 일정·파일별 작업 목록은 설계 검토 후 한 계획으로 작성한다.

| 순서 | 산출물·완료 기준 | 사용할 도구와 시점 |
| --- | --- | --- |
| A. 통합 설계 기준선 | 확인된 의도·전체 여정·경계·미결을 한 번에 검토 | Superpowers brainstorming. 제품 구조는 채택됐으며 정리된 문서의 최종 검토가 남음. 수동 피드백 실험 통과를 요구하지 않음 |
| B. 초기 화면 경험 검토 | 설계 이전부터 운영·대안·비교·버전업까지 연결된 화면 흐름, 세 모드와 실패/대기 상태 | 해당 제작 범위의 설계 승인·계획 후 UI 작업. 표시용 데이터와 실제 처리 구별. 세부 미관보다 업무·산출물 연결부터 확인 |
| C. 기능별 명세·기술 계획 | 의도/수용 기준 → 요구 → 실행 작업 → 시험의 연결 | Spec Kit constitution/specify/clarify/checklist, plan/tasks/analyze. Superpowers writing-plans로 실행 전 계획·검증 조건 구체화. 경쟁 계획 두 벌을 만들지 않음 |
| D. 실제 실행 기반과 설계·운영 연결 | 두 구독 연결, 상태·권한·산출물·기록, 설계와 실행 구성 일치, 실제 UI 재개 | LangChain ecosystem-primer/dependencies로 적합성 확인 후 선택한 프레임워크의 해당 스킬. LangGraph 선택 시 상태·HITL·persistence 활용. 공식 문서 확인, TDD·브라우저 E2E. API 전용 가정으로 구조를 먼저 고정하지 않음 |
| E. 실제 DeepTwin 성장 연결 | 대안 → 차이·렌즈 → 변경 → 이전 큐 반복 평가 → 사람 승인·환경 버전업 | 렌즈·출처·방화벽·실험·지식 계약 구현. Eval Engineering으로 실제 환경과 평가기 기반 시험 설계/실행. 미관측·경계·회귀·렌즈 기준선 비교 |
| F. 통합 수용·오픈소스 준비 | 새 설치 사용자의 핵심 여정, 로그 추출, 양쪽 구독, 실패·복구·반례의 실제 증거 | Spec Kit analyze/converge, Superpowers debugging/code review/verification, 단위·속성·통합·브라우저 시험. 공개·푸시는 별도 요청 범위에서 수행 |

실제 진행은 A의 통합 검토 뒤 설계 문서 정리·자체 검토·사용자 검토(B6–B8)를 거쳐, 먼저 초기 화면 범위의 실행 전 계획을 만든 다음 B의 화면 작업으로 이어간다. 그 화면 검토를 반영해 C에서 실제 기능 명세·기술 계획을 구체화한다. 하나의 계획 체계를 범위별로 적용하는 것이며, 계획 없이 UI부터 구현하거나 C까지 화면 검토를 기다린다는 뜻이 아니다.

**첫 UI는 B에서 본다.** 아직 효과 검증은 아니지만 설계·운영·대안·성장 경험이 의도와 맞는지 초기에 검토한다. D–E에서는 같은 화면을 실제 엔진과 연결한다. B를 설계 카드만 있는 독립 데모로 끝내거나 D만 완료하고 전체 제품 완성으로 부르지 않는다. 화면 배치·목업 제작은 이번 문서 작성에 포함하지 않는다.

실행 전 계획으로 넘어갈 때 Superpowers writing-plans를 사용하되 Spec Kit의 기능별 plan.md/tasks.md와 역할을 조정한다. 계획 보강과 실제 실행 작업의 기준을 하나로 유지한다. 현재는 brainstorming 단계이므로 writing-plans·구현 스킬을 시작하지 않는다.

LangChain Skills와 Superpowers는 개발을 돕는 절차이지 설치하면 작동하는 DeepTwin 엔진이 아니다. Deep Agents 채택은 명세 적합성을 검토한 뒤 결정한다. LangGraph도 참조 실행기 후보이며 철학 레지스트리·증거 방화벽·독립 평가·승격 정책을 대신하지 않는다. 버전·API·제공자 통합 조건은 실제 기술 선택 시 다시 확인한다.

렌즈는 E에 처음 붙이지 않는다. 초기 설계·크리틱을 실제 구현할 때부터 그 경로의 렌즈 정의·생성 규칙·감사 기록을 함께 만든다. 사건 기록, 대안/운영 접근 분리, 재현용 버전 계약도 D의 첫 실행부터 포함한다. 추출 화면을 나중에 만들더라도 앞선 로그는 남아 있어야 한다. 평가 기준 설계는 C부터 하며 실제 효과 판정은 실행 가능한 환경·평가기·증거가 준비된 뒤에만 한다.

첫 통합 구현의 업무·형식·도구 폭은 별도로 정하되 설계 → 운영 → 실제 대안 → 탐구 → 반복 평가 → 버전업이라는 전체 연결을 삭제하지 않는다. 기능별 순차 완성을 전체 목표의 축소와 구별한다.

## 8. 의도가 구현까지 보존됐는지 확인할 방법

기존 [수용·거부 사례 AC-001–034](../../acceptance-cases.md)를 유지하고 아래 연결로 기능별 검증을 설계한다. 이 표는 통과 결과가 아니다.

| 보존할 의도 | 거부해야 할 구현 | 기존 근거 |
| --- | --- | --- |
| 프레임워크가 실제 환경 구성·운영 | 사용자가 코드를 준비해야 하는 검수 앱, 장식 그래프·업로드 껍데기 | INT-002–015; AC-001–009 |

| 렌즈의 실제 작동·독립적 평가 | 철학자 역할극, 이름만 다른 3안, 다수결을 독립성 증명으로 사용 | INT-017·021–023·027–029; AC-012–016·022–024 |

## 9. 상세 설계 전에 남은 결정

다음 다섯 묶음은 미결이다. 필요한 하위 기능을 시작하기 전에 해결하되 사용자에게 전부를 다시 설명하거나 설문으로 채우라고 요구하지 않는다. 근거와 추천안을 먼저 제시한다.

1. **첫 지원 범위·배포:** 업무군, 파일·도구, 운영체제·설치 방식, 공식 실행기 패키징과 지원 모델/구독 등급. 두 구독 경로 자체는 필수이며 미결이 아니다.
2. **구체 UI 조작:** 기본 모드, 기능 배치, 대안 저장·탐구/실험 시작·재개, 편집 충돌, 승인 대상·효력의 표시. 세 모드와 부분 반복 원칙은 확인됐다.
3. **렌즈·크리틱 계약:** 최초 검토된 미세렌즈·출처, 하이브리드 규칙, 라우팅·예산, 후보 선별 기준, 판단 오류 독립성의 보장 범위·수용 시험. 단순한 오류 감소로 요구를 낮추지 않는다.
4. **실험·승격 정책:** 이전 큐 선정과 재현 범위, 실제 업무 지표·임계값·평가기, 한도·진전 없음·정지/재개, 최종 봉인/전향 자료, 환경 버전의 변경 묶음과 롤백 범위.
5. **기록·보호·배포 권리:** 저장·보존/삭제·용량·기록 실패 처리, 원문/가림·접근, 공유 파일·전달/수신 보관, 코드·문서·렌즈·데이터 라이선스. 논문 예시를 승인된 정책으로 복사하지 않는다.

## 10. 문서 검토와 다음 단계

이 문서는 사용자가 채택한 제품 구조를 기준선으로 정리한 것이다. 기존 결정의 증거는 제품 의도 기준표와 대화이며, 이 문서가 사용자 원문을 대체하지 않는다. 상세 시나리오의 역사적 수정은 [전체 사용자 여정](../../whole-journey-review.md)과 [진행 기록](../../brainstorming-progress.md)에 남긴다. 이전 초안 경로는 이 문서로 연결하는 안내만 유지하여 서로 다른 설계 정본을 만들지 않는다.

문서화 과정에서는 승인 범위·현재 단계·문서 경로를 명시하고 기존 제품 내용과 미결 사항을 유지한다. 새 UI·제품 코드·설치·제품 모델 실행·계정 조작·공개는 하지 않는다. MANUAL-001의 원본과 종료 이력은 그대로 두며 추가 대안을 요청하지 않는다. 이 기준선 채택을 실제 엔진 검증 성공이나 모든 미결 사항의 승인으로 해석하지 않는다.

정리된 문서를 사용자가 검토한 뒤 Superpowers writing-plans로 이행한다. 그 계획에서 초기 화면 범위와 이후 기능별 설계/구현 순서를 구체화하고, Spec Kit와 경쟁하는 별도 작업 목록을 만들지 않는다. 미결 선택을 필요로 하는 해당 구현은 그 선택이 검토되기 전 착수하지 않되, 모든 하위 기능의 상세 결정을 한꺼번에 요구하지 않는다.
