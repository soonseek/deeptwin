# DG-V01 · 검증·선별·보완 설계 초안

2026-09-07 · Draft 0.5 · 별도 사용자 동의로 A/B1 부품에 이어 B2 내부 감사·오프라인 실행기와 B3 결과 분류·문서 동기화·회귀 확인. 최종 문서 명세/전체 품질 검토 통과. 실제 크리틱 자격 시험·제품 모델 호출·운영 채택은 미실시.

## 1. 승인된 입력과 이번 설계의 범위

사용자는 DG-L01의 [17개 정의 후보와 3개 조합 사례 검토본](../../lenses/review-report.md)을 다음 검증 설계의 기준 자료로 쓰는 데 “응”이라고 답했다. 원전·판본 공백, 학술 미검토, 효과 미검증과 운영 미채택은 유지한다. 이후 엔진 연결 계획 작성, A 호출부 구현, B 상세 계획 작성, B1의 세 작업 구현에 각각 후속 동의했다. 최신 “진행해”는 B2 감사·실행 계획 Task 1–3의 오프라인 구현 승인이다. B1의 합성 자료·규칙·입력/응답 계약에 B2의 사전 기록·오프라인 실행 및 B3 분류·회귀가 연결됐다. 실제 모델·비용·B4 설치/서비스, C 실행·미결 수치 확정·전체 운영 채택 승인으로 확대하지 않는다.

상위 근거는 [그래프 생성 계약](2026-09-07-deeptwin-graph-generation-design.md) §3·6·7·9, [렌즈 조합 계약](../../lenses/composition-contract.md) §1·3·6·7이다. 핵심은 멀티에이전트 관제 환경의 역할·완결된 다중형식 산출물·전달·도구·모델·권한을 평가하는 것이다. 철학 이름에 맞는 문장을 쓰거나 새 감독 노드를 늘리는 시험이 아니다.

## 3. 증명의 단계를 섞지 않는다

| 단계 | 실제로 확인할 것 | 통과해도 주장할 수 없는 것 |
| --- | --- | --- |
| 검사자 자격 | 정답·반례 근거가 별도로 정리된 자료에서 결함, 정상 대안, 미결을 구별; 입력 격리 실제 확인 | 모든 업무의 오류 독립성, 렌즈의 효용 |
| 설계 생성 | 같은 요구를 만족하는 후보의 역할·입출력·전달·기억·권한·평가 구조가 실질적으로 구별됨 | 실제 PDF 생성·도구 실행·업무 품질 |
| 업무 수행 비교 | 같은 입력에서 실제 각 단계 산출물·전달·도구 효과·품질·비용을 비교 | 사용자 판단 흡수나 장기 성장 |
| DeepTwin 성장 | 실제 대안 이후 새 증거로 변경한 환경이 이전 큐·미관측·경계·회귀에서 어떤 차이를 냈는지 평가하고 사람이 정확한 버전을 승격 | 원전 전체의 타당성, 다른 사람·업무에도 동일한 효과 |

첫 구체 시험은 [V01-Q01 Task Spec](../../../evals/deeptwin/tasks/v01-q01/Task.md)이다. 이것은 크리틱의 판별 경계를 먼저 검사하는 개발용 시험 설계다. A 전송·B1 순수 계약과 B2 내부 오프라인 실행기는 있다. 실제 harness의 `task.toml`·`instruction.md`·environment·verifier 패키지, 실제 접근 경계·교차 호출 계보·독립 의미 판정이 연결되지 않아 Q01은 Draft이며 해당 의미 시험은 미실시다. 오프라인 완료 출력은 `semantic: not_checked`, `score: null`이고 구조·참조 계약 통과를 의미 정확성·Q1–Q8 성적으로 쓰지 않는다. 기존 MANUAL-001이나 사용자의 YouTube 설명을 정답·피드백으로 사용하지 않는다. 나머지 단계는 아래 공통 계약을 따른 후속 시험이며 첫 시험의 성공으로 완료하지 않는다.

## 4. 무엇을 어떤 근거로 판정하는가

각 결과는 업무 요구·원자료·후보·모델/도구·렌즈/조합·검사기 버전과 연결한다. 상태는 `통과 / 실패 / 미결 / 미검사 / 시험 무효`를 구별한다. 통과에는 검사한 항목과 범위가 반드시 붙는다.

| 판정 책임 | 독립 근거와 검사 | 실패·미결 처리 |
| --- | --- | --- |
| 구조·권한 | 원형 산출물의 생산자/수신자/형식/접근/버전, 역할 책임, 허용 행위와 승인 경로를 정해진 스키마·정책에서 재계산 | 필수 결함은 다른 점수로 상쇄 불가. 필드 존재만으로 의미가 충분하다고 하지 않음 |
| 원자료 의미 | 원본의 목적·예외·조건과 후보의 실제 계약을 대조. 생성자의 요약이나 self-score를 정답으로 삼지 않음 | 근거 없는 단정은 실패; 자료 자체가 부족하면 미결. 규칙으로 결정 가능한 사실은 LLM에게 재투표시키지 않음 |
| 반례 타당성 | 반례 제안자가 아닌 경로에서 가능한 조건인지, 고정 요구와 관련 있는지, 반박 근거가 있는지 확인 | 허구·무관한 반례는 기각. 미결 반례를 후보의 확정 실패로 바꾸지 않음 |
| 후보의 반례 대응 | 타당성 판정, 해당 후보의 기능 정보, 고정 기준으로 회피/완화/실패/미결을 별도 판단 | 반례 생성자의 결론·권위와 후보 대응의 성공은 별개 |
| 실제 업무 효과 | 각 단계의 원형 산출물, 독립 원자료/정책, 도구 결과와 외부 상태 차이, 제한된 의미·시각 평가 | 설명문·파일 존재·LLM의 성공 주장만으로 실제 효과 판정 불가 |

반례가 아직 미결이면 관련 항목의 자동 통과를 보류한다. 이미 독립 근거로 확인된 다른 항목의 필수 실패는 그 미결 때문에 지워지지 않는다. 판정자는 동등하게 유효한 구조·표현·파일 구성을 허용하며 특정 철학자, 문구, CSV 열 이름, 노드 수를 정답으로 삼지 않는다.

도구 장애·격리 실패·누락된 판정 로그·잘못된 reset·판정 모델 오류는 시험 무효다. 정상 환경에서 에이전트가 요구된 산출물을 만들지 못한 것은 업무 실패다. 제공자 사용량 제한은 에이전트의 철학적 판단 실패로 집계하지 않는다. 다만 완전한 관측 아래 승인된 실행 예산을 소진한 사건은 예산 내 완료 실패로 따로 보고한다.

## 5. 동일 모델을 포함한 크리틱 자격

구성 식별에는 실제 제공자·연결 방식·모델 및 확인 가능한 버전·추론 설정·프롬프트·도구·자료 접근·파서·판정 규칙·참조 정의의 내용 해시를 포함한다. 공급자가 불변 모델 버전을 제공하지 않으면 식별 한계와 검사 날짜를 표시하고 영구 자격이라고 주장하지 않는다. 구성이나 관련 정의가 바뀌면 영향받는 항목을 재검사한다.

프레임워크가 각 검토 호출의 입력과 저장소 접근을 분리해야 한다. 생성자 렌즈 정체성·자기점수·다른 검토자의 결론은 전달하지 않는다. 후보의 실제 기능에 필요한 모델·도구·권한·역할·원자료는 숨기지 않는다. 이름을 가린 프롬프트만이 아니라 읽기 권한·도구 접근·출력 저장소·인계 manifest를 검사한다. 숨긴 이름을 기능 내용에서 추정할 수 있는 한계도 남긴다.

자격 시험에는 실제 검토 대상 구성과 별도로 준비된 정상안, 다른 유효안, 필수 결함, 인용은 있으나 의미가 다른 안, 잘못된 반례, 자료 부족, 유도 문구와 누출 시도를 포함한다. 개발용 결함 후보의 실패를 렌즈 없는 업무 기준군의 실패로 재사용하지 않는다.

- 알려진 필수 결함을 자동 통과한 경우 해당 구성·항목은 수정·재검사 전 자동 통과 자격을 갖지 못한다. 사람의 위험 수용도 검사 성공으로 바꾸지 않는다.
- 정상안 오거절, 놓친 결함, 미결 비율을 항목별 분모와 함께 기록한다. 원자료 의미 검토와 후보 생성이 같은 예외를 함께 놓치는 사건도 연결해 기록한다.
- 공동 실패는 동일 항목의 쌍별 결과와 `생성자가 놓친 경우 크리틱도 놓친 비율`을 함께 확인한다. 조건별 표본 수·불확실성을 표시한다. 동일 prompt 호출 몇 회, 무오류 소표본, 단순 합의율로 통계적 독립성을 선언하지 않는다.
- 구현으로 강제하는 정보 격리와 의미 판단의 확률적 성능을 구별한다. 사용자가 요구한 판단 오류 독립성의 범위·수용 기준이 충족되지 않으면 해당 요구는 미충족으로 남긴다. 모델을 다르게 바꾸는 것으로 이 요구를 대체하지 않는다.

허용 오거절·공동 실패의 수치와 필요한 표본 수는 아직 승인되지 않았다. 이를 0이나 임의 백분율로 채우지 않는다. 자격 검사의 경계 사례가 먼저 실행·점검되어야 추정할 수 있으며, 검증용 자료를 본 뒤 합격 기준을 완화하는 것은 새 평가 버전이다.

## 6. 렌즈의 추가 기여를 확인하는 통제 비교

출발 자료는 DG-L01의 질문·반대 예측·기권 조건이다. 첫 개발 사례를 여러 번 보며 만든 정의는 그 사례의 성적만으로 일반화하지 않는다. 개발에 쓰인 예시와 봉인된 새 사례의 계보를 구별한다.

비교군 제안: 기존에 가장 잘 작동하는 절차, 렌즈 없이 수행, 일반적인 다각도 점검, 관련 정의 각각의 단독 적용, 해당 조합. 기존 절차와 렌즈 없음이 동일하면 중복군임을 기록한다. 역할극이나 이름만 넣은 조건을 실제 렌즈 조건의 대리로 사용하지 않는다.

모든 군에서 같은 업무 목적·필수 정확성·완결된 원형 인계·자료·권한·도구 능력·역할별 모델 설정·평가 기준을 유지한다. 기준군이 원래 갖고 있던 의미 검토나 추적 기능을 빼지 않는다. 일반 다각도 군에도 합당한 탐색 기회를 주며, 렌즈 조건의 이점이 단순히 더 많은 호출에서 온 것인지 비용을 맞춘 비교와 실제 소비량으로 구별한다.

비교 단위를 먼저 고정한다. 초기 **생성 경로**만 비교할 때 실행 시 추가 렌즈 개입은 고정한다. **비평 경로**를 비교할 때는 동일한 후보 풀을 각 조건에 제공한다. **사후 SPLI** 비교에서는 동일한 실제 대안·새 증거 접근 조건과 튜닝 예산을 유지한다. 세 경로를 한꺼번에 바꾼 실험은 전체 구성 효과만 말할 수 있고 개별 경로의 기여로 분해하지 않는다.

| --- | --- | --- |
| 추가 판별 질문과 판단 | 적용 자료·질문·반대 예측·실제 선택 변화 및 무변경 이유 | 철학자 이름 개수·설명 길이 |
| 전달의 효과 | 수신자가 실제 받은 전체 산출물, 의미/출처 보존, 수행 오류·재작업·도구 관측 | 새 표나 필드의 존재 자체 |
| 최종 업무 품질 | 원본과 대조 가능한 내용·허용된 다른 결과·필요 시 실제 시각/사용성 검사 | 정답 예시와 문장 유사도·생성자 자기점수 |

질문·평가 기준·튜닝/봉인 구분·모델·예산·반복·제외 규칙은 결과 관측 전에 기록한다. 각 trial은 격리된 초기 상태로 시작하고 실행 순서·제공자 변화·취소·실패를 보존한다. 지원되지 않는 seed나 구독 사용량 수치를 만들어 내지 않는다. 정상군이 이미 같은 판단을 수행하거나 조합이 추가 기여 없이 비용만 늘리면 `추가 가치 미확인/불필요`도 유효한 결론이다.

## 7. 후보 선별과 한도 내 보완

상위 계약의 기본 3안·최소 두 구조 축 차이를 유지한다. 여기서 두 축은 **초기 비교안 사이의 다양성 조건**이지 단일 문구·한 전달 개선의 최소 규모가 아니다. 미세한 개선도 별도로 평가할 수 있다.

선별 제안은 필수 검사 → 미결·검사자 자격 확인 → 공통 품질 기준 비교 → 구조적 중복 제거 → 최대 3안 제시 순이다. 구조 축은 책임, 입출력 계약, 전달/제어, 기억, 권한, 평가이며 업무상 달라지는 결과와 근거가 있어야 한다. 이름·좌표·노드 수·설명 문자열만 다르면 중복이다. 축만 억지로 둘 바꾸면 품질이 같거나 나빠도 다양성 합격이라는 뜻은 아니다.

품질은 업무 충족·원자료 의미 보존·검증 가능성·운영 부담의 근거와 불확실성을 먼저 비교한다. 높은 점수가 필수 실패를 상쇄하지 못한다. 사용자가 확인한 우선순위가 있으면 그 기준을 사용한다. 유효안 사이에 상충하는 이점이 남고 우선순위가 없으면 다목적 비교로 남기며 임의 가중치를 숨겨 순위를 확정하지 않는다. 정확한 정렬·동률 처리 규칙은 후속 확정 항목이다.

통과한 독립 후보가 1~2개면 그대로 먼저 보여 주고 부족 이유를 표시한다. 0개면 부적합안을 채워 넣지 않는다. 동일 요구 묶음 안의 보완은 실패 항목·중복 이유에 근거하고 재검토한다. 요구·권한·합격 기준을 낮추거나 이전 버전 통과를 재사용하지 않는다.

실행 전 `시간 한도 / 호출·동시성 한도 / 제공자가 지원하는 사용량 한도 / 보완 횟수 / 무진전 허용 횟수 / API 사용 시 승인 비용`을 유한한 값으로 고정해야 한다. 제공자가 사용량을 보여 주지 않으면 관측 불가를 표시하고 시간·호출·반복 한도를 집행하며 돈·토큰을 정확히 제한했다고 주장하지 않는다. 구독→API 전환이나 모델 대체를 자동으로 하지 않는다.

무진전은 새 유효 후보·해결된 실패/미결·실질적 구조 차이가 없고, 같은 결함이나 정규화된 같은 후보를 반복한 상태다. 진전이 있어도 전체 한도는 늘어나지 않는다. 취소·사용자 확정·한도·자격 미달 시 신규 dispatch를 막고 진행 호출에 중단을 요청한다. 늦은 응답은 당시 요청에만 붙이고 현재 후보를 덮어쓰지 않는다. 원격 중단·사용량 종료 보장과 로컬 적용 차단은 구별한다. 위 수치가 비어 있으면 자동 보완 활성화 불가다.

## 8. 사용자 대안 이후 성장 검증

검증 단위는 실제 에이전트가 만든 전체 문서·이미지·표·PDF 등의 특정 버전과 사용자가 작성한 전체 또는 부분 대안이다. “여기를 고쳐라”라는 지시, 최초 업무 설명, 개발 검토 승인은 대안 산출물로 대체하지 않는다. 부분 대안의 관찰 범위와 변경의 후속 영향 범위를 별도로 남긴다. 사람의 생각을 특정 버튼으로 번역하지 않는다.

실제 판단 차이·확인된 H_exp에서 질문과 반대 예측을 고정하고 새 E_phi로 H_exp를 검증한다. H_phi/S_phi는 해석 감사로 격리하며 운영 지식·변경 후보의 직접 입력이 아니다. 개선 후보가 생기면 기준 환경과 후보 환경으로 관련 이전 업무 큐를 다시 수행해 중간·최종 산출물, 영향받은 다른 역할, 실패·부작용·비용을 비교한다. 같은 큐를 튜닝하며 반복한 것은 미관측 검증이 아니다.

후보를 고정한 뒤 별도 미관측·경계·회귀에서 검증한다. 봉인 자료를 보고 수정하면 그 자료는 개발 자료가 되며 새 봉인이 필요하다. 개선 없음·다른 곳의 악화·증거 부족을 숨기지 않는다. 사람은 개선 근거와 허용 범위를 보고 **정확한 환경 버전**을 최종 승인한다. 승인 전 운영 승격은 없고 원 버전·실패 후보도 남긴다. 초기 그래프 선택이나 라이브러리 배포는 이 승격이 아니다.

## 9. 로그·사용자 경험·후속 작업

전체 후보·비선택 정의·조합·기권·반례·타당성·후보 대응·자격 검사·수정·한도·중단·버전과 근거를 연결한다. 사용자 업무 입력과 실행 로그는 배포 후 프레임워크가 관측 가능한 첫 제어 사건부터 프레임워크 범위에서 보존·추출 가능해야 한다. 비밀·숨은 사고과정·무관한 앱 사용 기록은 수집하지 않는다. 원문 무조건 복제·외부 자동 전송을 뜻하지 않는다. 로그 내보내기와 제작자 전달은 사용자가 선택하는 분기다.

일반 화면은 업무 언어의 실제 그래프 비교, 단계별 원형 산출물, 검토 이유와 남은 불확실성을 보여 준다. 내부 철학명·시험 ID·자격 절차를 기본 UX의 추가 단계·설문·승인 버튼으로 노출하지 않는다. 감사 상세에서는 해당 근거를 찾아볼 수 있어야 한다.

재사용할 프로젝트 사실은 [.agents/skills/deeptwin-eval-world/SKILL.md](../../../.agents/skills/deeptwin-eval-world/SKILL.md) 초안에 분리했다. 현재 runtime의 경계, 대안/요구 입력의 구별, 원형 전달, 검사와 효과의 차이만 담고 시험의 정확한 입력·정답·fixture 조건은 Task.md에만 둔다. 기존 메인 저장소의 `.agents/skills/` 관례를 같은 worktree에 적용했으며 전역 설치나 제품 사용자에게 배포한 것이 아니다. 연결된 지식 초안을 포함해 계획의 참고 자료로 사용하되, 새 평가 방법의 실제 타당성이 승인·입증된 것은 아니다.

사용자 동의 후 [첫 크리틱 연결 구현 계획](../plans/2026-09-07-deeptwin-critic-transport.md)을 작성하고 별도 실행 동의로 A를 구현했다. `generation_profiles.py`의 불변 책임 프로필, 단일 격리 코어, `CodexCriticTransport`의 네 책임 진입점과 오프라인 경계 검사가 추가됐다. 이어 B1의 `critic_contract.py`, Q01 합성 자료 생성기와 연구 규칙 보존본, B2의 [감사 journal](../../../app/critic_audit.py)과 [내부 오프라인 실행기](../../../app/critic_trial.py)를 구현했다. 기존 업무 이해 지시·호환 서명·안전 로직·UI/API와 제품 capability 상태는 유지한다.

B2는 불변 10필드에 정확한 입력·schema·manifest·선택·지시/코드 해시 snapshot을 고정하고 private SQLite에 dispatch 전 commit한다. 현재 SQL 선택 버전·account binding을 재검증하지만 provider refresh는 하지 않는다. caller가 통제한 대역만 인스턴스별 직렬 실행하며 audit와 별도 0700 요청 경로를 사용한다. 타입·경로 검사는 우발적 사용 방지이며 OS/적대적 Python 격리가 아니다. runtime profile은 `declared_not_preflight_confirmed`, 요청 model/effort와 보고된 model·확인 불가 실제 effort는 구별한다.

중복·한도·첫 종료 상태·단일 읽기 snapshot, 모든 timeout·활성 취소와 journal 장애의 로컬 적용 차단을 검사했다. 취소 commit이 신호보다 먼저이며 쓰기 실패는 원래 실행에도 audit fault를 전한다. 복구는 호출자가 이전 worker 부재를 확인한 뒤에만 명시적으로 한다. 늦은 worker의 raw는 버리고 bounded event만 관측하지만 쓰기 실패 시 event가 없을 수 있으므로 완전한 감사·원격 중단 보장은 아니다.

정상 대역의 JSON/참조/상태 오류는 `completed` + `output_contract: model_output_invalid`, transport/factory 오류·다른 model은 `invalid`와 일반 원인으로 남긴다. 완료 출력은 항상 `semantic: not_checked`, `score: null`이며 journal 장애는 가짜 terminal로 바꾸지 않는다. 원문은 UTF-8 64,000 bytes까지 보존하며 초과·invalid Unicode·dispatch 전 만료의 세부 기록과 점수 부재는 [감사·실행 계획의 결과 분류](../plans/2026-09-07-deeptwin-critic-audit-ledger.md#task-3-결과-분류상위-문서와-연결-검토)를 따른다.

이 journal은 배포 후 프레임워크가 관측 가능한 첫 제어 사건부터의 로그 보존·추출과 선택적 내보내기/제작자 피드백 전체 기능의 완성이 아니다. 해당 제품 요구와 관제 그래프·원형 산출물·철학 렌즈 기반 DeepTwin 정체성을 유지하며, 개발 결과를 사용자 피드백으로 생성하지 않는다. 실제 harness·반례 원본 해시/부모 기록 계보·provider 전 구간 취소·독립 의미 판정기는 [B4 준비 조건](../plans/2026-09-07-deeptwin-critic-evaluation.md#5-실제-시험-전에-반드시-닫아야-할-준비-조건)에 남는다. A/B1/B2 부품 검사와 B3 회귀를 첫 시험 전체, DG-C01 인터페이스, 크리틱 의미 정확성·오류 독립성·렌즈 효과·실제 파일 수행 성능의 완성으로 쓰지 않는다. C의 모델·반복 수·판정 모델·시간·최대 예상 사용량/비용을 확인하기 전 실제 모델 시험은 시작하지 않는다. 자동 모델 대체·API 전환·재시도는 없다. 이후 실제 검증 자료와 교정 결과를 바탕으로 자격 임계값·효과 판정 기준·정렬·자동 보완 한도를 확정한다. 현재 동의만으로 DG-V01 전체 확정 또는 운영 준비 완료가 되는 것은 아니다.

## 10. 문서 검토와 후속 구현 기록

후속 B 계획 작성: A 결과 뒤 사용자의 “진행해”에 따라 [B 전체 계획](../plans/2026-09-07-deeptwin-critic-evaluation.md), [입력 계약](../plans/2026-09-07-deeptwin-critic-input-contract.md), [감사·오프라인 실행기](../plans/2026-09-07-deeptwin-critic-audit-ledger.md)를 작성했다. B 코드를 구현하거나 모델을 호출한 것은 아니다. 조사에서 확인한 전송 timeout의 시작 위치, 미설치 Harbor, 의미 파서와 의미 검사기의 차이를 실제 시험 전 준비 조건으로 명시했다. 전체 평가 Task와 오류 독립성 요구는 여전히 미완료다.

그 뒤 B1 실행 제안에 대한 별도 “진행해”로 B1의 세 작업을 구현했다. 새 agent 생성 한도 때문에 root가 테스트 우선으로 구현하고 기존 별도 검토자를 재사용했다. 각 작업의 명세·품질 검토를 거쳐 입력 계약 113개, A 전송·프로필 포함 165개, 전체 Python 앱 회귀 482개가 통과했다. 전체 회귀에는 기존 Starlette/AnyIO 경고 1건이 남는다. 검토 중 소유자 교정 경로와 내부 리스트 공유를 수정하고, 보호장치 하나만 없을 때 실제 실패하는 테스트로 중복 키·크기 검사를 보강했다. 자세한 근거와 미완료 경계는 [B1 구현 기록](../plans/2026-09-07-deeptwin-critic-input-contract.md#2026-09-07-b1-구현검사-기록)을 따른다. 모델 호출·사용자 DB·UI·서비스·제품 capability 변경은 없었다. B1 보고 당시 다음 단계였던 B2의 후속 결과는 다음 문단에 구별한다.

최신 “진행해”로 B2 감사·실행 계획 Task 1–3을 진행했다. Task 1과 Task 2는 각각 별도 명세·품질 검토 PASS이며 집중 검사 140개/107개를 확인했다. root의 관련 회귀는 315개(1.75초), 전체 회귀는 729개·기존 경고 1건(9.37초)이었다. B3 분류·문서 동기화·회귀는 반영했고 최종 문서 명세/전체 품질 검토도 통과해 감사 계획 Task 3 Step 3을 완료했다. 상세한 초기 모듈/API 부재 RED와 실제 행동 수정, 파일에 저장하지 않은 메모리 보호장치 제거 검사는 [B2/B3 실행 기록](../plans/2026-09-07-deeptwin-critic-audit-ledger.md#2026-09-07-b2b3-실행-기록)을 따른다. 기존 핵심 파일 100개의 root 해시는 동일했고 새 구현 두 파일·테스트 두 파일 외 기존 production/UI·fixture·렌즈·World Skill·B1 역사 기록은 유지했다. 네 책임의 schema roundtrip이 의미 정답이나 Q01 전체 통과를 뜻하지 않는다.

아래는 초기 문서 작성 시점의 기록이다. root가 초안·Task Spec·World Skill을 직접 읽고 관련 코드와 연결을 확인했다. `v01_runtime_discovery`는 읽기 전용으로 실제 업무 이해 경로와 합성 UI·시험 정의를 조사했다. `v01_contract_review`는 상위 그래프·렌즈 조합 계약과 대조했고, `v01_eval_review`는 평가 설계 지침·Task·World Skill 및 중요 코드 근거를 별도로 검토했다. 두 검토 경로 모두 수정 후 문서 초안 범위에서 통과했다. 제품 크리틱이나 평가 모델을 실행한 것이 아니다.

수정한 실질 지적은 세 건이다. 후보 대응 판정에 반례의 명제·조건·원자료·고정 기준을 함께 전달하도록 명시했고, 모든 반례를 무조건 기각해도 통과하는 허점을 타당/기각/미결 사례로 보완했다. 보완 사례는 조건부 위험의 가능성과 특정 후보에서 실제로 성립하는지의 미결을 다시 구별해 유효한 답을 오거절하지 않도록 수정했다. root는 연구용 제안 경로의 자체 렌즈 입력과 생성자 정체성 비공개를 명료화하고 코드 심볼·스킬 경로를 바로잡았다.

새 세 파일과 연결 문서의 로컬 링크·미완성 표식·끝 공백 검사에서 오류가 없었고 `git diff --check`도 통과했다. 스킬 형식 검사는 번들 Python의 YAML 의존성 부재로 처음 실행하지 못했으나, 이미 설치된 프로젝트 가상환경에서 재실행해 `Skill is valid!`를 확인했다. 패키지는 설치하지 않았다. 이 검사는 문서 구조·스킬 형식 검사이지 시험의 행동 타당성·격리·렌즈 효과 검증이 아니다. 앱 코드·사용자 DB·계정·모델 연결·실제 UI 동작은 변경하지 않았고 커밋·푸시는 하지 않았다.
