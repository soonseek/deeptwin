갱신일: 2026-09-06

상태: 사용자 직접 발언을 기록한 작업 문서. 제품 전체 설계의 승인 완료를 뜻하지 않는다.

### 독립 제품·실제 외부 도구 실행 — 최신 직접 교정(INT-034–035)

사용자는 개별 에이전트의 브라우저·외부 도구 사용과 PDF 등 실제 산출물 생성을 필수로 요구한 뒤, Claude/Codex 구독 이용을 그 앱에서 DeepTwin을 사용하는 방식과 혼동하지 말라고 정정했다. 설명 후의 “다음”은 이 요구를 보존하면서 설계 검토를 계속하라는 요청이다. A/B 화면 골격 선택·설치·연결·모델 호출·구현 시작·외부 게시 승인으로 확대하지 않는다.

- **직접 요구와 기존 원칙의 연결:** INT-002·010·015·025–026·032를 실제 도구와 제품 소유 경계까지 명확히 한다. 업무 설명부터 환경 구성·관제·산출물·대안·탐구·반복 평가·운영 버전업은 DeepTwin 안에서 이어진다. 기술 설정은 프레임워크가 맡으며, 사용자는 업무상 역할·자료·도구·완료 조건을 이해·수정하고 필요한 권한·연결을 확인할 수 있어야 한다.
- **책임 경계:** 도구·산출물·권한·업무 상태와 기록을 특정 제공자의 대화 세션에만 남기지 않는다. 모델 경로가 바뀌어도 기존 환경과 이력은 유지해야 하며, 기존 평가의 호환성과 재검증 필요는 별도로 판단한다. 내부 제공자 연결이 인증·추론 외에 수행 루프를 포함하는지, 어떤 제어가 가능한지는 검증 대상이다. 이름만 ‘연결부’로 바꾸거나 UI만 감싸는 것으로 독립 운영 책임이 충족됐다고 하지 않는다.
- **구독 경계:** 양쪽 구독 경로 각각의 MUST와 명시적 선택 API를 유지한다. 공식 실행 구성요소를 내부에 사용하는 것과 사용자에게 외부 앱·CLI에서 업무를 하게 하는 것은 다르다. 내부 공식 실행기 사용 금지나 구독 자격증명을 추출한 범용 모델 API 중개를 요구 또는 승인한 것으로 해석하지 않는다. 현재 자료와 요구만으로 실제 통합·과금·정책 적합성 완료를 선언하지 않는다.
- **논문 근거:** 4.2절(16쪽)은 업무 설명·자료에서 정보 출처·도구와 역할·권한·산출물을 추출한다. 4.3절(17쪽)은 설계안에 도구 접근·권한·실패·부작용 처리를 포함하고, 4.4절(18쪽)은 실제 실행 스키마·도구 사건·입출력 산출물 계보를 정의한다. 6.1절(37–38쪽)은 실행 엔진이 그래프·역할·도구 호출을 수행하고 특정 프레임워크에 종속되지 않는 인터페이스를 제안한다. 브라우저/PDF의 필수 지원과 독립 제품·구독 경험은 이번 사용자 요구로 명확해진 것이며, 논문에 특정 구현 패키지나 완성된 구독 연결이 제시됐다고 하지 않는다.
- **준비·연결 원칙 확인:** 필요한 도구 구성과 준비 상태를 설계 때 먼저 보여 주되 설계 검토 전에 모든 계정·도구 연결을 끝내게 하지는 않고, 실제 사용 전에 부족한 연결을 안내하는 흐름에 사용자가 “응”이라고 답했다. 업무상 도구·자료·산출물 계획의 수정 가능성과 미연결·권한 부족·미지원·검증 전의 구별을 유지한다. 설계 자체에 필요한 자료/권한이 없을 때의 제약과 수행에만 필요한 연결을 구별하며 준비되지 않은 역할·의존 작업에 미치는 영향을 드러낸다. 자동 설치·신규 도구 개발·연결 시점의 세부 정책·매 호출 승인·화면 골격의 일괄 승인은 아니다.
- **실행 관제의 정보 우선순위 확인:** 업무 진행과 역할별 실제 산출물을 기본으로 보고, 선택한 역할의 실제 도구 작업·상세 근거를 필요할 때 이어서 확인하는 방향에 사용자가 “응”이라고 답했다. 파일을 만든 역할·사용한 자료·버전과 후속 전달/활용 근거를 연결하며 작성 중/확정 버전, 실시간 화면/과거 기록을 구별한다. 열람 자체를 대안 피드백으로 바꾸지 않는다. 이는 정보 우선순위의 확인이지 특정 버튼·고정 패널·기본 모드·브라우저 실시간 표시 기술·지원 형식·자동 전환의 확정이 아니다.
- **실패·개입·복구 원칙 확인:** 허용된 안전한 복구는 프레임워크가 맡고, 사람이 필요한 문제만 영향받는 작업과 연결해 요청하는 원칙에 사용자가 “응”이라고 답했다. 일시적 조회 실패는 기존 권한·시간·비용 한도 안에서 복구하고, 새 로그인·권한·판단이 필요한 역할과 의존 작업은 기다리되 안전한 독립 작업은 계속한다. 외부 행동 응답 유실은 결과 미확인으로 구별해 실제 발생 여부 확인 전 임의 반복하지 않는다. 실제 저장 상태·재개 지점을 확인하고 복원 불가 시 재시작 범위·비용·위험을 알린다. 이는 경험 원칙의 확인이며 재시도 횟수·자동 재개 정책·새 실행/설치/과금 권한은 확정하지 않는다. 일반 오류 복구와 개선 실험·사람 최종 승인·환경 버전업을 구별한다.
- **산출물·개선 연결:** 실제 파일과 만든 역할·사용한 입력·버전을 후속 역할, 전체/부분 자기 대안, 차이 탐구에 연결한다. 도구 선택·조회 결과·오류·전달 누락도 시스템 설명 가설의 근거가 될 수 있다. 단순 도구 오류를 무조건 철학 문제로 바꾸지 않으며, 필요한 판단 차이의 렌즈 탐구·독립 증거·이전 큐 평가·사람 승격을 유지한다. 도구 재사용/새 조회와 외부 쓰기 부작용 통제를 구별하고 자격증명은 기록·내보내기에서 제외한다.
- **아직 정하지 않은 것:** 최초 지원 도구·파일·OS 목록, 도구 실행 기술·패키징, 브라우저 세션 격리·공유, 연결·설치·업데이트·권한 회수 절차, 파일별 미리보기·대안 편집 방식, 사용량·부작용·재현 정책. 이 미결을 이유로 실제 도구 사용과 독립 제품 요구 자체를 후속 선택 기능으로 내리지 않는다.

수용·거부 기준은 AC-035–037에 연결했다. 세 차례 확인된 경험 원칙을 [기존 UI 설계 §8](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#8-독립-제품의-도구-준비실행복구)에 통합하고 UI-13–15를 추가했다. 기존 UI 설계의 검토 기록은 당시 §1–7과 12개 사례에 대한 것이며 이번 요구까지 검증 완료한 것으로 소급하지 않는다. 이후 사용자는 통합 문서 `f55566a`를 기준으로 다음 상세 설계 계획으로 넘어가는 데 “응”이라고 답했다. 당시 확인은 통합 원칙에 한정되며 A/B·세부 조작·기술은 선택하지 않았다.

**화면 골격 후속 선택(2026-09-06):** 화면 상세 작성·추천안 제시 후 “첫 시제품의 기본 배치는 이 A안으로 잡는 것이 맞을까요?”에 사용자가 “응”이라고 답했다. 왼쪽 환경·업무 탐색, 상단 대상·버전, 중앙 작업공간/대화/그래프 전환을 첫 시제품의 기본 골격으로 확인했다. 기본 모드·세부 조작·자동화·저장·제작 범위·기술 선택은 별도 검토 대상이다. UI 정본 §9.3의 클릭 시제품 제작 범위는 제안이며 실제 화면·도구/제공자 연결·엔진은 미구현이다. 아래 과거 미선택 기록을 당시 이력으로 보존하고 현재 A 선택을 우선한다.

**시제품 범위 후속 확인:** 이후 사용자는 §9.3의 여덟 장면·세 모드와 실제 UI 조작/표시용 결과를 구별한 클릭 시제품 제작에 “응”이라고 답했다. 해당 로컬 화면을 제작하고 에이전트 동작 검사를 수행했다. 사용자 화면 검토·실제 AI·도구·학습·평가 효과와 세부 제품 정책은 별도 검증한다. 원본 전문과 부분 자기 버전, 렌즈의 세 진입 경로, 이전 업무 큐·영향·사람 최종 승인, 독립적인 복구·로그 추출의 UI 연결을 검토한다. 사용자 업무 설명이나 실패 POC를 새 학습 증거로 재사용하지 않는다. 구현·검토·실제 검증의 최신 상태는 [진행 기록](brainstorming-progress.md)을 따른다.

### 최우선 의미 교정 — 대안 수행은 입력, 차이의 해석은 탐구 대상(INT-033)

**검토 절차 직접 정정:** 선행 산출물을 보여 주지 않은 채 받은 유튜브 콘텐츠 기획 업무 설명에 대해 사용자는 피드백으로 반영해서는 안 되며 실험으로는 무효라고 지적했다. 업무 상황·자료·실제 선행 산출물을 먼저 제시하고 그 뒤 실제 자기 대안을 받아 비교해야 한다는 정정이다. 해당 설명은 이번 검토의 피드백·학습·효과 검증 자료에서 제외하며, 이후 개인화된 원본을 만든 다음 앞선 설명을 소급해 피드백으로 붙이지 않는다. 설계 요구·평가표로 재포장해 우회 사용하지도 않는다. 대화 이력은 절차 오류 기록이며 사용자 대안 증거가 아니다. 일반적인 업무 부트스트랩 입력과 실제 대안 수행은 제품에서도 구별한다. 현재 요청에 따라 전체 여정 끝의 검토 절차를 재설계했으며 새 절차·예시 패킷·실험이 실행 또는 승인된 것으로 확대하지 않는다.

**후속 확인:** ‘사용자는 대안 수행을 남기고, DeepTwin은 그 차이에 담긴 판단을 탐구한다’는 책임 구분과 논문 4.5–4.8절의 설명에 사용자가 “응”이라고 답했다. INT-033의 핵심 의미가 확인됐다. 대안 편집·업로드 UI, 임시 저장/제출 시점, 상세 렌즈 라우팅·자동화 정책, 전체 설계·구현까지 승인한 응답은 아니다.

**흡수 구조 후속 확인:** 대안 원문·탐구 기록·실행 지식을 분리하고, 검증된 지식과 구성 변화가 환경의 성장으로 남는다는 설명에 사용자가 “응”이라고 답했다. 논문 4.8.5–4.9절 및 5.5절에 근거한 분리·반영 원칙의 확인이다. 구체 저장 기술·스키마·평가 수치·후보 수·시험 예산·UI·충돌 해결 정책의 승인으로 확대하지 않는다. 설명과 범위는 전체 여정 6.1절에 연결한다.

**재학습 원칙 후속 확인:** 성장은 지식을 계속 추가하는 것뿐 아니라, 새 대안 수행과 기존 학습의 관계를 탐구해 이전 지식의 적용 조건을 나누거나 범위를 수정하고 잘못된 학습을 대체하는 것도 포함한다는 설명에 사용자가 “응”이라고 답했다. 전체 여정 6.2절의 핵심 원칙 확인이다. 최신 대안의 무조건 우선·과거 증거 덮어쓰기·무검증 운영 반영이나 구체 충돌 해결 자동화·권한·중단 UX의 승인은 아니다.

**후속 해석 교정(INT-031·033):** ‘이 정도 보면 됐다, 다시 해 보자’는 대안을 일부 남긴 뒤 변화된 전체 수행을 보며 다음 판단을 발견하는 자연스러운 사용 방식에 대한 설명이다. 이를 ‘부분 작성 완료 → 명시 제출 → 비교 시작’이라는 사용자 절차로 바꾼 직전 제안은 철회한다. 특정 버튼만 만들지 않는 것으로 교정을 대신하지 않는다. 제출 여부를 사용자의 확정 판단과 등치하지 않으며, 재현을 위한 버전 식별과 사용자가 자신의 판단을 완결했다고 선언하는 행위는 별개다. 실제 저장·탐구/재실행 계기·UI 조작은 아직 미정이고, 반대로 침묵·마음속 의도를 자동 실행이나 운영 승인의 근거로 쓰지도 않는다.

**범위의 구별:** 대안의 범위는 실제로 확보한 비교 증거의 범위다. 그 차이를 렌즈와 가설로 탐구해 바꾸는 작동 방식은 다른 단락·산출물·에이전트·관련 업무에도 영향을 줄 수 있다. 미검토 영역은 승인된 영역도 변경 금지 영역도 아니다. 부분 증거만으로 전역 일반화를 확정하지 않되 영향·검증 범위를 작성 부분에 가두지 않는다. 구체 변경 가설과 의존 관계, 관련 이전 큐의 재실행·회귀 검사를 통해 원래 대안 범위 밖의 개선·악화도 확인한다. 논문 4.7절(22쪽)의 국소 상태와 하류 결과, 4.9절(29쪽)의 메커니즘 개입 후 비교에 근거한다.

현재 문서에서 ‘피드백’은 별도 명시가 없는 한 에이전트의 산출물과 비교할 사용자의 실제 대안 수행을 중심으로 읽는다. ‘이 부분은 이런 문제가 있으니 이렇게 고쳐 달라’는 코멘트를 대표 입력으로 삼았던 직전 사례는 철회한다. 그 방식은 사용자가 차이를 미리 한 가지 해석으로 정리해 주도록 만들어 DeepTwin이 맡을 탐구를 사용자에게 넘긴다. 최초 업무 요청·명시적 환경 설정 변경 등 다른 의사소통 채널까지 금지하는 뜻은 아니다.

- **논문 명시 — 4.5절 19–20쪽:** 완성 산출물/선택 구간의 수정 또는 새 대안 수행이 핵심이며, 이유 설명은 선택적 보조 증거다. 사후 자기설명을 암묵지의 완전한 설명이나 행동과 독립된 증거로 취급하지 않는다.
- **논문 명시 — 4.6–4.7절 20–22쪽:** 산출물·결정·행동·절차의 관찰된 차이를 정렬하고 복수의 시스템 설명과 전문가 판단 가설을 조사한다. 사용자가 먼저 원인·의도·수정 원칙을 확정해 주는 절차가 아니다.
- **논문 명시 — 4.8절 23–28쪽:** 한 수행은 여러 렌즈와 양립한다. 출처 기반 미세렌즈와 unknown, 대조 상황·새 선택/수행 증거로 설명들의 판별력을 시험한다. 철학적 해석을 바로 운영 지식으로 바꾸지 않으며 실제 내면 원인을 복원했다고 주장하지 않는다.
- **기본 흐름:** 해당 업무 상태·원 에이전트 산출물·사용자 대안 및 범위 보존 → 관찰된 차이 → 복수 가설 → 필요한 렌즈 탐구와 새 수행/응답 증거 → 가설 갱신/기권 → 변경 후보 → 이전 큐 반복 평가·검증·사람 최종 승인. 대안 원문과 그에 대한 시스템의 해석을 별개로 보존한다.
- **부분 수행:** 사용자 버전이 문서 일부에만 있어도 그 대안을 증거로 탐구를 시작할 수 있다. 사용자에게 나머지 산출물이나 이유를 채우도록 강제하지 않는다. ‘일단 이 정도로 다시 보자’라는 표현을 특정 발화·버튼·제출 상태로 요구하지 않으며, 작성 범위를 탐구·변경·영향·평가 범위의 상한으로 삼지 않는다. 대안 원문 복사나 무검증 운영 반영도 허용한 것으로 보지 않는다.
- **비교 가능성:** 같은 역할·업무·입력 상태와 원본/대안의 버전을 연결하되, 결과를 보고 고친 대안과 결과를 보기 전의 독립 수행을 구별한다. 추가 자료·외부 지식·시간 차이가 있으면 확인 가능한 범위에서 기록하며 동일 조건이나 독립성을 꾸며내지 않는다.

### 피드백 해상도·부분 반복에 대한 직접 교정(INT-030–032)

**해석 교정(INT-032·033):** 에이전트별로 책임지는 완결된 산출물은 전체 업무 흐름에서는 중간 산출물일 수 있다. 협업의 전달·입력 단위는 이러한 산출물이며, 사용자는 전체·단락·문구 등 필요한 범위에서 자기 버전의 수행을 남긴다. 두 버전과 앞뒤 산출물의 관계에서 무엇이 달라졌는지는 DeepTwin이 탐구한다. 작은 대안을 받는다는 이유로 전달·진단의 맥락을 한 문장으로 잘라내지 않는다. 직전 ‘고객은 자동화를 원한다’ 예시는 사용자가 협업 구조를 잘못 표현한다고 거부했으므로 대표 시나리오에서 철회한다. ‘기본 해상도’는 작은 문구만이 기본이라는 뜻이 아니라 산출물 맥락을 유지하며 여러 깊이에서 검토할 수 있다는 뜻으로 바로잡는다.

**논문 근거와 해석:** 4.3절(17쪽)은 역할별 입력·출력 계약과 산출물 책임을, 4.4절(18쪽)은 입력·출력 아티팩트 참조와 중간 산출물에서 최종 산출물 부분으로 이어지는 ArtifactLineage를 명시한다. 4.5절(19–20쪽)은 완성 산출물과 일부 구간 수정을 모두 받는다. 따라서 산출물을 중심으로 협업을 추적하고 그 안에서 피드백 범위를 구별한다는 해석이 타당하다. 조사보고서 → 초안 전체 → 크리틱 검토문 → 수정 초안은 이 관계를 설명하는 새 가상 사례이지 승인된 고정 실행 그래프가 아니다.

사용자가 거부한 것은 작은 피드백을 받는 버튼의 부재만이 아니라, 큰 정책·전체 환경 승인을 중심으로 짠 개선 경험의 해상도다. 직전 제안인 ‘업무/평가 기준 변경 승인 경계’는 승인되지 않았으며, 그 논의보다 미세 피드백의 부분 반복 경험을 먼저 바로잡는다.

- **논문 명시 — 4.4절 18–19쪽, 4.5절 19–20쪽:** 핸드오프의 전달 필드·누락, 산출물 부분의 계보, 선택 범위 수정과 중간 단계 대안 수행을 기록한다. 검토한 범위와 미검토 부분을 구별하며 미수정을 승인으로 보지 않는다.
- **논문 명시 — 4.6–4.7절 20–22쪽, 4.9절 29쪽:** 차이가 생긴 문구·행동·전달 사건에서 관련 기록을 좁혀 경쟁 가설을 검토한다. 개입은 최종 결과뿐 아니라 예측한 국소 상태와 후속 효과로 확인한다. 표현 하나를 곧바로 일반 규칙으로 만들지 않는다.
- **논문 명시 — 4.8절 23–28쪽:** 구체적인 판단 차이에서 미세렌즈가 대조 질문·새 업무 증거를 얻는 데 작용한다. 질문 부담·중단·기권을 허용하고 철학 해석을 운영 규칙으로 직접 흡수하지 않는다. 차이가 작다는 이유만으로 렌즈를 배제하거나 항상 발동시키지 않는다.
- **논문 기반 해석:** 피드백 위치, 해석할 판단 차이, 변경 부품, 검증 범위, 운영 승격 단위는 서로 다르다. 환경 버전은 검증된 작은 변경을 담을 수 있으며, 매 문구 수정마다 전체 환경을 처음부터 검토하는 의미가 아니다.
- **사용자 직접 확장 및 INT-033에 따른 의미 교정:** 부분 대안 산출물 → 차이 탐구와 시험 후보 → 재실행 → 결과 관찰 → 추가 대안 수행이라는 점진적 사용을 명시했다. 대안 제출 자체를 이미 해석·검증된 구성 변경으로 취급하지 않는다. 이 구체적 UX가 논문에 그대로 완성되어 있다고 주장하지 않는다.
- **경험 설계 제안:** 이번 시험에 포함할 변경과 미검토·보류·원인 미확정 항목을 구별해 보존한다. 안전하게 시험 가능한 변경은 전체 피드백이나 모든 렌즈 질문이 끝나기 전에도 시험할 수 있게 한다. 미해결 항목이 그 시험의 필수 조건이면 해당 이유와 영향을 받는 범위만 드러낸다. 현재 산출물 수정, 후보 시험 요청, 검증 후 지속 운영 반영은 구별하되 매 내부 단계마다 사람 승인을 요구하지 않는다.
- **검증·승격 설계 제안:** 해당 전달/산출물 변화와 후속 영향, 관련 이전 업무 큐의 비교를 이어 보고 반복 회차를 보존한다. 미검토 영역까지 개선됐다고 보고하지 않는다. 선택한 변경의 적용 범위에 필요한 검증과 사람 최종 승인(INT-018–019)을 유지하되 모든 별개 개선 과제의 해결을 강제하지 않는다. 필수 실패·근거 부족을 부분 승인으로 우회하지 않는다(INT-028). 세부 선택·묶음·의존성·실행 정책은 아직 확정하지 않는다.

- **발동 위치 — 4.2절 16쪽, 4.8절 23쪽, 전체 알고리즘 31쪽:** 확인된 판단 차이와 전문가 판단 가설을 얻은 뒤, 개입·운영 지식 후보를 만들기 전에 SPLI를 사용한다. 의무·피해·역할·정당성·예외·부담 배분의 충돌이 지식 범위에 영향을 주는 경우 발동한다. 사실·형식 오류에 무조건 적용하지 않는다.
- **사용자 언어를 먼저 얻음 — 4.8.2절 25쪽:** 실제 업무 사례 세 개의 공통점·차이점을 비교하게 하여 사용자가 중요하게 구분하는 기준을 얻는다. 이를 복수 미세렌즈에 연결하며 맞지 않으면 unknown을 유지한다. 철학자 이름을 먼저 제시해 답을 유도하지 않는다.
- **출처 있는 복수 관점 — 4.8.1절 23–25쪽:** 철학자 전체의 역할극이 아니라 규범·결과·맥락·앎·관계·권력·변화 등의 구체 미세렌즈를 사용한다. 한 행동을 설명하는 복수 해석과 반대 증거를 유지하며 개인의 고정 성향이나 철학 정체성을 추정하지 않는다.
- **능동적 피드백 확장 — 4.8.3절 25–26쪽:** 경쟁 해석이 다른 선택을 예측하도록 한 조건만 바꾼 대조 상황을 만든다. 사용자의 새 선택을 먼저 받고 설명은 필요할 때 요청한다. 정보 가치·부담·민감성·중복을 고려하며 거절·예산 소진·정보 부족 시 중단한다.
- **새 업무 증거로 돌아옴 — 4.8.4–4.8.5절 26–28쪽:** 해석의 확인·수정·거절과 에피소드 한정 기록을 남기고 미관측 선택의 예측을 먼저 고정한다. 새 업무 행동·응답 증거(E_phi)로 전문가 판단 가설을 갱신하거나 기권한다. 갱신한 가설과 시스템 가설로 개입을 검증한다.
- **흡수 경계 — 4.8.5절 28쪽 및 전체 알고리즘 31쪽:** 철학 해석(H_phi)이나 판단 관점 기록(S_phi)을 개입·지식 후보의 직접 입력으로 쓰지 않는다. 렌즈와 독립된 업무 증거가 뒷받침하는 조건·행동·예외를 후보로 만들고 전이·경계·회귀·사람 승인을 거친다.
- **효과의 검증 — 4.8.5절 27쪽:** 렌즈 없음·일반 다관점 지시·사용자 고유 기준만 사용·구조화 미세렌즈·철학자 역할극을 같은 비용에서 비교한다. 추가 효용은 보장된 결과가 아니다. 기준선을 이기지 못하면 해석의 사용 범위를 줄인다.

**제품 해석 초안:** 피드백은 사용자가 이미 남긴 수정만 수집하는 과정에 머물지 않는다. 필요한 상황에서 사례 비교·대조 질문·후속 업무 검증을 통해 아직 명확하지 않은 판단 조건과 예외의 증거를 더 얻고, 검증된 부분만 운영 구조에 흡수한다. 이 전체 순환을 설계·사용자 여정·검증 범위에서 명시해야 한다. ‘선택적 발동’을 근거로 철학 렌즈를 조용히 누락하거나 부차적인 해설 화면으로 축소하지 않는다.

**후속 응답:** 전체 순환을 설명하고 이를 실제 사용자 경험으로 먼저 제시하겠다는 안내에 사용자가 “그래”라고 답했다. 전체 경험 초안을 제시하는 단계로 진행하며, 아직 제시하지 않은 상세 UX의 승인으로 해석하지 않는다. 검토 초안: [전체 사용자 여정](whole-journey-review.md).

### 이전 업무 큐 평가·환경 버전업 — 사용자 직접 수정

사용자 원문:

> 7 적용 범위를 승인하고 다음 업무의 변화를 확인하기 전에, 해당 변화를 기준으로 이전 업무 큐를 다시 진행하여 얼마나 개선되었는지 평가하는 절차가 빠져있다. 그 루프를 돌면서 (자동 루프이든 사람 개입 루프이든) 개선 된 정도에 대해서 사람이 최종 승인하면 해당 환경이 해당 업무에 대한 멀티에이전트 환경으로서 버전 업 되는것이다.
>
> 8번은 직렬적으로 항상 이어지는 단계가 아니라 선택적으로 하는 행위이다.

- **직접 확정한 의미(INT-018–020):** 이전 업무 큐의 반복 재실행·비교 평가가 운영 반영 승인 전에 들어간다. 자동/사람 개입 반복 후 사람이 개선 결과를 최종 승인하면 해당 업무 환경을 버전업한다. 제작자 피드백 전달은 이 순서 밖의 선택 행위다.
- **논문 연결 — 4.9–4.10절, 29–30쪽:** 기준·개입 실행의 처치 외 조건을 가능한 한 고정하고 반복 분포를 비교한다. 동일 사례 재구성·전이·경계·역사적 회귀를 구분하고, 반복 튜닝에 사용한 자료를 미관측 검증 자료로 다시 사용하지 않는다.
- **논문 연결 — 5.4–5.5절, 36–37쪽:** 검증 결과를 사람이 권한 아래 승인하며, 지식·컴파일된 실행물·워크플로의 버전과 롤백 대상을 연결한다. ‘이전 업무 큐의 반복 평가’와 ‘업무별 환경 버전업’을 제품의 중심 경험으로 명시한 것은 이번 사용자 요구다.
- **구현으로 이어질 해석:** 기준 운영 환경과 실험 후보를 분리하고 회차별 변경·큐·평가·실패 이력을 남긴다. 승인한 정확한 후보와 검증 증거가 새 업무 환경 버전에 연결되어야 한다. 실험 후보 저장이나 자동 점수 통과만으로 운영 버전을 바꾸지 않는다.
- **후속 확인된 자동화 경계:** 허용된 실험 안에서는 차이·렌즈 탐구와 후보 생성·이전 큐 재실행·평가를 자율적으로 이어 가고, 새 사람 수행/선택이나 권한이 필요한 지점에서 개입하며, 검증된 특정 후보의 운영 승격은 사람이 결정한다는 설명에 사용자가 “응”이라고 답했다. 단계마다 승인을 요구하지 않고 관련 의존 지점만 보류하며, 한도·근거 부족·안전 문제를 성공으로 바꾸지 않는다. 부분 대안의 범위를 영향 상한으로 삼거나 침묵을 실행 허가로 추론하지 않는다. 전체 여정 7.1절에 연결한다.
- **아직 미정:** 이전 업무 큐의 범위·선정 기준·순서와 상태 재현, 지표·개선 임계값·평가기, 반복 횟수·비용·사용량과 중단/재개 조건의 구체 값, 실제 시작 계기와 사람 개입 UX, 환경 버전 묶음과 번호 체계. 외부 부작용의 실제 재실행이나 무한 자동 반복을 허용한 것으로 해석하지 않는다.
- **출처 구분:** 반복 평가에 사용한 자료와 최종 검증용 자료는 구분하며 관찰 부족·재현 불가를 성공으로 표시하지 않는다. 원 실행을 덮어쓰거나 전문가 대안을 정답으로 주입해 개선도를 높이지 않는다.

### 초기 설계 후보 탐색에도 렌즈를 활용 — 사용자 제안 및 보완 확인(INT-021–023)

사용자 원문:

> 나는 근데 이 시점이 우리가 갖고있는 철학 렌즈를 한번 더 사용할 수 있는 시점같은데? 사용자에게 어떤 종류의 철학렌즈인지, 심지어 '철학', '렌즈' 라는 단어를 보여주지 않은 상태로 3개의 안을 제안하는건데, 사실은 내부적으로 각 안의 핵심 설계 엔진을 우리 프레임워크가 갖고있는 철학자들의 개별 엔진들의 중점으로, 혹은 하이브리드로 해서 만들어낸 후, 별도의 크리틱 에이전트가 각각을 병렬적으로(개별적으로) 평가한 후, 점수가 높은 3개를 보여주는 방식인거지. 이 과정도 다 로그로 남기는 해야함. 나중에 까볼 때 혹시 어떤 다른 렌즈 또는 하이브리드 구성이 어떤 결과를 냈었는지 알려면 알 수는 있게.
>
> 아이디어 어때?

아래 논문 대조와 보완을 설명한 후 “내부의 관점별·하이브리드 생성과 독립 크리틱으로 질 좋은 서로 다른 세 안을 제시하고, 전체 탐색 기록을 실제 업무 성과까지 연결한다”를 초기 설계 방향으로 삼을지 물었고 사용자는 **“네”**라고 답했다.

**논문과 새 제품 선택의 구분:**

- 4.3절(17–18쪽)은 같은 확인된 업무 목적을 달성하면서 최소 두 구조 축이 다른 기본 3안, 선택·병합과 선택 이유 기록을 명시한다. 렌즈별 생성·병렬 크리틱·후보 선별 알고리즘까지 명시한 것은 아니다.
- 4.8.1–4.8.3절(23–26쪽)은 출처 기반 미세렌즈와 이름을 먼저 노출하지 않는 원칙을 다룬다. 4.8.5절(27쪽)은 반례 생성·설계 검토의 출처 라이브러리 활용과 동일 비용의 비렌즈 기준선 비교를 제시한다. 이를 초기 구조 생성에 확장하는 것은 이번 사용자 제안이다.
- 4.2절(16쪽)의 선택적 적용, 4.8.5절(28쪽)·5.5절(37쪽)의 H_phi/S_phi 운영 유입 금지는 유지한다. 출처가 고정된 렌즈 정의를 설계 탐색에 사용하는 경로와 사용자 판단에 대한 에피소드 해석을 운영에 주입하는 경로를 혼동하지 않는다. 후자는 허용하지 않는다.

**확인된 제품 방향과 경계:**

1. 사용자가 확인한 목적·권한·위험·필수 제약을 모든 후보가 공유한다. 관점 차이는 역할·권한·그래프·기억·핸드오프·평가·사람 개입 등의 실행 구조 차이로 나타나야 한다. 모든 업무에 특정 철학적 구성을 강제하지 않는다.
2. 개별 엔진은 철학자 역할극이 아니라 어떤 기준이 어떤 설계 요소를 생성하는지 명시한 규칙이다. 하이브리드는 구성요소·담당 요소·충돌 처리 방식을 기록한다. 해결되지 않은 규범 충돌을 가중치 평균이나 다수결로 결정하지 않는다.
3. 크리틱은 공통 업무 모델과 후보 설계로 요구 충족·실행 가능성·책임/권한·실패 대응·비용·검토 부담을 평가한다. 생성 렌즈의 이름·조합·생성자의 자기평가와 다른 크리틱의 평가를 가린다. 병렬 실행만으로 판단 독립성이 보장됐다고 주장하지 않는다.
4. 필수 제약 통과 후 품질과 구조적 다양성을 함께 고려한다. 적합한 후보가 부족하면 이를 알리고 기본 3개를 억지로 채우지 않는다. 일반 UI에서는 철학 용어를 숨기되 실제 선택 기준·운영 차이·위험은 설명한다. 사용자의 선택·수정·병합은 유지한다.
5. 모든 후보 및 생성 실패·탈락, 업무 모델/입력 버전, 렌즈 정의·출처·버전과 조합/생성 설정, 평가기/기준/점수/명시적 근거/의견 불일치, 선정 이유, 제시 순서, 선택·수정·병합, 후속 실행·평가·환경 버전을 연결한다. 모델의 숨은 사고과정이나 자격증명의 무차별 수집은 기록 범위가 아니다.
6. 초기 크리틱 점수는 예상 설계 품질이며 실제 개선 증거가 아니다. INT-018–019의 이전 업무 큐 반복 평가와 사람 최종 승인·환경 버전업을 대체하지 않는다. 렌즈 없는 생성 방식도 동일 비용 조건으로 비교하여 후보 수 증가 효과와 관점의 추가 효용을 구별한다. 효과가 이미 입증됐다고 주장하지 않는다.

**미결:** 최초 렌즈 목록과 채택·개정 절차, 업무별 발동/라우팅, 후보 수와 생성 예산, 하이브리드 구성 문법, 크리틱 모델·수·검증 방법, 점수식·임계값·다양성 측정과 불일치 처리, 후보 부족 시 재탐색 정책, 감사 화면·권한·원문/보관/내보내기 범위, 비렌즈 비교의 시점·실험 설계. 이를 이번 “네”로 세부 확정하지 않는다.

이번 확인은 제품 안에서 사용자의 업무 환경 설계안을 생성하는 기능에 대한 승인이다. 프레임워크 자체의 화면 구성 대안 선택, 시각적 동반 도구 사용, 전체 상세 명세나 구현 시작의 승인은 아니다. 로그 수집·실제 생성·평가·외부 전송을 활성화하지 않았다.

### 렌즈를 크리틱·보완·재설계에 연결 — 후속 확인(INT-029)

사용자는 일반적인 ‘보완 → 재검증 → 사용자 질문’ 설명에서 렌즈의 실제 작용이 빠졌다고 지적했다. 기존 문서의 초기 설계 렌즈와 피드백 SPLI가 존재하는 것만으로 그 연결까지 설계됐다고 주장하지 않았다. 다음 확인 질문에 사용자가 “응”이라고 답했다.

> 즉, 렌즈를 ‘초기 설계 생성’뿐 아니라 ‘크리틱의 반례 탐색’과 ‘막힌 판단을 풀어 재설계하는 과정’에 연결하는 것이 의도하신 모습입니까?

**확인된 연결:**

1. **초기 생성:** 출처 기반 단독·하이브리드 미세렌즈가 역할·권한·기억·승인 등 다른 실행 구조를 생성한다(INT-021–023 유지).
2. **크리틱의 탐색:** 렌즈가 후보의 숨은 전제·누락된 이해관계·책임·예외를 드러낼 반례·검증 질문·시험 상황을 만든다. 평가기는 철학 이름·권위나 생성자의 자기평가가 아니라 공통 업무 기준·근거·실제 시험 결과로 판단한다. 렌즈가 다르다는 사실을 INT-027의 판단 오류 독립성 증명으로 쓰지 않는다.
3. **판단 심화와 재설계:** 확인된 판단 차이와 전문가 판단 가설에서 조건·예외·책임 충돌이 남으면 SPLI로 경쟁 설명·최소변형 질문·새 사례를 탐구한다. 새로운 사용자 선택·수정·거절 또는 실제 업무 증거로 판단 가설을 갱신하고 후보 보완·독립 재검증·이전 큐 평가·최종 검증과 사람 승격으로 연결한다. 초기 탐색용 렌즈 정의와 에피소드 H_phi/S_phi의 증거 지위를 혼동하지 않는다.

**함께 설명한 경계:** 단순 계산·필드 누락에는 렌즈를 의례적으로 강제하지 않는다. 에피소드 해석 자체를 운영 규칙·개입의 근거로 넣지 않으며, 근거 부족은 점수로 상쇄하지 않는다(INT-028). 일반 사용자에게 철학·렌즈·철학자 이름을 먼저 보여 답을 유도하지 않는다. 발동·미발동 이유, 렌즈 정의·출처·버전·조합, 질문·응답, 후보 수정과 평가 결과를 추적하되 숨은 사고과정·비밀정보를 수집하지 않는다.

**근거의 구분:** 논문 4.8.1–4.8.5절(23–28쪽)은 미세렌즈, 대조 질문, 새 업무 증거와 갱신·개입·승격 경계를 명시한다. 4.8.5절(27쪽)은 반례 생성·설계 검토의 출처 라이브러리 활용을 다룬다. 이를 초기 후보 생성과 크리틱·보완 루프의 구체 역할로 연결하는 것은 사용자와 확인한 제품 확장이다. 구체 렌즈 목록·질문/후보 수·보완 예산·평가 알고리즘·UI 상태·전체 구현 승인이나 효과 검증 완료는 아니다.

**다음 검토 사항:** 후보 수정과 업무·평가 기준 변경의 구분, 변경 승인과 후보 간 공정한 재비교, 렌즈 질문의 사용자 부담·자동화 범위. 직전에 제안했던 검증 상태 표와 자동 보완 정책 전체가 이번 응답으로 승인된 것은 아니다.

### 동일 모델 크리틱의 판단 오류 독립성 요구 — 설계 재검토(INT-027)

사용자 원문:

> 아니. 동일 모델이라는 이유로 크리틱이 유효하지 않을 수 있다라는 한계를 벗어날 수 있도록 크리틱 에이전트가 설계되어야 한다. 판단 오류의 독립성을 보장할 수 있는 설계여야한다.

- **직접 요구:** 같은 모델의 공통 오류를 수동적으로 고지하는 수준에서 끝내지 않고, 동일 모델로도 유효한 독립 크리틱을 구성하는 것을 필수 설계 문제로 다룬다. 최종 사용자의 단일 구독 경로를 유지하며 이질 모델·두 구독·숨은 API 연결을 필수 해결책으로 요구하지 않는다.
- **직전 제안의 상태:** 기본 모델 하나를 전 역할에 배정하고 필요한 사용자만 역할별 지정을 펼치는 UX는 이 응답으로 승인되지 않았다. 우선 크리틱의 독립 검증 구조와 보장 계약을 검토한 뒤 모델 배정 UX로 돌아간다.
- **논문 명시 — 6.4절, 40쪽:** 평가는 단일 LLM 판정자에게 맡기지 않는다. 결정적 검사기, 형식별 비교기, 근거를 요구하는 의미 평가, 권한 있는 전문가의 블라인드 판단, 알려진 결함을 이용한 통제 실험 등을 구분한다. 생성·진단·평가 모델이 같거나 같은 계열일 때 자기정당화가 커지는지는 위험 가설이며, 생성기와 봉인 평가기의 역할·컨텍스트·접근 권한을 분리하고 평가기 교체 민감도를 분석한다.
- **논문 명시 — 8.4–8.5절, 51–52쪽:** 진단기에게 결함 위치·라벨을 공개하지 않는 통제 실험, 위험-커버리지·기권·부수 오류 측정과 봉인된 새 사례 검증을 둔다. 주요 개입 결과는 블라인드 전문가 승인율·중요 판단 오류율이며 LLM 판정자는 보조 지표다.
- **구분해야 할 주장:** 접근·정보 격리의 구조적 불변조건, 검증된 입력·명세 범위에서의 결정적 판정, 특정 업무 분포에서 측정한 오류·공동 실패, 모든 업무에서의 판단 오류 통계적 독립성은 서로 다른 주장이다. 앞의 조건이나 낮은 오류율을 마지막 명제의 증명으로 바꾸지 않는다. 현재 구현·실험 결과로 어느 보장도 달성했다고 선언하지 않는다.
- **제시한 설계 구조(세부 미확정):** 승인된 원업무 자료에서 후보를 보기 전에 검증 기준·예비 판단을 작성해 봉인한다. 생성자의 요약·자기평가·렌즈 정체성·타 크리틱 결론과 공유 기억 유입을 차단한다. 검증 가능한 제약은 별도 버전 관리된 검사기로, 의미·판단은 출처 대조·반례 시험·봉인 사례로 검증한다. 미확정 항목을 자동 합격시키지 않고 권한자 검토로 보낸다. 초기 설계 크리틱과 운영 개선 평가의 각 목적에 맞게 적용하며, 사람 검토는 오류 독립성의 증명으로 취급하지 않는다.
- **미결:** 사용자가 요구한 독립성의 보장 범위와 확률적 의미, 업무별 정답/판정 근거, 검사기 신뢰 전제, 허용 오류·공동 누락·오거절·보류/검토 범위 및 비용 기준, 모델 변경 시 재검증, 부족한 증거의 처리. 이 항목을 임의로 ‘상관 오류가 조금 줄면 완료’로 낮추지 않는다.

**후속 확인(INT-028):** 위 독립 검증 구조와 논문 6.4절·외부 연구의 범위를 설명한 뒤 다음 질문에 사용자가 “응”이라고 답했다.

> 이 구조에서 ‘검증 근거가 부족한 항목은 크리틱 점수가 높아도 자동 통과시키지 않는다’는 조건까지 필수로 두는 것이 의도에 맞습니까?

확인된 조건은 검증 근거 부족·필수 검사 실패를 높은 점수나 다수결로 덮어 자동 통과시키지 않는 것이다. 독립 검증 구조를 설계하는 방향과 연결하되, 모든 업무의 오류 독립성이 이미 보장됐다는 뜻이나 구체 검사기·평가 수치·자동화 범위·화면·모델 배정 방식·전체 구현의 승인으로 확대하지 않는다. 필요한 새 증거의 확보, 수정·재검증과 권한자 검토의 구체 경험은 다음 설계에서 확인한다. 사람의 확인은 미검증 사실을 소급해 검증 완료로 바꾸는 행위가 아니다.

### 세 가지 화면 모드 모두 제공 — 사용자 직접 결정(INT-024)

사용자 원문:

> 3가지 모드 모두 제공

직전에는 프레임워크 자체의 화면 구성을 업무 작업공간 중심·대화 중심·그래프 캔버스 중심으로 비교하고, 작업공간 중심에 나머지를 보조 수단으로 배치하는 방식을 추천했다. 사용자는 세 가지를 모두 모드로 제공하도록 수정했다. 작업공간 중심만 채택되었다거나 대화·그래프가 보조 위젯에 불과하다고 기록하지 않는다.

- **직접 확정:** 작업공간 모드, 대화 모드, 그래프 캔버스 모드를 모두 제품 범위에 포함한다. 이는 초기 생성 결과로 제시하는 업무 환경 설계안 기본 3개(INT-021–022)와 별개의 UI 결정이다.
- **논문과의 구분:** 논문 4.3–4.4절(17–18쪽)은 구조 비교와 실행 구성·기록 연결을 정하지만 세 화면 모드 자체를 명시하지 않는다. 모드 제공은 이번 사용자 직접 요구다.
- **후속 확인된 설계 관계:** 세 모드는 같은 업무 환경·설계 버전·실행·산출물·사용자 대안·탐구·실험·평가·승인 상태를 다루는 서로 다른 표현·조작 방식으로 설계한다. ‘같은 환경·산출물·성장 이력을 서로 다른 방식으로 다루는 관계’라는 설명에 사용자가 “응”이라고 답했다. 모드 전환만으로 새 환경·별도 실행·승인·버전업을 만들지 않고 공통 권한·검증·로그 경계를 유지한다. 이는 공통 관계의 확인이며 모드별 기능 동등성·구체 화면·저장·자동 실행 정책의 승인은 아니다.
- **검토할 경험:** 작업공간은 실제 역할별 산출물과 사용자 대안을 함께 다루는 데, 대화는 같은 자료·산출물을 참조하며 업무 설명과 탐구를 이어 가는 데, 그래프는 실제 역할·입출력 산출물·전달·실행 기록의 관계를 탐색하는 데 초점을 둔다. 대화에서 제공한 자기 버전도 같은 업무 상태의 대안 산출물로 보존하며, 코칭 지시나 자기설명을 핵심 피드백으로 요구하지 않는다. 그래프의 예정된 연결, 기록된 전달, 관찰된 파생 관계, 검증된 영향은 구별한다. 세 모드에 모든 기능을 동일하게 배치하는지와 그래프 직접 편집 범위는 아직 미정이다. 비개발자에게 코드나 노드 편집을 필수로 요구하지 않는다.
- **미결:** 기본 진입 모드, 사용자별 선택 저장, 수동/자동 전환 정책, 모드 전환 UI, 동시 다중뷰, 모드별 조작/기능 범위, 작성 중인 내용의 저장과 동시 수정 충돌 처리. 특정 기본값·자동 전환·전체 기능 동등성을 이번 발언으로 확정하지 않는다.

세 모드 제공과 같은 환경·산출물·성장 이력을 다룬다는 관계는 확인됐다. 상세 화면 배치·완성 목업·시각적 동반 도구 실행·전체 구현 시작에 대한 승인은 아니다.

### Claude·Codex 구독 실행 필수, API 전환은 사용자 선택(INT-025–026)

사용자 원문:

> 일단 클로드 코덱스 2개 구독 모델 기반 실행은 무조건 지원하는 것으로 스펙을 확실히 잡고 가야겠어. 원하면 API 방식 전환.

배경: 사용자는 API 비용 부담을 줄이기 위해 누구든 자신의 기존 구독을 이 프레임워크에서 이어서 사용하기를 원한다고 설명했다. 공식 연결 경로의 가능성과 제한을 확인한 뒤 위와 같이 제품 요구를 명시했다. 이 요구는 논문에서 추론한 것이 아니라 사용자 직접 결정이다.

**대상 혼동 교정 — 사용자 직접 발언:**

> 내 말은 차후에 이 오픈소스를 다운로드받고 사용할 그 실 사용자들의 모델 사용 행태에 대해서 말한거야

INT-025–026은 배포된 제품의 최종 사용자 실행 계약이다. 제작자의 개발 과정에서 Claude Code·Codex를 사용하는 방식과 분리한다. 개발자 컴퓨터의 설치·인증 성공을 제품 지원 증거로 대체하지 않는다. 개인 계정 점검으로 논의를 옮긴 흐름은 중단하고 최종 사용자의 UI 연결·역할별 실행·사용량·전환 경험 설계로 복귀한다. 사용자의 “다음”은 브레인스토밍 계속 요청이며 모델 호출·개인 계정 추가 조작·구현 시작 승인이 아니다.

**필수 제품 계약:**

- Claude 구독 실행과 Codex 구독 실행은 각각 MUST다. 로그인 버튼·연결 안내·실행 파일 설치만으로 지원 완료라고 하지 않는다. 각각의 지원 계정에서 API 키 없이 실제 핵심 LLM 업무 경로를 실행하는 수용 증거가 필요하다.
- 양쪽 지원은 사용자가 두 구독에 모두 가입해야 한다는 뜻이 아니다. 사용자가 보유한 지원 구독 하나로 해당 실행 경로를 선택할 수 있어야 한다. 여러 역할에 두 제공자를 섞는 상세 모델 배정 UX는 별도 설계한다.
- 초기 업무 이해·설계 후보 생성·크리틱, 승인된 환경의 실행, 피드백 정제·필요한 탐구, 반복 평가 등의 핵심 LLM 경로에 숨은 필수 API 호출을 두지 않는다. 구독 실행을 설계 화면에만 한정하고 실제 작업/평가를 API 전용으로 남기지 않는다. 외부 업무 도구의 별도 인증·요금은 모델 구독과 구분해 안내한다.

## 사용 기록·피드백에 관한 사용자 원문

### 아직 확정하지 않은 설계 선택

- “모든 로그”의 이벤트 종류, 상세 수준, 요청·응답·업로드 자료의 원문 포함 범위.
- 기록 고지·설정의 구체 방식, 민감정보 처리, 저장 위치, 보관 기간·용량·삭제 정책. 자격증명·숨은 추론은 수집 대상에서 제외한다.
- 내보내기 대상 선택, 전달 전 포함 원문·가림 범위 확인의 구체 방식, 파일 형식, 전달 경로와 수신·보관 정책.
- 설치·업데이트·프레임워크 버전·설계 버전 등 원인 분석에 필요한 연결 정보의 세부 스키마와 재현 수준 판정. 관련 맥락과 제외/결손에 따른 재현 한계를 표시한다는 원칙은 확인됐다.

이 미결 사항은 후속 설계에서 다룬다. ‘모든 로그’라는 표현만으로 비밀번호·API 키의 무차별 저장, 업로드 자료 전체 공개, 제작자 서버로의 자동 전송, 무기한 보관을 허용한 것으로 해석하지 않는다. 이 문서 작성으로 로그 수집이나 외부 전송을 활성화하지 않았다.

## 구축 단계에 연결할 사항

아래는 직접 요구를 구현 단계에 반영하기 위한 **개발 절차 제안**이다.

| 단계 | 놓치지 않을 사항 |
| --- | --- |
| 1. 의도 정리 | INT-005–007을 전체 범위 지도에 포함하고, 업무 내부 지식 개선과 구별한다. |
| 2. 시제품 | 사용자 관점의 기록 안내, 로그 추출, 피드백 첨부·전달 흐름을 검토한다. 세부 화면은 아직 미확정이다. |
| 3–4. 명세·계획 | 첫 사용부터 필요한 이벤트·출처·버전 연결과 보관·민감정보·내보내기 계약, 검증 작업을 정의한다. |
| 5. 첫 실제 사용자 여정 | 첫 실행부터 실제 요청·설계·변경·승인 흐름의 기록을 연결하고, 누락 여부를 검증한다. |
| 6–7. 기능 확장 | 새 실행·실패·수정 흐름에도 기록 계약을 확장한다. 피드백 개선 절차를 업무 내 지식 승격과 별도 검토한다. |
| 8. 공개 전 검증 | 새 설치 → 사용·요청·설계 변경 → 로그 추출 → 피드백과 함께 전달하는 실제 흐름을 확인한다. 포함하면 안 되는 정보도 검사한다. |

## 현재 브레인스토밍 상태

**최신 사용자 교정 — 시제품 정체성 검토:** 페이지별 스크린샷을 본 사용자는 설계 비교는 멀티에이전트 관제 환경의 그래프를 기반으로 해야 하며, 역할 산출물은 에이전트별 실행 단계·이력에서 개별적으로 보고 일반 텍스트로 제한할 수 없다고 지적했다. 핵심 정체성은 “멀티 에이전트 관제 환경 기반의 LLMOps + 철학 렌즈 기반 딥트윈”이다. 이는 기존 요구의 맥락 교정이며 그래프 탭·PDF 뷰어를 추가하면 해결되는 단독 기능 요청으로 축소하지 않는다. 실행 그래프·사건·다형식 산출물·평가와 운영 판단이 동일 환경/실행에 연결되고 DeepTwin의 대안 비교·탐구·개입·이전 큐 평가·환경 버전업도 그 대상에서 이어져야 한다. 새 세부 화면/구현 방식은 아직 승인되지 않았다. 기존 시제품 동작 테스트 통과와 제품 정체성 검토 실패를 구별한다. 이 발언은 제품 설계 교정이지 업무 산출물에 대한 학습용 사용자 대안이 아니다.

**후속 확인 — 환경 맥락 유지형 작업대:** 사용자는 이 작업대를 다음 상세 설계의 기준으로 삼는 한정된 질문에 “맞아”라고 답했다. 같은 환경의 설계 비교·실행 관제·개선 실험을 연결하고 작업공간·대화·그래프에서 환경 버전·업무·실행·단계 수행/시도·다형식 산출물의 소속을 유지하는 연결 구조를 확인했다. 참조 관계를 필수 클릭 순서로 만들지 않는다. [UI 정본 §10](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#10-환경-맥락-유지형-작업대--채택된-연결-구조)에 반영했으며 기존 시제품 재승인·예시의 세부 기능 고정·새 구현 승인으로 확대하지 않는다. 다음 검토는 실행 그래프와 수행·시도별 실제 입출력/전달을 이어 보는 상세 경험이다.

**후속 확인 — 수행·시도별 산출물 탐색:** 사용자는 전체 그래프를 유지하면서 선택한 수행·시도의 정확한 입출력·전달 이력을 펼쳐 보는 방식에 “응”이라고 답했다. [UI 정본 §10.3](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#103-확인된-탐색-방식--실행-그래프에서-개별-산출물까지)의 경험 방향을 확인했다. 구체 접힘 규칙·패널·형식별 편집/비교·자동 저장/대안 식별/시험 시작·새 구현까지 승인한 응답은 아니다. 당시 다음 검토로 제시한 다형식 원본·자기 버전 경험의 후속 확인은 아래에 구별한다.

**후속 확인 — 공통 다형식 작업면:** 사용자는 같은 작업면에서 원본과 자기 버전을 함께 다루고 열람·작성·비교 방법은 산출물 형식에 맞추는 방향에 “응”이라고 답했다. [UI 정본 §10.4](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#104-확인된-작업면--다형식-원본과-자기-대안)를 확인 상태로 기록했다. 모든 형식의 범용 편집기·자동 매칭·구체 지원 목록·저장/대안 식별/시험 시작·새 구현의 일괄 승인은 아니다. 당시 다음 검토로 제시한 차이 중심 실행·탐구의 후속 확인은 아래에 구별한다.

**후속 확인 — 차이 중심 실행·탐구 연결:** 사용자는 차이를 선택하면 관련 실행 구간과 경쟁 설명·근거가 함께 따라오는 탐구 방식에 “응”이라고 답했다. [UI 정본 §10.5](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#105-확인된-탐구-방식--관찰-차이-중심의-실행탐구-연결)를 확인 상태로 기록했다. 패널·표시 규칙·질문 정책·자동 실행·진단/렌즈 효과·새 구현의 승인 또는 검증은 아니다. 당시 다음 검토로 제시한 반복 평가 작업면의 후속 확인은 아래에 구별한다.

**후속 확인 — 업무·회차별 실행 쌍 비교:** 사용자는 업무·회차를 고르면 기준/후보 그래프·산출물·평가 근거가 함께 열리는 작업면을 반복 평가의 기본 화면으로 삼는 데 “응”이라고 답했다. [UI 정본 §10.6](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#106-확인된-비교-작업면--이전-업무-큐의-실행-쌍-비교와-버전-승인)을 확인 상태로 기록했다. 배치·평가식·회차 수·예산·자동 실행/승인 조작·개선 효과·새 구현까지 승인하거나 검증한 것은 아니다. 당시 다음 검토로 제시한 초기 후보 그래프 비교의 후속 확인은 아래에 구별한다.

**후속 확인 — 초기 후보 그래프의 같은 초점 비교:** 사용자는 비교 초점을 고르면 각 후보 그래프의 관련 구조·검토 근거가 함께 따라오는 방식에 “응”이라고 답했다. [UI 정본 §10.7](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md#107-확인된-설계-비교--초기-후보-그래프의-같은-초점-비교병합)을 확인 상태로 기록했다. 구체 배치·생성/평가식·병합 자동화·승인 조작·독립성 검증·새 구현의 승인이 아니다. 당시 개별 확인을 묶은 §11 통합 문서와 다음 UI 계획 범위를 사용자 검토로 제시했다. 논문 기반 구조·기록·대안·개입/검증과 사용자 확장을 구별하며, 새 시제품은 정체성/조작 검토이지 엔진 효과 POC가 아니다. 실제 구독·도구·학습·운영 적용은 별도 계약과 검증 대상으로 유지한다.

**통합본 확인과 계획 작성:** 사용자는 §11 통합본을 수정 UI 설계 기준으로 확인하고 writing-plans로 화면 구현 계획을 작성하는 질문에 “응”이라고 답했다. [수정 UI 계획](../.worktrees/ui-structure/docs/superpowers/plans/2026-09-06-deeptwin-control-workspace.md)과 합성 시험 자료 부록을 작성했다. 기존 시제품은 보존하고 별도 control-prototype/ 경로를 계획한다. 이는 향후 파일 경로이며 이번에는 구현 파일·자료 생성·모델/도구 연결·테스트 실행을 하지 않았다. 실제 조작과 표시용 엔진 상태, 새 초안과 사전 구성 사례, 부분 증거와 후속 영향, 문서/코드 검사와 사용자의 정체성 수용을 구별한다. 제작은 다음 사용자 선택 전이다.

- 사용자 요청에 따라 1단계 Superpowers brainstorming을 시작했다.
- 설계의 깊이(INT-015)와 기본 피드백 입력 경험(INT-016)은 확인됐다. 철학 렌즈 누락 지적(INT-017)을 반영한 전체 여정에 사용자가 이전 업무 큐 반복 평가·사람 최종 승인·업무 환경 버전업(INT-018–019)과 선택적 제작자 피드백(INT-020)을 직접 추가·수정했다. 세부 화면·기술 선택은 미확정이다.
- 초기 설계의 단독·하이브리드 미세렌즈 후보 생성, 독립 크리틱과 품질·다양성 기반 선별, 일반 UI의 업무 언어, 전체 탐색 기록과 후속 성과 연결(INT-021–023)이 확인됐다. 기존 피드백 SPLI 경로와 구별되는 새 설계 단계 확장이다.
- 프레임워크 자체의 화면은 작업공간·대화·그래프 캔버스 세 모드를 모두 제공한다(INT-024). 같은 환경·산출물·성장 이력을 다룬다는 공통 관계도 후속 확인됐다. 각 모드의 세부 화면·조작·기능 동등성은 후속 설계·검토 대상이다.
- Claude·Codex 각각의 본인 구독 기반 실제 실행은 MUST이며, API는 사용자가 명시적으로 원할 때 선택·전환한다(INT-025–026). 양쪽 구독의 지원 여부는 확정됐고 상세 연결·모델 배정·사용량 정책은 후속 설계한다.
- 초기 브레인스토밍에서는 제품 의미와 사례를 다룬다. 이후 기능별 설계에서 세부 기술 결정을 다룬다.
- 대안 수행 중심 입력과 해석 책임, 부분 증거와 전체 영향, 흡수 구조·재학습 및 자동 실험/사람 개입 경계의 후속 확인을 유지한다. 업무 설명 수집을 피드백 검토로 이어 가려던 절차는 사용자 정정에 따라 철회했다. 뒤이은 MANUAL-001도 사용자가 기준 기획안을 부적합하다고 판단하여 실제 대안 비교 전에 종료했다. 이전 업무 설명과 이번 시도 거절을 대안·학습·효과 평가 증거로 변환하지 않는다. 사용자가 인정한 대화를 통한 의도 이해와 아직 하지 못한 실제 제품 검증을 구별하며, 같은 수동 검증을 다시 요구하거나 전체 설계·구현 승인으로 확대하지 않는다.
- 진행 기록: [brainstorming-progress.md](brainstorming-progress.md).
- 채택된 상위 기준선: [통합 제품 설계 기준선](superpowers/specs/2026-09-06-deeptwin-integrated-product-design.md). 사용자는 통합안을 다음 상세 설계의 기준선으로 삼는 데 ‘응’이라고 답했고 정리된 문서의 최종 검토와 계획 이행에 ‘그래’라고 답했다. 이후 [별도 작업 폴더의 UI 설계](../.worktrees/ui-structure/docs/superpowers/specs/2026-09-06-deeptwin-ui-structure-design.md)와 검토 사례를 작성했고 A 골격·첫 제작 범위 확인 뒤 클릭 시제품을 만들었으나 사용자 정체성 검토에서 실패했다. 후속 환경 맥락 유지형 연결·탐색·다형식 작업면·탐구·반복 평가·초기 그래프 비교의 경험 방향이 확인됐다. 이 확인을 통합한 UI 문서와 다음 계획 범위도 후속 ‘응’으로 확인됐으며 수정 UI 전용 계획을 작성했다. 실제 엔진은 미구현이며 세부 UI·기술·효과 검증과 새 구현의 일괄 승인으로 확대하지 않는다.
- 최신 직접 교정 INT-034–035와 AC-035–037은 외부 도구·실제 산출물·독립 제품 책임을 명확히 한다. 기존 기준선의 후속 직접 정정 우선 원칙을 적용하며 UI 상세의 도구 준비·연결·실행 경험은 별도로 검토한다. 의도 원문은 계속 이 문서와 대화에서 확인한다.
