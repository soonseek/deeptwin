# DeepTwin — 사용자 의도 보존을 위한 구축 절차 제안

작성일: 2026-09-06  
상태: **검토용 제안. 사용자 승인 완료된 제품 명세가 아니다.**

현재 B5 검토 문서: [통합 제품 설계안](integrated-product-design.md). 아래 8단계는 이전 구축 제안의 상세 기록이며 승인된 일정이 아니다. 통합안 7절은 최신 의도를 연결한 구축 순서 제안이다. 초기 화면 제작도 해당 범위의 설계 검토·승인과 실행 전 계획을 거친다. MANUAL-001은 기준 산출물 부적합으로 비교 전에 종료했으며 재시도나 수동 검증 통과를 다음 설계의 조건으로 두지 않는다.

이 문서는 구축 순서와 개발 도구의 역할을 제안한다. 제품 범위, 화면,
프레임워크, 승인 효력을 새로 확정하지 않는다. 기존 `BOOTSTRAP.md`는
설치 이력이며, 그 안의 CLI·오프라인 코어 우선 순서를 사용자 요구로
간주하지 않는다. 설치된 패키지도 제품 요구사항의 근거가 아니다.

2026-09-06 추가 직접 요구: 설치 직후부터 사용·요청·설계 변경 등 로그를 기록하고,
사용자가 원할 때 추출하여 피드백과 함께 제작자에게 전달하는 흐름을 포함한다.
원문·미결 범위·단계별 반영 사항은 [제품 의도 기준표](product-intent.md)의
INT-005–007을 따른다. 기록 기반은 초기 기능부터 마련하며, 프레임워크 자체의
개선 경로를 아래 7단계의 업무 지식 개선과 구별한다.

후속 직접 요구(INT-018–020): 변경한 환경으로 이전 업무 큐를 재실행·비교 평가하고
자동 또는 사람 개입으로 반복 개선한 뒤, 사람이 결과를 최종 승인하면 해당 업무의
멀티에이전트 환경을 버전업한다. 제작자 피드백 추출·전달은 사용자 여정의 필수
직렬 단계가 아니라 원할 때 하는 선택 행위다. 아래 개발 단계 번호와 혼동하지 않는다.

후속 확인(INT-021–023): 초기 설계안 생성에도 출처 기반 미세렌즈 단독·하이브리드
탐색과 별도 크리틱의 개별·병렬·블라인드 평가를 사용한다. 필수 제약을 통과하고
품질과 구조적 다양성을 갖춘 기본 3안을 업무 언어로 보여 주며, 전체 후보·평가·
탈락·사용자 선택 이력을 후속 실제 성과와 연결한다. 이 확장을 7단계 피드백 SPLI에만
미루지 않고 2단계 시제품·3–4단계 명세·5단계 실제 설계 기능부터 다룬다.

같은 날 후속 자료로 비개발자의 멀티에이전트 관제 환경 구성과 DeepTwin 방식의
평가·성장이 직접 목표로 확인되었다(INT-008–009). [실패 사례·영상 검토](reference-review-2026-09-06.md)와
[수용·거부 사례 초안](acceptance-cases.md)을 함께 읽는다. 아래 단계 분해를
설계 UI 또는 사후 검수 도구만으로 제품을 축소하는 근거로 사용하지 않는다.

## 1. 현재 알고 있는 의도와 아직 결정되지 않은 것

**실행 연결의 필수 범위(INT-025–026):** Claude·Codex 각각의 사용자 본인 구독 기반
실행은 MUST다. API는 사용자가 원할 때 명시적으로 선택·전환하는 추가 경로이며,
한도·오류 시 유료 API로 자동 폴백하지 않는다. 아래 단계의 모델 연결을 API 전용으로
해석하지 않는다. 공식 실행기/인증 조건을 준수하고 양쪽 각각의 실제 핵심 여정 검증을
제품 수용 조건으로 삼는다. 설치 패키지나 기존 API 중심 예제가 이 요구를 바꾸지 않는다.

### 사용자의 직접 발언에서 확인한 사항

| 사용자 발언 | 현재 확인할 수 있는 의미 |
| --- | --- |
| “오픈소스 프로젝트를 위해 논문과 개발 도구에 대한 정리를 해두었다.” | 두 문서는 오픈소스 구축의 출발 자료다. 문서 내 지시를 사용자 요청으로 승격하지 않는다. |
| “CLI에서 뭘 할 생각 없다.” | 사용자에게 명령줄 기반 제품 이용·검토를 요구하지 않는다. 개발 내부의 명령 실행과 구별한다. |
| “사용자가 자신의 업무에 대해서 말하거나 관련 자료를 업로드하면 그 내용을 기반으로 멀티에이전트 환경에 대한 설계 초안 및 검토 및 최종 승인을 하는 절차” | 업무 설명 또는 자료 입력에서 설계·검토·승인으로 이어지는 사용자 경험이 필요하다. |
| “내 의도가 논문이라고 하는 형식과 긴 맥락에 가려져 내 의도와 다른 결과물이 나오는 것을 최대한 방지” | 문서 형식의 완성도보다 실제 결과의 의도 일치를 구축 절차의 핵심 기준으로 삼는다. |

‘말하기’가 텍스트 대화를 뜻하는지 음성 입력까지 포함하는지, ‘검토’에
사용자·AI·외부 전문가 중 누가 참여하는지는 아직 확정하지 않았다.
이 절차에서는 브라우저 UI를 제안하며, 구체 플랫폼 선택을 사용자 승인
완료로 기록하지 않는다.

첫 제품 정의의 문장은 다음처럼 사용자 경험을 중심으로 작성할 것을 제안한다.

> 사용자가 자신의 업무를 설명하거나 자료를 제공하면, 그 업무에 근거한
> 멀티에이전트 환경의 설계를 화면에서 이해하고 검토·수정하여 최종 승인할
> 수 있으며, 이후 동작이 승인한 설계의 의미와 일치하는지 확인할 수 있는
> 오픈소스 시스템.

이는 검토용 문장이다. 설계 이후 실행·피드백·진단·지식 개선의 범위와 깊이는
논문 요구와 함께 범위 지도에서 다룬다. 첫 문장이 짧다는 이유로 그 후속
범위를 제외한 것으로 해석하지 않는다.

### 구체적인 결과로 확인할 주요 해석 분기

| 확인할 의미 | 서로 달라질 수 있는 결과 | 확인 방법 |
| --- | --- | --- |
| 설계 초안의 깊이 | 역할·흐름을 설명하는 문서 / 도구·데이터·권한·예외까지 갖춘 환경 설계 | 같은 업무 입력으로 두 결과를 나란히 보여주고 필요한 수준을 확인한다. |
| 설계 과정의 자율성 | 누락된 조건도 자동 결정 / 중요 조건을 확인하면서 공동 설계 | 승인 담당자가 자료에 없는 사례에서 어떤 동작을 기대하는지 확인한다. |
| 최종 승인의 효력 | 버전 확정 / 환경 생성 허용 / 실제 업무 실행 허용 | 승인 버튼 직전 요약과 직후 상태·외부 효과를 보여준다. |
| 전체 제품에서의 위치 | 설계·승인만 제공 / 실행·피드백·진단·지식 개선으로 이어지는 입구 | 승인 이후까지 이어지는 한 업무 사례와 전체 범위 지도를 함께 검토한다. |

질문지를 한꺼번에 작성하게 하기보다, 개발자가 구체적인 예시와 추천안을
먼저 제시한다. 사용자는 결과를 선택·수정하거나 잘못된 방향을 지적한다.
사용자가 선택하지 않은 가정에는 제안 표시를 유지한다.

사용자 후속 요청에 따라 각 확인 질문에는 **논문 절·쪽의 근거, 논문을 핵심 근거로
도출한 답, 명시와 해석 및 남는 제품 선택의 구분**을 먼저 제시한다. 그 후 이
해석이 사용자 의도에 맞는지 묻는다. 논문이 이미 답하는 내용을 근거 없이
사용자의 단순 선택으로 돌리지 않는다.

## 2. 의도를 보존하는 연결 구조

다음 연결을 하나의 사례에서 끝까지 유지한다.

`사용자 원문 → 확인된 의도 → 맞는/틀린 결과 사례 → 화면·행동 → 요구사항 → 작업 → 검증 증거`

원문은 짧은 요약으로 대체하지 않고 문맥과 함께 보존한다. 각 의도 항목에
출처, 상태(확인됨·제안·미결), 관련 사례, 요구사항 식별자를 붙인다.
논문에만 있는 요구는 ‘논문 유래 후보’, 개발자가 추가한 것은 ‘개발 제안’으로
분리한다. 논문 내용과 직접 발언이 충돌하면 충돌을 드러내고, 구현자가
조용히 한쪽 의미로 정리하지 않는다.

다음 파일은 향후 필요한 산출물 제안이며, 이 문서 작성으로 생성·승인된
것은 아니다. 이후 `docs/product-intent.md`는 직접 발언을 기록하는 작업 문서로
작성했으며, 제품 전체 설계의 승인 완료를 뜻하지 않는다.

| 산출물 | 역할 |
| --- | --- |
| `docs/product-intent.md` | 1–2쪽의 의도 기준표와 원문 참조. 현재 결정을 빠르게 복원하는 출발점. |
| `docs/acceptance-cases.md` | 대표 업무 입력, 기대 결과, 거부 사례, 판단 이유. 모델 문구의 완전 일치 대신 의미와 동작을 검증. |
| `docs/scope-map.md` | 논문 요구와 사용자 요구를 첫 통합 구현·후속 구현·미결·명시적 제외로 구분. 연기와 제외를 구별. |
| `docs/decisions.md` | 변경 이유, 이전/이후 의미, 근거 사례, 사용자 확인 여부. |
| `.specify/memory/constitution.md` | 확인된 의도를 보존하는 개발 원칙. 사용자에게 확인되지 않은 제품 선택을 헌장으로 고정하지 않음. |
| `specs/<feature>/spec.md`, `plan.md`, `tasks.md` | 기능별 요구·기술 설계·실행 작업의 단일 기준. |

핵심 원칙은 문서 수를 늘리는 것이 아니라, 각 작업의 근거와 확인 방법을
찾을 수 있게 하는 것이다. 기능마다 새 문서 묶음을 복제하지 않고 기존
의도·사례를 참조한다. 새 개발 세션은 해당 기능과 연결된 의도·사례·최근
결정부터 읽는다. 요약만으로 새로운 제품 결정을 추론하지 않는다.

## 3. 제안하는 구축 순서

### 1단계 — 의도 기준선과 전체 범위 지도

- 직접 발언, 논문 요구 후보, 개발자 제안, 미결 사항을 분리한다.
- 앞 절의 해석 분기를 실제 결과 예시로 비교한다. 이전 구축 시도의 실패
  사례가 제공되면 가장 먼저 거부 사례로 반영한다.
- 논문의 요구 목록을 사용자 가치와 연결한다. 실행·관찰·피드백·진단·평가·
  지식 관리가 초기 설계 UI를 만들면서 사라지지 않도록 범위 지도를 만든다.
- 완료 증거: 첫 대표 업무, 기대 결과, 원하지 않는 결과, 중요한 미결 사항이
  짧고 구체적으로 설명된다. 제품 의미를 바꾸는 미결 사항은 영향받는 기능의
  구현 전에 해결하고, 다른 기능의 진행까지 막지는 않는다.

사용자가 보는 것: 긴 기술 명세보다 먼저 **같은 입력으로 달라지는 결과 예시**.

### 2단계 — 내용이 있는 사용자 여정과 클릭 가능한 UI

- 업무 설명/자료 입력 → 이해한 내용과 부족한 정보 → 설계 초안 → 검토·수정
  → 최종 승인 → 승인 직후 상태까지 연결한다.
- 이후 실행·피드백·개선은 연결 지점과 미결 범위를 표시한다. 첫 시제품에서
  모든 후속 기능의 상세 화면까지 확정할 필요는 없다.
- 화면에는 대표 업무의 구체적인 입력과 설계 결과를 넣는다. 샘플 자료만으로
  동작하는 곳과 실제 처리되는 곳을 구분한다.
- 설계 근거, 사용자가 수정 가능한 항목, 승인 대상과 효력, 미결 조건이 어디에
  보이는지 확인한다. 그래프·카드·대화 등 표현 방식은 제안 후 선택한다.
- INT-021–023의 내부 탐색·평가 진행, 구조가 다른 기본 3안과 부족/실패 상태를
  표현한다. 일반 비교 화면에는 철학 용어를 쓰지 않고 업무상 차이를 설명한다.
  시제품의 후보·평가 예시는 실제 모델 생성·검증 결과와 명확히 구별한다.
- INT-024에 따라 작업공간·대화·그래프 캔버스 세 모드를 모두 검토한다.
  같은 업무·버전·검토 맥락을 유지하는 연결을 제안하며, 기본 진입 모드와
  전환·동시 표시·모드별 조작 범위는 별도 설계한다. 한 모드만 제공하는 축소안으로 바꾸지 않는다.
- Claude/Codex 구독 연결·모델 선택·한도/오류 상태와 사용자가 선택하는 API 전환을
  시제품 여정에 포함한다. 표시용 로그인/사용량을 실제 연결 성공으로 보고하지 않는다.
- 부족하거나 모순된 자료의 화면도 포함한다. 정상 경로만 검토하지 않는다.
- 완료 증거: 사용자가 화면을 따라가며 원하는 업무 흐름과 잘못된 해석을
  구별할 수 있다. 화면 모양에 대한 동의를 분석 품질 승인으로 확대하지 않는다.

**최초로 직접 보는 UI는 이 단계다. 아직 실제 AI 동작의 완료 증거는 아니다.**

### 3단계 — 확인한 사례와 화면을 명세·수용 기준으로 변환

- Spec Kit `constitution`, `specify`, `clarify`, `checklist`를 적용한다.
  헌장은 원칙을, 기능 명세는 무엇을 왜 제공하는지를 다룬다.
- 각 요구사항에 의도와 사례 식별자를 연결한다. 근거 없는 기능 추가는
  별도 제안으로 분리한다.
- 승인하는 설계의 범위, 버전, 승인 주체와 효력, 승인 후 변경 시 처리,
  저장·환경 생성·실행의 상태 구분을 제품 언어로 명시한다.
- 사용자가 모르는 정보와 시스템이 추정한 정보를 구별한다. 설계가 자료에
  기반한다는 것을 어떻게 확인할지도 수용 기준에 넣는다.
- 초기 후보 생성의 공통 업무 모델·필수 제약, 단독/하이브리드 규칙, 크리틱의
  평가 정보 경계, 품질·구조 다양성 선별, 전체 탐색 로그와 성과 계보를 명세한다.
  후보 수·예산·평가식·임계값·권한/보관 정책의 미결 선택을 구체화한다.
- 두 구독 실행을 필수 요구로 유지하고 API 키 없는 핵심 LLM 경로, 명시적 API
  전환, 과금 경계·실행기/모델 기록·비밀정보 비노출을 AC-019–021과 연결한다.
- 완료 증거: 기대 사례와 거부 사례로 명세를 평가할 수 있다. 중요한 의미를
  일반적인 기본값이나 도구의 자동 추정으로 채우지 않는다.

### 4단계 — 첫 통합 기능의 기술 계획과 검증 작업 분해

- Spec Kit `plan` → `tasks` → `analyze` 순으로 실행한다. 먼저 전체 플랫폼을
  세부 설계하지 않고, 첫 사용자 여정을 끝내는 데 필요한 범위를 계획한다.
- Context7/공식 문서로 사용할 라이브러리의 API·버전 제약을 확인한다.
  LangChain Skills는 명세에 맞는 구현 방법을 검토하는 데 사용한다.
- 모델 연결, 자료 처리, 화면/API, 설계 데이터, 승인 상태 저장, 오류 처리,
  검증용 고정 사례를 한 계획에 포함한다.
- 초기 기술 검증에 Claude·Codex 공식 구독 실행 경로를 각각 포함한다. 인증·
  구조화 결과·병렬 크리틱·이벤트/로그·중단/승인·재개·사용량 한계의 적합성을
  확인하고, API 전용 LLM 호출을 전제한 아키텍처를 먼저 굳히지 않는다.
- 해당 기능에 필요한 데이터 경계·권한·출처·버전 규칙을 먼저 설계하고,
  UI와 함께 구현한다. 안전성과 재현성을 마지막 별도 작업으로 미루지 않는다.
- `tasks.md`에 테스트 작성과 실제 브라우저 검증을 명시적으로 넣는다.
  생성된 작업 목록에 테스트가 자동으로 충분히 들어간다고 가정하지 않는다.
- 완료 증거: 모든 핵심 요구에 구현 작업과 검증 방법이 연결되고, 명세·계획·
  작업 간 중대한 모순과 누락이 해결된다.

### 5단계 — 실제 웹에서 첫 사용자 여정을 끝까지 구현

- 실제 업무 설명 또는 지원 형식의 파일을 처리하여, 입력에 근거한 설계를
  만들고, 검토·수정하고, 합의한 효력으로 최종 승인하는 흐름을 연결한다.
- 단독·하이브리드 후보 생성, 독립 크리틱과 제약·품질·다양성 선별을 실제로
  연결한다. 실패·탈락 후보까지 생성 설정/렌즈 버전/평가 근거/사용자 선택을
  기록하며 중립적 UI와 감사 정보의 경계를 검사한다(AC-012–016).
- 초기 점수를 실측 성과로 표시하지 않는다. 비렌즈 생성 방식과 동일 비용의
  비교를 계획·검증하고, 후속 실행/평가/환경 버전과 연결할 식별자를 보존한다.
- 승인된 설계 버전과 승인 기록을 실제로 저장한다. 두 제공자의 구독 연결을
  실제 설계·크리틱에 적용하며, 모델·비용·자료 전송 선택을 연결 전에 해결한다.
  API 방식은 사용자 명시 선택 시에만 이용하도록 구현·검증한다.
- 고정 예제·모의 응답은 회귀 테스트에 활용하되 실제 생성 기능과 구별한다.
  설치와 import 검증을 제품 동작 검증으로 보고하지 않는다.
- 승인한 시제품 사례를 같은 입력으로 다시 실행한다. 입력 조건을 바꾸었을
  때 관련 설계가 달라지고, 바꾸지 않은 조건은 유지되는지도 확인한다.
- 완료 증거: 화면 조작, 실제 설계 결과, 저장된 상태·버전·승인 기록이 일치한다.
  실제 AI 결과의 적합성과 프로그램 상태의 정확성을 각각 검증한다.
- 세 모드의 제공과 공통 업무·버전·권한·로그 연결을 AC-017–018에 따라 검증한다.
  단계적으로 만드는 중인 상태를 세 모드 제공 완료로 보고하지 않으며,
  모드 전환 때문에 별도 실행·승인이 중복 생성되지 않는지 확인한다.

**실제 데이터를 사용하는 설계·검토·승인 UI는 이 단계의 완료 조건이다.**
달력상의 기간은 대표 사례와 첫 지원 범위가 정해진 후 산정한다.

### 6단계 — 승인된 설계와 실행 환경을 연결

- 1단계에서 정한 제품 범위와 승인 효력에 따라 환경 생성·실행을 연결한다.
  설계 승인이 곧 실제 업무 실행 허가인지 임의로 가정하지 않는다.
- 두 구독 경로가 설계뿐 아니라 승인된 업무의 실제 실행을 지원하는지 확인한다.
  한도/인증 오류 때 상태를 보존하고 유료 API로 자동 전환하지 않는지 검사한다.
- 화면에 표시된 역할·도구·데이터 접근·권한이 실제 런타임에 적용되는지
  검증한다. 미승인 변경이 실행 구성에 섞이지 않도록 한다.
- 사람의 판단이 필요한 지점, 중단·재개·실패 처리, 상태 보존을 연결한다.
- 필요한 불변 실행 기록과 재현 계약을 구현한다. LangGraph 체크포인트는
  실행 상태 보존 수단이며 논문의 재현 요구 전체를 자동 충족하지 않는다.
- 완료 증거: 승인한 구성이 실제 실행에 적용되고, 불허된 동작을 막으며,
  결과와 근거를 화면에서 확인할 수 있다.

### 7단계 — 피드백·철학 탐구·반복 평가·업무 환경 버전업

- 범위 지도에서 확인한 논문 요구를 사용자 가치와 연결해 작은 기능 단위로
  구현한다. 각 기능은 3–6단계의 명세·구현·검증 절차를 반복한다.
- 실제 역할별 완결 산출물과 실행 맥락 → 사용자의 전체/부분 자기 대안 → 차이·시스템/전문가 판단 가설 → 필요한 SPLI의
  사례 비교·능동 질문·새 업무 증거 → 갱신된 가설과 변경 후보의 연결을 검토한다.
- 사용자에게 문제 원인·수정 지시를 먼저 해설하도록 요구하지 않는다. 부분 대안의
  범위로 작동 변경과 후속 영향·검증 범위를 제한하지 않으며, 전체 대안 완성이나
  별도 제출 선언을 시험의 일률적 관문으로 만들지 않는다(INT-030–033).
- 운영 반영 전에 기준 환경과 후보 환경을 분리하고 이전 업무 큐를 재실행한다.
  개선·악화·비용·실패 등을 비교하여 자동 또는 사람 개입으로 후보 수정·재실행·
  재평가를 반복한다. 재현 조건·큐 범위·평가 기준·반복 예산·중단 조건을 명세한다.
- 최종 후보를 고정하고 분리된 미관측/전향 자료·경계·회귀 검사로 확인한다.
  반복용 큐를 봉인된 최종 검증 자료로 재사용하지 않으며 외부 부작용을 통제한다.
- 사람이 개선 결과와 적용 범위를 최종 승인하면 그 정확한 후보를 해당 업무의
  새 환경 버전으로 반영한다. 후보·평가·승인·운영 버전·롤백 대상의 계보를 연결한다.
  자동 반복 개선과 자동 운영 승격을 혼동하지 않는다.
- 초기 설계 탐색(INT-021–023)에서 어떤 관점·조합·선별·수정을 거쳤는지 실제
  결과와 함께 추적한다. 초기 크리틱 점수와 실측 개선을 구별하고, 출처 기반
  설계 탐색과 사용자 에피소드 철학 해석의 운영 유입 금지 경계를 유지한다.
- 전문가 의견을 자동으로 정답으로 취급하는지, 평가 자료가 실행에 노출되는지,
  개선 후보가 승인 없이 적용되는지 등을 관련 명세와 테스트로 검증한다.
- 논문에 있는 Hsys/Hexp, R1–R21, 데이터 경계 등은 원문과 연결된 요구 후보로
  관리하고, 어떤 사용자 결과에 필요한지 설명한다. 용어를 구현했다는 이유만으로
  사용자 가치가 충족됐다고 판정하지 않는다.
- 선택적 발동·후속 연구와 제품 기능의 누락을 구별한다. SPLI는 INT-017의 핵심
  탐구 경험에 포함하며 모든 업무에서 무조건 호출하지 않는다. 효용의 실증은 별도 검증한다.
- 완료 증거: 철학 탐구에서 얻은 증거와 변경 후보가 이전 업무 큐의 반복 평가를
  거쳐 사람 최종 승인과 업무 환경 버전업, 이후 업무의 관찰·재검증으로 이어진다.
  제작자에게 로그를 전달하지 않아도 이 여정을 완료할 수 있다.

### 8단계 — 전체 여정 수용 검증과 오픈소스 공개 준비

- Claude·Codex 각각 구독으로 핵심 LLM 여정(설계·크리틱·실행·피드백·반복 평가)을
  검증하고 명시적 API 전환을 별도 검사한다(AC-019–021). 한쪽이라도 미충족이면
  두 구독 지원이 완료된 제품으로 수용·공개 판정하지 않는다. 정책·기술 장애는
  보고하고 해결 방향을 확인하며 필수 범위를 조용히 연기·제외하지 않는다.
- 처음 확인한 사례와 거부 사례를 새 환경에서 다시 실행한다. 화면·결과·
  권한·버전·재현 기록을 함께 확인한다.
- Spec Kit `converge`로 명세 대비 남은 구현을 찾고, 별도의 의도 검토로
  ‘명세 자체가 처음 의도를 바꾸지는 않았는가’를 확인한다.
- 합성 예제와 키 없는 재현 모드, 사용자용 UI 안내, 개발자 설치 안내,
  CI·보안·라이선스·기여 문서를 준비한다. 키 없는 예제가 실제 AI 설계 품질을
  입증하는 것은 아님을 구별한다.
- 첫 연구 프리뷰, 작동하는 제품, 실증이 끝난 연구 주장을 구별해 공개한다.
  실제 외부 게시·배포는 공개 대상과 범위에 대한 별도 요청을 따른다.
- 완료 증거: 충족·미충족·후속 범위와 검증 근거를 사용자가 확인할 수 있다.

이 프로젝트에서는 Spec Kit의 기능별 `plan.md`와 `tasks.md`를 작업의 단일

기본 저장 경로가 다른 도구는 이 프로젝트의 문서 규칙에 맞춰 적용한다.

이 도구들은 개발하는 AI가 사용하는 도구다. 제품 안에서 업무를 이해하고
설계를 생성하는 에이전트, 설계를 검토하는 사용자, 실행 중 승인을 맡는
사람의 역할과는 별개다. 원격 추적·외부 서비스 연결도 스킬 권고만으로
활성화하지 않는다.

## 5. 검토 부담을 줄이면서 의미 변경을 잡는 운영 방식

집중적인 사용자 검토는 세 종류로 묶는다.

1. **의도·사례 검토:** 1단계에서 맞는 결과와 원하지 않는 결과를 확인한다.
2. **사용자 여정 검토:** 2단계에서 실제 화면과 승인 전후 의미를 확인한다.
3. **작동 결과 검토:** 5단계 및 이후 기능 묶음에서 같은 사례를 실제로 실행한다.

파일마다 승인받거나 모든 기술 선택을 사용자에게 묻지 않는다. 라이브러리
내부 구성, 리팩터링, 테스트 보완처럼 이미 확인된 행동을 보존하는 일은
개발자가 진행한다. 대상 사용자, 설계 자율성, 입력 자료의 취급, 승인 효력,
실제 외부 동작, 핵심 사용자 흐름을 바꾸는 선택만 구체적인 전후 차이와 함께
사용자 판단으로 올린다.

각 기능 완료 보고에는 다음을 짧게 남긴다.

- 원래 의도와 관련 사례.
- 이번에 사용자가 실제로 할 수 있게 된 일.
- 화면뿐 아니라 저장 상태·권한·결과를 확인한 증거.
- 달라진 의미가 있는지, 아직 미구현·미검증인 범위가 무엇인지.

드리프트가 발견되면 영향을 받는 부분을 먼저 구분한다. 원래 의도를 만족하게
고칠 수 있는 버그는 고친다. 제품 의미 선택이 필요한 경우에는 원문·현재
동작·차이·선택지를 보여준다. 그 선택을 의도 → 사례 → 명세 → 작업 → 테스트
순으로 반영한다. 구현하기 편하다는 이유로 수용 기준부터 낮추지 않는다.

마지막으로 프로젝트 소유자의 제품 방향 검토와 제품 이용자의 환경 설계 승인,
실행 중의 업무 승인, 향후 지식 승격 승인은 서로 다른 판단이다. 하나를 받았다고
다른 승인을 받은 것으로 처리하지 않는다.
